# BriefingRelay 보안 설계 / 강화 로드맵

"누구나 이 메일링 API를 쓰지 못하게" 하기 위한 위협 모델과, v1 에 구현된 방어 + 앞으로의 강화 항목.

## 위협 모델 (무엇을 막나)

| 위협 | 시나리오 |
|---|---|
| **오픈 릴레이 남용** | 인증 없이 아무나 호출해 회사 도메인 이름으로 스팸/피싱 발송 |
| **API 키 유출** | 고객 PC의 키가 새어 제3자가 API 호출 |
| **대량 발송/폭주** | 유효 키로 무한정 발송해 O365 한도 소진·계정 차단·평판 훼손 |
| **수신자 악용** | 키 소유자가 임의 외부 주소로 대량 발송(스팸 발판) |
| **전송 구간 도청** | 평문 HTTP 로 API 키·본문 탈취 |
| **키 대조 타이밍 공격** | 응답 시간차로 키를 점진 추측 |

## v1 구현된 방어 (검증 완료)

| 방어 | 구현 | 검증 |
|---|---|---|
| API 키 인증(fail-closed) | `X-Api-Key`, 키 없거나 무효 → 401. 키 0개면 전부 거부 | 401 확인 |
| **인증 우선** | 미인증 호출자에겐 서버 구성 상태(계정/키 유무)조차 노출 안 함 | 401→(인증 후)503 순서 확인 |
| 상수시간 키 비교 | `FixedTimeEquals` | 코드 |
| 일일 쿼터 | 키별 `DailyQuota`, 초과 429 | 429 확인(quota=2) |
| 수신자 도메인 화이트리스트 | 키별 `AllowedDomains`, 위반 403 | 403(gmail) 확인 |
| 입력 검증 | 수신자 수/본문 크기 상한, 주소 형식 → 400 | 400 확인 |
| 키 즉시 비활성화 | `Disabled: true` → 재발급 없이 차단 | 코드 |
| From 고정 | 발신 주소는 서버 설정값(호출자 지정 불가) | 코드 |
| 자격증명 분리 | 비번/키는 secrets 파일/env 주입, git 미포함 | .gitignore |
| 발송 경로 검증 | 실제 O365 연결까지 도달(dummy 인증실패 502) | 502 확인 |

## 강화 로드맵 (우선순위)

### P0 — 운영 전 필수
- **HTTPS 강제**: 인터넷 노출 시 반드시 리버스 프록시(nginx/Caddy)로 TLS 종단. 평문 금지. (README 배포절 참조)
- **키 저장소 영속화**: 현재 쿼터 카운터는 인메모리(재시작 시 리셋). 재시작 우회 발송을 막으려면 SQLite/Redis 로 이전.
- **감사 로그**: 키 이름·수신자 수·시각·결과를 파일/DB 에 남겨 남용 추적(본문·주소 전체는 최소 수집).

### P1 — 남용 억제
- **키별 레이트리밋(분당)**: 일일 쿼터 외 순간 폭주 차단(.NET RateLimiter 파티션=키).
- **수신자 사전등록**: 설치별 "허용 수신자 목록"을 서버가 보관 → 임의 주소 발송 원천 차단(도메인보다 강함).
- **IP 허용목록**: 고객 고정 IP 가 있으면 키+IP 이중 조건.
- **본문 형상 제약**: 브리핑 템플릿 해시/구조 검증으로 임의 콘텐츠 발송 방지(선택).

### P2 — 키 관리 고도화
- **키 로테이션·만료**: 발급일/만료일, 무중단 교체(구·신 동시 허용 창).
- **요청 서명(HMAC)+nonce**: 키를 헤더로 직접 보내지 않고 요청 서명 → 탈취·재전송(replay) 방지.
- **비밀 관리자**: 서버의 O365 비번을 Key Vault/Secrets Manager 로 이전(파일 평문 탈피).
- **mTLS**: 클라이언트 인증서로 설치본 신원 강화(키 유출만으로 불충분하게).

### P3 — 확장/운영
- **스케일아웃 대응**: 다중 인스턴스 시 쿼터/레이트리밋을 분산 저장소로.
- **모니터링·알림**: 비정상 급증·연속 실패·차단 발생 시 알림.
- **관리 API/UI**: 키 발급·비활성·쿼터 조정을 런타임에(현재는 설정 파일 편집+재시작).

## 설계 노트 / 트레이드오프
- **쿼터는 시도 기준 소비**(성공만이 아님) — 실패 재시도 폭주를 억제하나, 정상 실패가 한도를 깎음. 브리핑(저빈도)엔 무해. 필요 시 "성공만 차감"으로 전환 가능.
- **키는 여전히 고객 PC 에 존재** — 유출 자체는 못 막지만, (1) 메일 비번은 서버에만, (2) 키별 폐기/쿼터/도메인 제한으로 **피해 범위와 통제력**을 확보하는 것이 이 구조의 목적.
