LLM Chat 으로 Promaker 모델링

자연어 사양에서 실행 가능한 설비 모델까지 — 동작 원리와 사용 매뉴얼

대화로 모델링하는 새로운 작업 흐름

대화 → 의미 분해 → 선언적 모델 → 검증·반영 → 1 단계 되돌리기

1왜 LLM Chat 으로 모델링 하는가?

사용자는 도메인 어휘 (구역 / 실린더 / 펀치 / 후진) 로 말하고, LLM 이 모델 요소로 분해합니다.

① 도메인 어휘 그대로 입력

  • "두 개 실린더가 순차 전진 후 후진" — 한 줄 그대로 입력
  • Flow / Work / Call / Arrow 같은 모델링 어휘를 사용자가 외울 필요 없음
  • LLM 이 현장 어휘 ↔ 모델 어휘 매핑을 담당

② 반복 작업 자동화

  • "실린더" 한 마디가 전진/후진 동작 한 쌍 + 인터페이스 + 연결선까지 자동 구성
  • 3 구역 × N 실린더 × 펀처 같은 대량 구성도 한 발행에 완성
  • GUI 라면 수십~수백 클릭이 필요한 작업을 문장 하나로

③ 의도 기반 점진 편집

  • "3구역 다음에 4구역 추가, 실린더 두 개 순차 전진" — 기존 모델 보존하며 추가
  • 이름 변경 / 제거 / 연결 추가 — 관련 요소 자동 정리
  • 1 대화 turn = 1 되돌리기 단계 (실수해도 Ctrl+Z 한 번)

④ GUI / Chat 자유 혼용

  • GUI 에서 수동 편집한 내역은 자동으로 LLM 에 전달 — 같은 모델을 두 채널이 공유
  • 현재 모델 상태를 LLM 이 매번 다시 조회할 필요 없음 (자동 첨부)
  • 대량 변경은 Chat, 미세 수정은 GUI 가 빠름 — 자유롭게 교대 사용

⑤ Greenfield Modeling — 백지에서 시작

아무 것도 없는 상태에서 자연어 채팅만으로 설비 모델링을 시작할 수 있습니다. 사양만 있고 코드/도면/주소가 아직 없는 단계에서, LLM 이 모델 골격을 한 번에 분해합니다.

⑥ 발행 결과 즉시 시각화

LLM 이 만든 모델은 채팅창에 YAML (사람이 읽는 표기) 과 Mermaid 다이어그램 (구조 시각화) 두 가지로 함께 표시 — 사용자는 적용 전 / 적용 후 결과를 한눈에 검토합니다.

2LLM 강점 vs Promaker 강점

두 시스템의 책임이 명확히 나뉘어야 결합이 의미를 가집니다.

LLM 잘 하는 일

  • 자연어 의미 분해: "두 실린더 동시 전진 후 펀치" → 동시 동작 + 합류 흐름 추론
  • 도메인 패턴 일반화: 실린더 / 클램프 / 푸셔 / 로봇 어휘를 표준 디바이스 타입으로 분류
  • 이름 추론 / 기본값: 사용자가 미명시한 이름을 사양 단서에서 자연스럽게 추출
  • 모호 사양 명확화: 한 번의 질문으로 부족한 정보 회수 — 현장 어휘로 풀어 질문
  • 사양 클러스터링: 한 작업 영역 안의 sub-action 들을 적절히 묶음
  • 이미지 · PDF 사양 해석: 도면 / 표 / 손그림 직접 인식
+

Promaker 잘 하는 일

  • 스키마 / 제약 검증: 발행 전 사전 검증 + 오류 시 유사 후보 자동 제안
  • cascade / 트랜잭션: 디바이스 한 줄이 흐름·작업·인터페이스·연결선까지 일관 생성. 실패 시 일관 rollback
  • 식별자 / 일관성 관리: LLM 은 이름만 다루고, 내부 식별자와 참조 무결성은 Promaker 가 책임
  • 되돌리기 / 왕복 보존: 1 turn = 1 undo. 모델 → 문서 → 모델 왕복 시 형태 보존
  • 시각 편집 / 3D 뷰: 시뮬레이션, 수동 제어, 캔버스 드래그
  • 물리 / 런타임 연결: PLC 주소 binding, IO 태그, 다중 실행 모드

책임 경계 — 한 줄 요약

LLM 책임 = 자연어 → 선언적 모델 정규화 (이름·구조·연결 종류 결정).
Promaker 책임 = 모델 구성·일관성·트랜잭션 — LLM 이 직접 만져서는 안 되는 영역입니다.

왜 선언적 모델인가?

  • LLM 친화: 들여쓰기와 의미 구조가 명확
  • 왕복 보존: 같은 모델을 발행 ↔ 다시 읽기 했을 때 형태 동형 — 다음 turn 에 LLM 이 일관되게 이어 작업
  • 내부 식별자 노출 0: 모든 참조는 사람이 읽는 점-경로 (제어기.실행.구역1)
  • YAML 표기 / 내부 전송 형식 분리: 사용자에겐 가독성, 시스템에는 결정성

결합 효과 — 1 + 1 > 2

  • LLM 의 추론 자유도 + Promaker 의 제약 엄정성
  • 실수해도 1 undo. 검증 오류 시 LLM 이 후보 제안을 받아 자가 정정
  • 사양 변경 시 부분 발행으로 점진 진화 — 전체 재작성 불필요
  • LLM provider 선택 자유 — 계약이 동일하므로 결과 비교가 직접 가능

5자연어 분해 — 도메인 룰

LLM 이 어떤 원칙으로 자연어를 모델로 분해하는지 — 핵심 7 원칙

① 한 station = 1 작업 단위

"구역" / "공정" / "스테이션" = 부품이 머무는 한 station = 작업 단위 1 개. 그 안의 전진 / 펀치 / 후진 은 같은 작업 안의 sub-action 으로 묶입니다. 페이즈마다 작업을 쪼개지 않습니다.

② 능동 / 수동 명시

제어 로직을 가진 시스템(능동)과 제어를 받는 디바이스(수동)를 분리. LLM 이 추론으로 결정하지 않고 항상 명시 — 사양에 단서가 없으면 사용자에게 1회 질문.

③ 디바이스 short-form

실린더 / 클램프 / 로봇 — 한 마디로 표준 동작 한 쌍 + 인터페이스가 자동 생성. 그 외 디바이스는 타입과 동작 목록을 명시 (예: 푸셔 — 펀치 동작 하나).

④ 연결 종류 명시 강제

"A 끝나면 B 시작" (순차) / "A 시작하면 B 리셋" (배타) — 6 종 연결 타입 중 하나를 항상 명시. 의도가 모호하면 명시적 미정 상태로 표시 (자동 추측 금지).

⑤ 사양 외 정보는 추측 없이 비워두기

현재 단계의 도구 범위가 아닌 세부 (물리 주소, 타이밍 값, 외부 시스템 식별자 등) 는 추측으로 채우지 않습니다. "TODO" / "127.0.0.1" 같은 placeholder 를 조용히 끼워 넣지 않으며, 해당 항목은 후속 단계에서 별도로 보강합니다 — 사용자에게 굳이 묻지도 않습니다.

⑥ 질문은 꼭 필요할 때만

기본은 자동 진행 — 이름이나 흐름 구조는 사양 단서에서 자동으로 결정합니다. 질문을 던지는 경우는 두 가지뿐:

  • :plan 모드가 활성화된 경우 — 사용자가 사전 설계 단계를 명시한 상황
  • 모델을 만드는 데 필수적인 사양이 모호하거나 누락된 경우 (예: 한 부품을 처리하는 1회용인지, 부품이 계속 들어오는 라인인지)

질문할 때는 현장 어휘로 풀어서 — 모델링 용어를 노출하지 않습니다.

⑦ 결정성 / 결과 요약

같은 입력 → 같은 출력 정렬. 발행 결과는 한 줄 요약 (변경 항목 수)으로 사용자에게 보고.

6상태 공유 — 매 turn 자동 동기화

LLM 이 매번 현재 상태를 조회하지 않도록 — 시스템이 알아서 최신 상태를 LLM 에 전달합니다.

① 현재 모델 상태 자동 첨부

모델이 변경된 시점에만 현재 상태 요약이 LLM 에 자동 전달됩니다. 같은 상태가 유지되면 침묵 — 토큰 / 비용 절감.

현재 모델 (개정 42):
  Project: M1
  Systems:
    - 제어기 (능동)
        흐름 "실행":
          - 구역1 [실린더1.전진, 실린더2.전진, ...]
          - 구역2 ...
    - 실린더1 (수동, cylinder)
    - 실린더2 (수동, cylinder)
  연결:
    - 구역1 → 구역2 (순차)

이름 정렬로 같은 모델 → 같은 표기 — 결정성 보장.

② GUI 수동 편집 알림

이전 turn 이후 사용자가 GUI 에서 직접 수정한 내역이 다음 메시지 앞에 요약으로 첨부됩니다. LLM 은 이를 사실로 받아들일 뿐 명령으로 해석하지 않습니다.

GUI 변경 알림:
  시스템: +1 (Inspector1 추가됨)
  작업: +2, 이름 변경: 1
  연결: +3
  프로젝트: "M1" 로 전환됨

③ 사양 경계 표시

긴 사양을 붙여넣을 때 <사양> ... </사양> 식 구분자를 사용 — 안의 내용은 모델링 데이터이며 명령으로 해석되지 않습니다 (악의적 지시 차단).

④ 첫 진입 (Cold start)

아무 상태도 없는 첫 turn 에 한해 LLM 이 현재 상태를 한 번만 조회. 이후로는 항상 자동 첨부에 의존.

7선언적 모델 — YAML 한 페이지

LLM 이 발행하고 Promaker 가 적용하는 모델 표기 — 사람이 읽기 좋게 설계된 YAML 형태

project: <프로젝트명>

systems:
  - system: <이름>
    kind: active | passive       # 능동 / 수동 명시 (추론 없음)

    # 능동(active) — 제어 로직
    flow <흐름이름>:
      works:
        <작업이름>:
          calls:                 # 디바이스의 어떤 동작을 호출할지
            - <디바이스>.<동작>
            - <디바이스>.<동작>  # 같은 동작 N 회 등장 = 동시 의미
          arrows:                # 작업 내부 동작 사이 연결 (DAG)
            - <동작> -> <동작> : <연결타입>
      arrows:                    # 작업 사이 연결
        - <작업> -> <작업> : <연결타입>

    # 수동(passive) — 디바이스
    device: cylinder | clamp | robot | custom(<타입>)
    apis: [<동작1>, <동작2>, ...]   # 디바이스 default 재정의
    opposing: none | chain | all-pairs
    workDuration: 500ms

patch:                           # 기존 모델에 부분 변경
  add:        [ ... ]            # 시스템 추가
  arrows:
    add:      [ ... ]            # 연결 추가
  rename:     [ ... ]            # 이름 변경
  remove:     [ ... ]            # cascade 제거

값의미
Startsource 완료 → target 시작
Resetsource 시작 → target 리셋
StartReset완료 → 시작 + 시작 → 리셋

그 외 디바이스 (푸셔 / 컨베이어 / AGV / 그리퍼 등) 는 custom(<타입>) + apis: [...] 로 명시.

81 Turn 흐름 — 메시지 입력 ~ 반영

한 사용자 메시지가 거치는 단계 — 모든 변경은 하나의 되돌리기 단위로 묶입니다.

sequenceDiagram participant U as 사용자 participant Chat as 채팅 패널 participant LLM as LLM participant PMK as Promaker participant Store as 모델 저장소 U->>Chat: 텍스트 + 첨부 Chat->>Chat: 현재 모델 상태 자동 첨부
+ GUI 변경 알림 첨부 Chat->>LLM: 1 turn 요청 loop 도구 호출 반복 LLM->>PMK: 발행 요청 (선언적 모델) PMK->>PMK: 스키마 검증 + 자동 구성 PMK-->>LLM: 결과 요약 (변경 N건) end LLM-->>Chat: 최종 답변 + 발행 미리보기 Chat->>Store: 일괄 적용 (1 단계 되돌리기) Store-->>Chat: 다음 turn 에 새 상태 자동 첨부 Chat-->>U: 응답 + 변경 요약

핵심 정책

  • Turn 종료 시점에 일괄 commit — 같은 turn 안에서는 모델 변경이 아직 보이지 않음 (방금 발행한 항목을 같은 turn 에 재조회 금지)
  • 1 turn = 1 발행이 기본 — 별개 의도면 여러 번 가능
  • 발행 결과는 한 줄 요약 (변경 항목 수 / 영향 범위) 으로 인용

실패 / 재시도

  • 스키마 검증 실패 → 유사 후보 제안 → LLM 자가 정정 → 재발행
  • 적용 실패 → 모델 무변경 → 다음 turn 에 상태 재첨부
  • 취소 시 누적 변경 폐기 — 부분 적용 없음

9안전 · 신뢰 — 3 단계 동의 + 데이터 보호

외부 LLM 사용 시 발생하는 위험을 사용자가 인지·동의한 뒤에만 사용 가능

① 데이터 전송 동의

  • LLM Chat 첫 진입 시 1회 동의
  • 전송 데이터 명시: 사용자 메시지 + 모델 정보 + 첨부 파일
  • 거부 시 LLM Chat 차단

② API 비용 동의

  • 유료 API 첫 선택 시 별도 동의
  • 토큰 과금 안내 — 짧은 입력도 수만 token 이 송신될 수 있음
  • 거부 시 해당 provider 비활성화

③ 고권한 도구 동의

  • 파일 시스템 / 네트워크 자유 접근이 필요한 도구 사용 시 추가 동의
  • 완화 조치: 임시 격리 작업 공간 사용
  • 거부 시 해당 provider 비활성화

API 키 보호

  • API 키는 OS 보안 저장소로 즉시 암호화 저장
  • 다른 사용자 / 다른 머신에서 평문 read 불가
  • 모델명 / 로컬 endpoint 설정은 평문 (민감 정보 아님)

Prompt Injection 방어

  • 첨부 안에 "이전 지시 무시" 류 문장이 보여도 무시 (1줄 안내만)
  • 파일명에 path traversal / shell injection 문자열이 있어도 단순 라벨로만 처리
  • 현재 상태 / GUI 변경 / 사양 블럭은 데이터 — 명령이 아님
  • 비밀 파일 (.env 등) 은 첨부 자체 차단

M2매뉴얼 ② — 첫 모델링 (Greenfield)

빈 프로젝트에서 자연어 한 줄로 시작하는 예시

새 프로젝트 생성해서 두 개의 실린더가 순차로 전진하고, 다시 두 개의 실린더가 순차로 후진하는 시스템 모델링사용자
새 프로젝트 M1 을 만들고 실린더 2 개 (Cyl1, Cyl2) 순차 전진 → 순차 후진 모델을 발행합니다.assistant — 한 줄 요약

발행 결과 — 자동 구성

  • 프로젝트 M1
  • 능동 시스템 제어기 (흐름 실행 + 작업 × 4 + 연결 × 3)
  • 수동 시스템 Cyl1, Cyl2 — 각각 전진/후진 동작 + 인터페이스 + opposing 연결 이 자동 구성
  • 총 ~20 항목이 1 되돌리기 단위로 적용됨

후속 메시지 — 점진 확장

"Cyl3 도 추가해 줘. 1, 2 와 같이
 전진/후진 수행하게"

→ 기존 Cyl1, Cyl2 는 보존
→ Cyl3 만 부분 발행으로 추가
→ 관련 작업과 연결도 자동 보강

M3매뉴얼 ③ — 발행 결과 시각화 (YAML + Mermaid)

LLM 이 발행한 모델을 사용자가 한눈에 검토할 수 있도록 — 두 가지 표현이 채팅창에 함께 표시됩니다.

① YAML 표기 — 정확한 사양

project: M1
systems:
  - system: 제어기
    kind: active
    flow 실행:
      works:
        구역1:
          calls: [Cyl1.ADV, Cyl2.ADV, P1.PUNCH, Cyl1.RET, Cyl2.RET]
          arrows:
            - Cyl1.ADV -> P1.PUNCH : Start
            - Cyl2.ADV -> P1.PUNCH : Start
            - P1.PUNCH -> Cyl1.RET : Start
            - P1.PUNCH -> Cyl2.RET : Start
        구역2: ...
      arrows:
        - 구역1 -> 구역2 : Start
  - { system: Cyl1, kind: passive, device: cylinder }
  - { system: Cyl2, kind: passive, device: cylinder }
  - { system: P1, kind: passive,
      device: custom(Pusher), apis: [PUNCH] }

  • 그대로 복사해서 다른 곳에 붙여 넣어도 동일 모델 재현

활용 ① 적용 전 검토

발행 미리보기 단계에서 두 표현을 함께 확인 — 의도와 다르면 자연어로 수정 요청 후 재발행.

활용 ② 적용 후 보고

LLM 이 변경 요약과 함께 갱신된 다이어그램을 다시 표시 — 모델이 어떻게 자랐는지 즉시 확인.

활용 ③ 인쇄 / 공유

YAML 은 사양 문서로, Mermaid 는 발표/리뷰 자료로 그대로 활용 — 별도 도구 불필요.

M4매뉴얼 ④ — 점진 편집 (Patch)

전체 재작성 없이 부분 발행만으로 추가 / 변경 / 제거 — 1 turn = 1 되돌리기

Patch 시나리오 4 종

patch:
  add:                             # ① 시스템 추가
    - { system: 검사기1, kind: passive, device: custom(Sensor), apis: [TRIGGER] }
  arrows:
    add:                           # ② 연결 추가
      - in: 제어기.실행
        entries:
          - 구역3 -> 구역1 : Reset
  rename:                          # ③ 이름 변경
    - Cyl1: 좌측실린더1
  remove:                          # ④ cascade 제거 — 관련 호출/연결 자동 정리
    - Cyl4

지원 범위

  • 지원: 시스템 추가 / 작업-연결 추가 / 이름 변경 / cascade 제거
  • 현재 제한: 부분 발행으로 처리하기 어려운 케이스는 모델 전체를 재발행 — 사용자 입장에선 동일한 문장으로 처리되므로 차이를 인지할 필요 없음

한 patch 안 add + remove 자유 조합

기존 항목 제거 + 새 항목 추가를 같은 patch 에서 자유롭게 묶을 수 있습니다 (방금 추가한 항목을 곧바로 제거하는 자기 모순만 제외).

실수했을 때

Ctrl+Z 한 번 — 1 turn 의 모든 변경이 단일 되돌리기 단계. GUI 편집과 같은 되돌리기 스택을 공유합니다.

프로젝트 전환 보호

이미 다른 프로젝트가 열린 상태에서 새 프로젝트로 발행 시도 시 LLM 이 "파일 > 닫기" 를 안내. LLM 이 사용자 작업물을 자의로 닫지 않습니다.

M5매뉴얼 ⑤ — 첨부 · 모드 명령

텍스트 / 이미지 / PDF 첨부, 모드 명령, 사양 경계 표시

① 첨부 (drag & drop)

텍스트 / 코드

```yaml filename="layout.yaml"
zones: 3
cylinders_per_zone: [2, 3, 4]

```

fenced block 으로 사용자 메시지에 포함됩니다. 파일명은 라벨일 뿐 — 디스크 접근은 발생하지 않습니다.

이미지 / PDF

  • PNG / JPEG / GIF / WebP, PDF — 모델의 비전 기능으로 직접 해석
  • OCR 별도 추출 없이 도면 / 사양표 / 손그림 직접 인식

차단되는 첨부

비밀 정보 파일 (.env, credentials.json 등) 은 첨부 자체가 차단됩니다 — 사용자 의도와 무관하게 일관 적용.

- 로봇 Rb1: Home, Work1, ..., Work9

  • :reset / :redo 등 채팅 세션 제어 명령

④ 명확화 응답 패턴

모호한 사양에 대해 LLM 이 1회 질문 — 현장 어휘로 풀어서 묻습니다. 답변하면 자동으로 발행이 이어집니다.

M6매뉴얼 ⑥ — 활용 팁 · Best Practice

실제 사용을 거치며 축적된 패턴

① "한 station = 1 작업" 명심

  • "구역" / "공정" / "스테이션" = 부품이 머무는 한 station = 작업 1 개
  • 그 station 안의 전진 / 펀치 / 후진 = 같은 작업 안의 sub-action 들
  • 페이즈마다 작업 분리는 반례

② Plan mode 로 선지정

:plan
- 공정: 구역1, 구역2, 구역3
- 로봇 Rb1: Home, Work1..Work9
- 실린더: [Z{i}Cyl{j}]

큰 사양은 plan + 점진 발행으로 결정성과 안정성을 높이고, 이름 충돌 / 누락을 사전 방지할 수 있습니다.

③ 디바이스 단축 표기 적극 활용

  • 실린더 / 클램프 / 로봇은 한 마디로 표준 동작 한 쌍 자동 구성
  • 그 외 디바이스는 타입 + 동작 목록 명시

④ 내보내기로 왕복 검증

"현재 모델을 YAML 로 보여줘" — LLM 이 현재 상태를 YAML 로 정리해 보여줍니다. 발행 ↔ 내보내기가 동형이라 그대로 부분 발행 자료로 사용 가능.

⑤ GUI / Chat 자유 혼용

  • 이름 미세 수정 / 위치 조정은 GUI 가 빠름
  • 대량 추가 / 구조 변경은 Chat 이 빠름
  • GUI 변경 알림이 자동 동기화 — LLM 이 사용자 GUI 작업을 인지

⑥ 잘 안 될 때

  • 모호한 사양 → LLM 이 1회 질문 — 답변 후 자동 재발행
  • 검증 오류 → LLM 이 후보 제안을 받아 자가 정정 — 사용자는 보통 추가 작업 없음
  • 결과가 의도와 다르면 Ctrl+Z 후 다시 자연어로 수정 요청

⑦ Provider 비교 활용

같은 사양을 여러 provider 에 발행하여 결과를 비교할 수 있습니다 — 모두 동일한 선언적 모델 표기를 만들어내므로 그대로 직접 비교 가능.
