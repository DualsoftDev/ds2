# 산업 현장을 모델로 표현하는 일의 가치와 LLM 결합의 역할
## — DS 모델링 언어를 매개로 한 예측·관찰·직접 실행·표준 배포의 네 축

¹anonymous@dualsoft.com

## 초록 (Abstract)

산업 현장은 그 자체로는 실행될 수도, 관찰될 수도, 예측될 수도 없다. 현장이 정형화된 *모델*로 표현되어야 비로소 동일 사양 위에서 **예측(Simulation)**, **관찰(Monitoring)**, **직접 실행(Control)**, **표준 배포(Code-generation)** 라는 네 가지 행위가 일관되게 가능해진다. 본 논문은 이 네 활용을 가능하게 하는 모델 표현의 구체적 형식으로 고수준 모델링 언어인 **DS(Dualsoft) 언어** 를 소개하고, 그 위에 LLM(Large Language Model)을 결합한 의의를 정리한다. 핵심 논지는 두 가지로 압축된다. 첫째, 본 연구가 제공하는 일차적 가치는 단일 진실 원천(SSOT)으로서의 모델이며, 위 네 가지 활용은 모두 그 모델에서 분기되어 나간다. 특히 직접 실행과 표준 배포는 *동일 모델에서 분기되는 두 실행 매체* 이다. 둘째, LLM 의 기여는 모델의 가치를 새로 만드는 것이 아니라 그 가치에 도달하기 위해 사용자가 지불해야 하는 *진입 비용을 낮추는 것* 이다. 현장 어휘로 말하면 LLM 이 그것을 DS 언어의 모델 어휘로 정규화하므로, 모델링 도구의 학습 곡선이 크게 낮아진다. 본 논문은 이 두 명제를 모델 중심의 위계 위에 배치하여 결합 설계의 일반화 원칙을 도출한다.

**키워드**: 산업 자동화, 모델 기반 엔지니어링, DS 모델링 언어, 시뮬레이션, 모니터링, PC-based control, PLC 코드 생성, LLM, 진입 장벽

## 1. 서론

### 1.1 산업 현장과 모델의 관계

스마트 팩토리·Industry 4.0 흐름 속에서 공정과 설비를 디지털 자산으로 표현하려는 노력은 표준화와 도구화의 두 축으로 진행되어 왔다. 그러나 그 모든 노력의 출발점은 단 하나로 모인다 — *현장을 모델로 표현하는 일* 이다. 모델이 손에 들어오기 전까지, 산업 현장은 도면·표·사양서·구두 합의 같은 비정형 형태로만 존재한다. 비정형 상태의 현장은 검증하기 어렵고, 시뮬레이션하기 어렵고, 코드로 옮기기 어려우며, 운영 단계에서 의미 있는 형태로 모니터링되기도 어렵다.

반대로 일단 현장이 잘 정의된 모델로 표현되면 사정이 달라진다. 같은 모델 위에서 사용자는 다음 네 가지 행위를 동일한 사양으로 일관되게 수행할 수 있다.

- **Simulation** — 현장이 만들어지기 전에 동작을 *예측* 한다.
- **Monitoring** — 현장이 가동되는 동안 모델 위에서 실제 신호를 *관찰* 한다.
- **Control** — 모델을 PC 프로그램에 직접 적재하여 *그대로 실행* 한다.
- **Code-generation** — 모델로부터 표준 산업용 제어 코드를 생성하여 PLC 가 *표준 환경에서 실행* 하도록 *배포* 한다.

본 논문은 이 네 활용을 가능하게 하는 모델 표현 형식으로 DS 언어를 제안하고(§3), 그 언어를 다루는 도구로서 Promaker 를 소개하며(§4), 거기에 LLM 을 결합했을 때 무엇이 더 가능해지는지(§5)를 정리한다.

### 1.2 문제 정의

모델 표현의 가치는 이미 정해져 있다 (§1.1). 문제는 그 가치에 도달하기까지의 *진입 비용* 이다. 산업 현장의 엔지니어가 익숙한 어휘는 "구역", "실린더", "전진/후진", "공정", "스테이션" 같은 *현장 어휘* 인 반면, 모델링 언어가 요구하는 어휘는 Flow, Work, Call, Arrow 같은 정형화된 *모델 어휘* 이다. 사용자는 모델을 만들기 전에 모델링 언어의 어휘 체계를 먼저 익혀야 하며, 이 학습 곡선이 본질적 가치(§1.1 네 활용)로의 접근을 가로막는 가장 큰 마찰이다.

본 논문은 이 진입 비용 문제를 LLM 으로 완화하는 사례를 보고한다. 다만 그 완화가 **모델의 본질적 가치를 훼손하지 않는 형태** 로 이루어져야 한다는 추가 제약이 핵심 설계 문제로 등장한다. 즉 LLM 에게 코드를 직접 쓰게 하거나 모델의 무결성을 LLM 의 추론에 위임하면 §1.1 네 활용 모두의 결정성·재현성·안전성이 함께 약해진다.

### 1.3 기여

본 논문의 기여는 다음과 같다.

- 흐름 의도 표현 중심의 고수준 모델링 언어 **DS 언어** 를 정리하고, 그 1급 엔티티·Arrow 의미론·직렬화 형식을 소개한다.
- 산업 모델 표현 도구의 본질적 가치를 **예측·관찰·직접 실행·표준 배포의 네 축** 으로 정리하고, 그중 직접 실행과 표준 배포가 *동일 모델에서 분기되는 두 실행 매체* 임을 보인다.
- LLM 결합의 가치를 "모델의 가치를 새로 만드는 것" 이 아니라 "모델의 가치에 도달하기 위한 *진입 비용을 낮추는 것*" 으로 위치시키고, 이 위계가 흐려질 때 무엇이 약해지는지를 분석한다.
- 위 세 요소를 결합한 설계 원리를 사례를 통해 보이고, 그 결과를 "모델이 본질, LLM 은 채널" 이라는 한 줄 위계 위에서 정리한다.

## 2. 배경

### 2.1 모델 표현 도구로서의 Promaker

Promaker 는 데스크톱 환경에서 동작하는 모델 표현·편집 도구이다. 그 중심에는 §3 에서 소개할 DS 그래프 모델이라는 단일 진실 원천이 있고, 그래프 주변으로 시각 편집기·3D 뷰·시뮬레이터·IO 바인딩·표준 산출 변환기가 둘러서 있다. 사용자가 모델을 어떤 채널로 만들든 — 시각 편집, 텍스트 직접 편집, 외부 도구 가져오기, 그리고 §5 에서 다룰 LLM 채팅 — 결국 그래프는 동일하며, 모든 활용은 이 동일 그래프 위에서 펼쳐진다.

### 2.2 대화형 LLM 의 적성

최근의 대화형 LLM 은 비정형 자연어의 의도를 구조화된 형식으로 변환하는 데에 강한 적성을 보인다. 도메인 어휘를 모델 어휘로 옮기고, 누락된 정보를 사양 단서에서 추론하고, 모호한 부분을 한 번의 질문으로 명확화하는 작업은 LLM 이 잘 수행하는 영역이다. 반면 식별자 무결성, 트랜잭션 일관성, 표준 코드 생성처럼 *결정성과 재현성이 요구되는 영역* 은 LLM 의 강점이 아니다.

### 2.3 본 논문의 시야 — 모델은 본질, LLM 은 채널

§2.1 과 §2.2 사이의 관계는 본 논문 전체의 위계를 결정한다. **모델은 본질이고 LLM 은 채널이다.** 본질에 도달하는 채널을 한 가지 더 마련하는 것이 LLM 결합의 의의이며, LLM 이 본질을 대체하거나 본질의 일부를 침범하기 시작하면 본 논문이 다루는 네 활용 전체가 약해진다.

## 3. DS 언어

### 3.1 위치 — 산업 표준이 아니라 자사의 모델링 언어

본 논문이 다루는 모델 표현의 구체적 형식은 *DS(Dualsoft) 언어* 라고 부르는 고수준 모델링 언어이다. DS 언어는 산업 표준 단체가 정한 규범이 아니라, (주)듀얼소프트가 정의하여 Promaker 에서 사용하는 자사의 모델링 언어이다. 이하 본 논문에서는 단순히 "DS 언어" 로 부른다. 본 절은 그 언어의 설계 의도, 1급 엔티티, Arrow 의 의미론, 직렬화 형식, 그리고 기존 산업 표준과의 자리 관계를 차례로 다룬다.

### 3.2 설계 의도

기존의 산업 표준은 두 가지 층에서 모델 표현을 다룬다. 한쪽은 PLC 측의 제어 코드 규범(예: 사다리, 구조화 텍스트, SFC 등) 이고, 다른 한쪽은 자산 표현 측의 디지털 자산 규범(예: AAS) 이다. 두 층은 각자의 목적이 분명하다. 그러나 *현장 엔지니어가 공정 흐름을 가장 자연스럽게 옮길 수 있는 단위* 라는 측면에서는 두 표준 모두 한걸음 떨어져 있다고 본다. PLC 코드 규범은 *실행 매체에 가까운* 표현이라 흐름의 의도가 매체별 문법 속에 묻히기 쉽고, 자산 규범은 *데이터 모델에 가까운* 표현이라 시간적 흐름이 1급 개념으로 드러나지 않는다.

DS 언어는 이 사이 자리에 놓이는 *흐름 표현 중심* 의 고수준 언어이다. 사용자가 "구역 1 의 작업이 끝나면 구역 2 가 시작한다", "이 실린더의 전진과 후진은 동시에 일어나서는 안 된다" 같은 흐름 의도를 *1급 어휘* 로 직접 적을 수 있도록 의도되어 있다. 이 의도가 §4 의 네 활용으로 분기될 때 사용자가 *같은 어휘* 를 계속 본다는 점이 본 언어의 핵심 가치이다.

### 3.3 1급 엔티티

DS 언어의 1급 엔티티는 다음과 같이 정리된다.

| 엔티티 | 의미 |
|---|---|
| Project | 프로젝트 루트. 다수의 능동·수동 System 을 보유 |
| System (Active) | 제어 로직을 가진 시스템 |
| System (Passive) | 제어를 받는 물리 디바이스 |
| Flow | 독립적으로 트리거되는 흐름 단위 |
| Work | Flow 내 한 작업 단계 (station). Ready→Going→Finish→Homing 상태머신을 가짐 |
| Call | 디바이스의 한 행위 호출 |
| ApiDef | 수동 시스템이 제공하는 행위 정의 |
| Arrow | 요소 간 흐름 제어 (시간 특성을 가진 1급 개념) |

이 집합은 "한 station 에서 무엇이 일어나는가" 를 1급으로 표현할 수 있도록 설계되었다. 사용자는 station(Work) 안에 디바이스 행위(Call) 들을 묶고, station 사이에 Arrow 로 흐름 순서·인터로크를 표현한다. 사용자 입장에서 보이는 어휘가 통상의 현장 어휘와 가깝게 — "구역(=Work)에서 실린더의 전진(=Call) 이 끝나면 다음 구역으로(=Arrow) 진행한다" — 매핑되도록 의도된 것이 본 엔티티 구성의 의도이다.

### 3.4 Arrow 의 의미론 — 시간 특성을 가진 1급 개념

DS 언어에서 Arrow 는 단순한 선이 아니라 *신호의 시간 특성* 을 표현하는 1급 개념이다. 본 언어는 여섯 가지 Arrow 종류를 제공한다.

| 종류 | 신호 특성 | 의미 |
|---|---|---|
| Unspecified | — | 명시적 미정 (의도 표시) |
| Start | rising edge (순간) | 소스가 끝나는 순간 타깃 시작 |
| Reset | level (지속) | 소스가 진행 중인 동안 타깃을 리셋 상태로 유지 |
| StartReset | Start + Reset 결합 | 완료 시 시작 + 진행 중 리셋 유지 (인터로크) |
| ResetReset | 상호 reset (양방향) | 동일 디바이스의 상반 행위 쌍 — 상호 배타 |
| Group | (실행 의미 없음) | 시각 그룹 hint |

이 의미론을 1급으로 둔 이유는, §4 의 네 활용(예측·관찰·직접 실행·표준 배포) 모두가 *같은 Arrow 의미* 를 그대로 해석해야 하기 때문이다. 시뮬레이터에서의 Start 와 PC 가 직접 실행할 때의 Start, 그리고 PLC 코드로 변환된 후의 Start 가 모두 동일한 시간 특성을 가져야 §4.5 의 "한 모델, 두 실행 매체" 분기 신뢰가 성립한다. Arrow 가 단순한 그래프 선이 아니라 *시간 특성을 가진 1급 개념* 이어야 하는 이유는 이 일치 요건에서 나온다.

또한 ResetReset 은 동일 디바이스의 상반 행위 쌍에 대한 *상호 배타* 규약으로, 사용자가 자연어 시점에 흔히 빠뜨리는 안전 제약을 언어 자체가 1급으로 가지도록 의도되었다.

### 3.5 두 가지 직렬화 — 내부와 사람-친화

DS 언어는 두 가지 직렬화 형식을 가진다. 하나는 시스템 내부에서 그래프를 영속화하기 위한 *내부 직렬화* 이고, 다른 하나는 사람이 읽고 편집·diff·revert 할 수 있는 *사람-친화 텍스트 표기* 이다. 후자는 YAML 표기를 사용한다. 두 형식은 *round-trip 동형* 으로 유지되며, 한쪽에서 다른 쪽으로 다녀와도 의미가 보존된다. 이 동형성이 §6 의 다채널 협업(GUI / 텍스트 편집 / Chat) 을 받쳐주는 형식적 토대이다.

사람-친화 표기에서 모든 참조는 *사람이 읽는 점-경로* (예: `Cyl1.ADV`) 로 표현되며, 내부 식별자(GUID 등)는 텍스트 표면에 노출되지 않는다. 이 비노출은 두 가지를 동시에 만족시킨다. 사용자가 텍스트를 직접 읽고 편집하기 좋은 가독성, 그리고 §6 의 LLM 채널이 식별자 무결성을 침범하지 않도록 막아주는 책임 경계 보호이다.

### 3.6 본 언어가 어디에 자리잡는가

DS 언어는 산업 표준을 대체하려는 것이 아니다. 표준 PLC 코드 규범과 자산 규범은 산업 인프라의 호환성 측면에서 그 자체로 가치를 가지며, DS 언어는 그 표준들에 *흘려보내질 모델 표현의 출처* 로 자리잡는다. 즉 사용자는 DS 언어로 흐름 의도를 적고, 그 단일 출처에서 PLC 코드와 AAS 자산이 결정적으로 산출된다. *DS 언어는 사용자 측의 표현, 표준은 외부 호환의 출력* 이라는 분업이다. 이 분업이 깨지지 않는 한, DS 언어가 산업 표준 단체의 규범이 아니라는 사실은 표준 호환성에 대한 약점이 되지 않는다.

## 4. Promaker 자체의 장점 — DS 언어를 네 활용으로 분기시키기 (★ 본 논문의 중심)

### 4.0 전제 — 모델이 있으면 무엇이 가능해지는가

§3 에서 DS 언어를 통해 현장이 모델로 표현된 상태를 마련했다. 본 절은 그 모델이 손에 있을 때 *동일 사양 위에서 무엇이 가능해지는가* 를 정리한다. 핵심은 네 활용이 모두 *같은 그래프에서 유래한다* 는 점이다. 사용자가 시뮬레이터에서 본 동작과, 현장 모니터링 화면이 보여주는 동작과, PC 가 직접 실행하는 동작과, PLC 에 배포되어 실행되는 동작이 모두 같은 그래프에서 흘러나와야 한다. 그래야 사양 변경 한 번이 네 활용 전부에 그대로 반영되고, 디버깅이 한 모델 위에서 끝나며, 사용자가 *동일한 것을 본다* 는 감각이 유지된다.

본 절은 그 네 활용을 차례로 다룬다. 그 후 §4.5 에서 직접 실행(§4.3) 과 표준 배포(§4.4) 가 어떻게 동일 모델에서 분기되는 두 실행 매체인지를 비교하고, §4.6 에서 네 활용 모두를 받쳐주는 공통 기반을 정리한다.

### 4.1 Simulation — 모델로부터의 예측

시뮬레이션은 모델이 손에 들어왔을 때 가장 먼저 가능해지는 행위이다. 사용자는 실 설비 없이도 그래프 위에서 흐름의 동작을 단계별로 진행시켜 볼 수 있다. 시뮬레이션의 의미론은 §3 에서 정의한 DS 언어의 의미론과 동일한 어휘 위에서 정의된다 — Work 의 상태머신, Arrow 의 시간 특성, Passive 디바이스 내부의 상호 배타 규칙이 그대로 시뮬레이션의 동작 규칙이 된다. 즉 사용자가 모델에서 그린 것과 시뮬레이터에서 본 것 사이에 *의미의 단절이 없다*.

이 단절 없음이 만들어내는 가치는 두 가지다. 첫째, 설비 발주·시운전 이전에 흐름의 오류나 인터로크 누락을 발견할 수 있다. 사양상으로는 그럴듯해 보였던 흐름이 시뮬레이션 위에서 데드락에 빠지거나 동시 동작이 충돌하는 모습을 사용자가 직접 본다. 둘째, 현장에서 발견된 동작 이상을 시뮬레이터로 재현할 수 있다. 모델이 동일하므로 재현이 가능하고, 재현이 가능하면 디버깅이 가능하다.

시뮬레이션은 또한 사용자 교육과 의사 결정 보조라는 부수적 가치도 가진다. 신규 엔지니어는 시뮬레이션을 통해 시스템의 동작 원리를 익히고, 현장 의사결정자는 사양 변경의 영향을 실제 설비를 건드리기 전에 확인한다.

### 4.2 Monitoring — 모델 위에 실 신호 투영

시뮬레이션이 모델을 *예측에 쓰는 것* 이라면, 모니터링은 모델을 *관찰의 격자로 쓰는 것* 이다. 운영 단계에 들어선 설비는 매 순간 수많은 신호를 발생시키지만, 그 신호들이 의미를 가지려면 *해석의 틀* 이 필요하다. 모델은 바로 그 틀의 역할을 한다.

같은 그래프 위에 실 PLC 의 신호를 IO 바인딩으로 매핑하면, 디바이스 별 비트 신호가 비로소 "Cyl1.ADV 가 Going 상태" 처럼 *DS 언어의 어휘로 해석된 사실* 이 된다. Work 의 상태머신이 현장 동작의 진단 격자가 되고, Arrow 가 흐름의 차단·전이를 설명하는 단위가 된다. 알람·로그·OEE(Overall Equipment Effectiveness) 같은 운영 지표가 *이름 있는 모델 요소* 위에서 해석되므로, 이상 발생 시점에 사용자가 보는 화면이 "5번 비트가 1로 떴음" 이 아니라 "구역 2 의 실린더 후진이 Homing 단계에서 멈춤" 으로 표현된다.

이 해석의 격자는 자연어 시점부터 현장 태그명까지의 *명명 일관성* 위에서 성립한다. 사용자가 입력에서 사용한 이름이 모델 요소의 이름이 되고, 그 이름이 매크로 치환을 통해 현장 IO 태그명이 된다. 모니터링 화면이 갑자기 새로운 어휘를 들고 나타나는 일이 없으며, 사용자는 같은 어휘로 사양을 쓰고, 같은 어휘로 시뮬레이션을 보고, 같은 어휘로 현장을 관찰한다.

### 4.3 Control — 모델로부터의 직접 실행 (PC-based)

세 번째 활용은 모델을 PC 프로그램이 *직접* 적재하여 in-process 엔진으로 실행하는 것이다. 별도의 코드 생성·다운로드 단계가 없다. 모델 자체가 실행 단위이며, PC 프로세스가 모델의 의미론을 그대로 인터프리팅하여 현장 IO 와 통신한다. 시뮬레이터가 가상의 IO 와 대화한다면, 이 PC-based control 모드는 *같은 인터프리터가 실제 IO 와* 대화한다고 볼 수 있다.

이 모드가 적합한 영역은 분명하다. 소규모 셀, 시작품 단계 설비, 연구·교육용 장비, edge controller, soft control 환경처럼 산업용 PLC 인프라를 별도로 갖추지 않은 상황이다. 산업 PLC 가 제공하는 등급의 안전성·실시간성을 요구하지 않는 대신, *모델 변경 → 즉시 실 동작* 의 짧은 사이클을 얻는다. 모델을 한 줄 고치고 재로드만 하면, 시뮬레이션과 동일한 의미론으로 PC 가 실제 IO 를 흔든다.

이 활용의 가치는 시뮬레이션과 실 동작 사이의 단절이 좁아진다는 점에 있다. 통상의 워크플로에서는 시뮬레이션 통과 → 코드 생성 → PLC 다운로드 → 시운전이라는 긴 사슬을 거쳐야 비로소 "모델대로" 동작하는 설비를 본다. PC-based control 은 그 사슬을 압축하여, 모델을 만든 책상 위에서 그대로 *재컴파일 없는 실 동작* 을 가능하게 한다. 같은 모델이 책상의 시뮬레이션과 현장 PC 의 실제어를 동일 의미로 수행한다.

### 4.4 Code-generation → PLC 제어 — 표준 산업 배포

네 번째 활용은 모델로부터 PLC 가 실행할 수 있는 표준 코드를 생성하여, 그 코드를 산업용 PLC 에 다운로드해 실행하는 것이다. 산출물은 사다리 논리, 함수 블록 인스턴스, IO 매핑, 진단 메시지가 담긴 벤더 별 프로젝트 파일이며, 이것이 산업 PLC 가 이해하는 형식이다. 실행 주체는 PC 가 아니라 PLC 이며, PC 는 모델링과 배포 단계에서만 관여하고 운영 단계에서는 빠진다.

이 모드는 *양산 라인, 인증을 요구하는 환경, 다중 IO 와 고신뢰가 요구되는 설비* 에 적합하다. 산업 PLC 가 제공하는 등급의 안전성·실시간성·내환경성이 그대로 활용되며, 기존 현장의 엔지니어링 도구(벤더의 PLC IDE) 와 운영 도구(HMI, SCADA) 가 그대로 호환된다. 이 호환성은 DS 언어로 표현한 새로운 흐름을 *기존 산업 인프라 위에 안착시키는* 의의를 가진다.

코드 생성에서 가장 중요한 설계 결정은 *LLM 에게 코드 생성권을 주지 않는 것* 이다. 모델 → 코드 변환은 결정적(deterministic) 변환기가 수행한다. 즉 동일한 모델은 항상 동일한 코드를 만들고, 검증된 변환 규칙 위에서만 변환이 일어난다. 이 결정성이 약해지면 안전성(잘못된 코드가 실 설비에 흘러갈 위험), 표준 준수(벤더 코드 규약 위반), 재현성(같은 모델이 매번 다른 코드를 만드는 혼란) 셋이 함께 영향을 받는다.

또한 이 모드는 AAS(Asset Administration Shell) 같은 산업 디지털 자산 표준과 결합되기 좋다. 같은 모델로부터 PLC 코드뿐 아니라 Nameplate, TechnicalData, HandoverDocumentation 같은 표준 Submodel 을 동시에 산출하면, 외부 시스템과의 디지털 자산 교환이 모델 기반으로 통일된다. DS 언어가 사용자 측 표현이고 산업 표준이 외부 호환 출력이라는 §3.6 의 분업이 여기서 실제로 동작한다.

### 4.5 한 모델, 두 실행 매체 — §4.3 vs §4.4

§4.3 의 Control 과 §4.4 의 Code-gen → PLC 는 *같은 모델에서 분기되는 두 실행 매체* 이다. 사용자는 동일 사양으로 두 매체를 자유 선택·전환할 수 있다. 두 매체의 성격은 다음과 같이 정리된다.

| 축 | Control (PC 직접 실행) | Code-gen → PLC |
|---|---|---|
| 실행 주체 | PC 프로세스 (in-process 엔진) | 산업용 PLC |
| 산출물 | 없음 — 모델 자체가 실행 단위 | 벤더 PLC 프로젝트 파일 |
| 모델 변경 반영 | 즉시 (재로드) | 재생성 → 다운로드 → 재시작 |
| 적합 영역 | 소규모 셀, 시작품, 연구·교육, edge / soft control | 양산 설비, 인증·표준 환경, 다중 IO |
| 안전 / 실시간 등급 | PC OS 의존 | 산업 PLC 등급 |
| 결정성 보장 위치 | 모델 인터프리터 | 결정적 변환기 + PLC 실행 |
| 사이클 길이 | 짧음 (편집 → 재로드) | 김 (변환 → 다운로드 → 시운전) |
| 인프라 의존성 | PC + IO 인터페이스 | 산업 PLC + 엔지니어링 도구 |

핵심은 두 경로가 **동일 모델에서 분기** 한다는 것이다. 사용자는 시작품 단계에서 PC-based control 로 빠르게 동작을 확인한 뒤, 양산 단계에서 동일 모델을 그대로 PLC 코드로 변환·배포할 수 있다. 두 매체 사이에 *모델을 다시 만들 비용* 이 들지 않는다. 또한 운영 중에 발견된 사양 보강도 한 모델에서 수정한 뒤 두 매체로 다시 흘려보내면 되므로, 매체 별로 따로 유지보수할 필요가 줄어든다.

이 분기 구조는 시뮬레이션·모니터링과 결합되면 더욱 자연스럽다. 시작품을 PC 가 직접 제어하면서 동시에 같은 모델로 시뮬레이션을 돌려 예상 동작과 비교하거나, 양산 PLC 가 돌고 있는 현장의 신호를 같은 모델 위에 매핑하여 모니터링하는 흐름이 같은 어휘 위에서 이어진다. **하나의 모델이 네 가지 활용의 교집합** 이 되는 것이다.

### 4.6 네 활용의 공통 기반

§4.1~§4.4 네 활용은 표면적으로는 서로 다른 행위처럼 보이지만, 모두 다음 공통 기반 위에서 성립한다.

- **단일 진실 원천(SSOT)** — DS 그래프 하나가 네 활용 모두의 출처이다. 그래프의 텍스트 직렬화(YAML)도 함께 제공되어 사람이 읽고 편집하고 diff·revert 할 수 있는 형식으로도 보존된다. 모델은 디스크 위의 데이터로 영속화되고, 채널이 무엇이든 결국 같은 그래프를 갱신한다.

- **Cascade 와 트랜잭션** — 사용자가 "실린더 하나를 추가" 한다는 의도를 표현하면, 그래프 측에서는 디바이스 정의, 흐름 안의 호출, 인터페이스 정의, 연결선, Passive 내부 상호 배타 규칙 같은 다수의 요소가 함께 만들어진다. 이 다단 변경은 단일 트랜잭션 경계 안에서 일어나며, 검증에 실패하면 일관되게 원위치로 돌아간다. 부분 적용으로 인한 그래프 손상이 발생하지 않는다.

- **1 변경 = 1 undo** — 사용자 관점의 변경 단위와 시스템 관점의 변경 단위가 일치한다. 시뮬레이션 단계에서 한 변경을 시도해 보고, 결과가 마음에 들지 않으면 한 번의 되돌리기로 직전 상태로 돌아간다. 이 일치는 모니터링·Control·Code-gen 어느 단계에서도 동일하게 유지된다.

- **다채널 협업** — 시각 편집, 텍스트(YAML) 편집, 외부 도구 가져오기, 그리고 §5 의 LLM 채팅이 모두 같은 SSOT 위에서 동작한다. 한 채널의 변경은 다른 채널에 자동으로 반영되며, 사용자는 가장 빠른 채널을 그때그때 선택해 쓴다.

이 공통 기반이 있기 때문에 §4.5 의 분기 구조가 의미를 가진다. 같은 모델 위에서 분기한다는 말은, 그 모델이 분기 전후로 *불변* 임이 보장될 때만 진실이다. SSOT·트랜잭션·undo·다채널 협업이라는 공통 기반이 그 불변을 지탱한다.

## 5. LLM 활용의 장점 — 진입 장벽 낮춤

### 5.0 한 줄 명제

§3·§4 에서 DS 언어로 표현된 모델의 가치는 이미 정해져 있다. LLM 의 기여는 그 가치를 새로 만드는 것이 아니라, 가치에 도달하기 위해 사용자가 지불해야 하는 *진입 비용을 낮추는 것* 이다. 본 절은 이 한 줄 명제를 구체적인 진입 마찰 해소 사례 네 가지로 풀어낸 뒤, §5.5 에서 그 효과가 §4 의 네 활용 각각을 어떻게 *증폭* 하는지를 정리한다.

### 5.1 모델 어휘를 외울 필요 없음

사용자가 익숙한 어휘는 "구역", "실린더", "전진/후진", "공정 순서" 같은 *현장 어휘* 이다. 그러나 DS 언어가 1급으로 다루는 어휘는 Flow, Work, Call, Arrow, ApiDef 같은 *모델 어휘* 이다. 이 어휘 전환 부담이 모델 표현 도구의 가장 큰 진입 마찰이었다.

LLM 결합 후에는 그 부담이 LLM 쪽으로 옮겨간다. 사용자는 "두 실린더가 순차로 전진한 뒤 다시 순차로 후진" 같은 현장 어휘 한 줄을 입력하고, LLM 이 이를 DS 언어의 모델 어휘로 정규화한다. 사용자는 모델 어휘를 *몰라도* 모델을 만들 수 있다. 모델링 언어의 학습 곡선이 도구 사용 측면에서는 크게 낮아진다. 다만 사용자가 결과 모델을 *읽고 검토하는* 단계에서는 DS 언어의 어휘를 어느 정도는 인지하는 편이 좋다 — 텍스트 표기가 사람-친화적이기 때문에 검토 부담은 입력 부담에 비해 훨씬 작다(§3.5).

### 5.2 Greenfield 진입의 마찰 제거

백지에서 첫 모델을 만드는 일은 도구 학습 외에도 *시작 자체의 마찰* 을 동반한다. 어떤 메뉴를 먼저 누를지, 어디서부터 그릴지, 어떤 단축키를 외워야 빠른지 같은 운영적 결정들이 백지의 초입을 막아선다.

LLM 채팅 진입점은 이 마찰을 크게 줄인다. 사용자는 채팅창을 열고 사양 한 문장을 입력하면, 그 한 문장으로 모델의 골격이 만들어진다. 시뮬레이션·Control·Code-gen 중 어느 활용으로 진입하더라도, 그 활용이 의지하는 모델이 한 문장으로 손에 들어온다는 점이 중요하다.

### 5.3 점진 편집 — Brownfield 에서도 유효

LLM 의 진입 비용 절감 효과는 백지 상태에만 한정되지 않는다. 이미 존재하는 모델에 대해서도 "3구역 다음에 4구역 추가, 거기에 실린더 두 개 순차 전진" 같은 의도 표현으로 기존 모델을 보존하면서 점진적으로 변경할 수 있다. 이름 변경, 삭제, 연결 추가 같은 흔한 운영 변경도 모두 같은 진입점으로 처리된다.

이때 1 발화 = 1 변경 = 1 undo 라는 직관적 변경 단위가 유지되므로, 사용자는 점진 편집을 *실험적으로* 시도할 수 있다. 결과가 의도와 다르면 한 번의 되돌리기로 원위치한다. 점진 편집의 안전 그물은 §4.6 의 트랜잭션·undo 공통 기반이 그대로 받쳐준다.

### 5.4 GUI / Chat 자유 혼용

LLM 이 들어왔다고 해서 기존 시각 편집(GUI)이 대체되는 것은 아니다. 두 채널은 서로의 강점이 다르다. 미세 위치 조정, 단일 속성 수정 같은 작업은 GUI 가 빠르고, 한 번에 다수 요소를 만들거나 구조를 크게 바꾸는 작업은 Chat 이 빠르다. 사용자는 두 채널을 자유롭게 교대로 쓰며, 어느 채널을 쓰든 결과는 같은 SSOT 에 반영된다.

이 자유 혼용을 가능케 하는 것은 §4.6 의 *다채널 협업* 기반이다. GUI 에서 사용자가 직접 수정한 내역은 다음 채팅 턴에 LLM 에게 자동 통지되므로, LLM 은 매번 현재 모델 상태를 다시 묻지 않고도 사용자의 GUI 작업을 인지한 채 다음 편집을 이어간다. 두 채널 사이의 *상태 동기화 비용* 이 사용자 입장에서 보이지 않는다.

### 5.5 진입 장벽 낮춤이 §4 의 네 활용을 어떻게 증폭하는가

LLM 의 가치는 §4 의 네 활용 각각에서 다음과 같이 증폭된다.

- **Simulation 증폭** — 시뮬레이션을 *돌릴 수 있는 사람* 의 수가 늘어난다. 모델 어휘 학습이 필요 없으니, 시뮬레이션을 통해 흐름 오류를 잡아내고 사양을 점검하는 일이 더 많은 엔지니어에게 가능해진다.
- **Monitoring 증폭** — 모니터링용 모델을 *만들 수 있는 사람* 의 수가 늘어난다. 현장 신호의 해석 격자를 한 사람이 모델 어휘로 일일이 만들지 않아도, 현장 어휘 입력만으로 격자가 만들어진다.
- **Control 증폭** — 시작품·소규모 셀의 PC-based control 사이클이 짧아진다. "사양 변경 → 모델 수정 → 즉시 실행" 흐름의 첫 단계인 모델 수정이 한 발화로 줄어들면, 짧은 사이클의 가치가 본격적으로 살아난다.
- **Code-gen 증폭** — 양산 단계의 사양 변경이 표준 산업 인프라까지 흘러가는 데 드는 *재모델링 비용* 이 줄어든다. 변경 의도를 한 발화로 표현하면 모델이 갱신되고, 결정적 변환기가 그것을 PLC 코드로 옮긴다.

이 증폭 효과의 공통 원천은 단 하나다 — 모델을 만드는 비용이 낮아지면 *모델 위에 서 있는 모든 활용의 빈도가 높아진다*. §4 의 네 활용은 모델이 있어야 가능했지만, 모델을 만드는 일이 비싸면 활용도 드물게 쓰인다. LLM 은 활용 자체가 아니라 *활용의 빈도와 도달 범위* 를 키운다.

## 6. 결합 설계 — 책임 경계

### 6.1 한 줄 원칙

LLM 과 Promaker 의 책임 경계는 다음 한 줄로 정리된다.

> **LLM 책임 = 자연어 → DS 언어로의 정규화** (이름·구조·연결 종류 결정).
> **Promaker 책임 = 모델 구성·일관성·트랜잭션·표준 산출** — LLM 이 직접 만져서는 안 되는 영역.

이 경계는 §4 의 본질(모델) 과 §5 의 채널(LLM) 의 위계를 그대로 반영한다. LLM 은 DS 언어로 표현된 모델 문서를 *만들 책임* 을 지며, Promaker 는 그 문서를 그래프로 *집행할 책임* 을 진다. LLM 이 집행 영역(코드 생성, 식별자 관리, 트랜잭션)에 침범하기 시작하면 §4.4 의 결정성·표준 준수·재현성, §4.5 의 분기 신뢰성, §4.6 의 공통 기반이 함께 약해진다.

### 6.2 협업 계약으로서의 선언적 모델 문서

두 책임 사이를 잇는 인터페이스는 §3.5 의 *사람-친화 직렬화*, 즉 YAML 표기로 작성된 *선언적 모델 문서* 이다. LLM 은 자연어 입력을 받아 이 문서를 한 차례 발행하고, Promaker 는 그 문서를 검증한 뒤 그래프로 반영한다. 이 문서가 "협업 계약" 의 역할을 한다.

선언적 모델 문서가 협업 계약으로 적합한 이유는 네 가지다. 첫째, *LLM 친화성* — 들여쓰기와 의미 구조가 명확해 LLM 의 출력 신뢰도가 높다. 둘째, *round-trip 동형성* — 같은 그래프를 발행 → 다시 읽기 했을 때 텍스트가 동일하므로(§3.5), 다음 턴에 LLM 이 일관된 출발점에서 작업을 이어간다. 셋째, *내부 식별자 비노출* — 모든 참조는 사람이 읽는 점-경로로 표현되며, GUID 같은 내부 식별자는 LLM 에게 노출되지 않는다. 넷째, *가독성과 결정성의 분리* — 사용자에게 보이는 표기는 가독성 위주이지만, 시스템 내부의 적용은 결정적이다.

### 6.3 LLM 에게 코드 생성권을 주지 않는 세 이유

본 설계의 가장 명시적인 책임 경계는 *LLM 에게 PLC 코드 생성권을 주지 않는다* 는 결정이다. LLM 은 DS 언어로 표현된 모델 문서까지만 만들고, 그 이후의 코드 생성은 결정적 변환기가 담당한다. 그 이유는 세 가지다.

- **안전성** — 잘못된 PLC 코드가 그대로 설비에 흘러가면 물리적 위험을 야기할 수 있다. LLM 의 확률적 출력은 안전 기준의 *상한* 을 보장하기 어렵다.
- **표준 준수** — 벤더 별 PLC XML 사양은 매우 좁고 깊은 규범이며, LLM 이 학습한 일반 코드 분포와 멀리 떨어져 있다. 모든 디테일을 매번 만족시키기 어렵다.
- **재현성** — 동일 모델이 항상 동일 코드를 만든다는 보장이 있어야, 시뮬레이션·Control·Code-gen 사이의 분기 신뢰가 성립한다(§4.5). LLM 출력의 비결정성은 이 신뢰를 약화시킨다.

이 세 이유는 §4.5 가 가능하려면 §6.3 이 필요함을 보여준다. 동일 모델에서 두 실행 매체로 분기한다는 주장은 두 매체 사이의 결정성 보장 위에서만 성립한다. LLM 이 코드를 쓰는 순간 그 결정성이 약해지고, 분기의 신뢰가 함께 흔들린다.

## 7. 사용 시나리오 — §4 의 네 활용 × §5 의 진입 채널

본 절은 §4 의 네 활용이 §5 의 LLM 진입 채널과 결합되어 나타나는 전형 시나리오 네 가지를 정리한다.

### 7.1 Greenfield + Simulation — 자연어 한 줄에서 시작하는 예측

빈 프로젝트에서 사용자가 "두 실린더가 순차 전진 후 순차 후진" 한 줄을 입력하면, LLM 은 DS 언어의 선언적 모델 문서를 발행하고 Promaker 는 이를 트랜잭션으로 그래프에 반영한다. 사용자는 이어서 시뮬레이터를 열어 한 단계씩 진행시켜 본다. 모델 어휘를 직접 다룰 줄 모르는 사용자도 *예측 가능한 흐름* 을 짧은 시간 안에 손에 쥘 수 있게 된다.

### 7.2 모델 → PC 제어 (Control) — 시작품 단계의 짧은 사이클

소규모 셀이나 시작품 단계에서는 PLC 인프라를 갖추지 않은 채로 빠르게 동작을 확인하고 싶다. 사용자는 위 시나리오의 모델을 그대로 PC 가 적재해 실행한다. 시뮬레이션과 같은 의미론으로 *실제 IO* 가 움직인다. 사양이 바뀌면 한 발화로 모델을 고치고 재로드만 하면 다음 사이클이 시작된다. *재컴파일 없는 실 동작* 의 사이클이 LLM 진입 채널과 결합되어 한층 더 짧아진다.

### 7.3 모델 → PLC 배포 (Code-gen) — 양산 단계의 표준 안착

양산 라인에 들어가는 단계에서는 같은 모델을 결정적 변환기에 통과시켜 산업 PLC 가 이해할 표준 코드로 옮긴다. 사용자는 모델을 다시 만들지 않는다. 시작품 단계에서 검증된 그 모델이 그대로 양산 코드의 출처가 된다. 동시에 표준 디지털 자산(AAS Submodel) 도 같이 산출되어, 외부 시스템과의 자산 교환 흐름까지 포함된다.

### 7.4 운영 단계 — Monitoring + Patch

현장이 가동되기 시작한 뒤에는 모니터링 화면이 DS 언어의 어휘로 신호를 해석한다. 운영 중에 새 사양이 들어오면, 사용자는 같은 채팅 채널로 점진 편집을 가하고 모델을 갱신한다. 갱신된 모델은 다시 시뮬레이션·Control·Code-gen 의 어느 경로로든 흘러갈 수 있다. *운영 → 변경 → 재배포* 의 큰 순환이 같은 모델 위에서 닫힌다.

## 8. 안전·신뢰

LLM 결합은 외부 시스템(클라우드 LLM provider, 로컬 모델 endpoint 등)과의 상호 작용을 동반하므로, 모델의 본질적 가치를 지키기 위한 안전·신뢰 장치가 함께 설계된다.

### 8.1 단계별 동의

LLM 채팅 첫 진입 시 데이터 전송 동의를 받고, 유료 API 첫 사용 시 비용 동의를 별도로 받으며, 고권한 도구가 결합된 provider 의 경우 추가 동의를 한 번 더 받는다. 거부 시 해당 경로는 비활성화된다. 사용자는 자신의 데이터·비용·권한이 어디까지 노출되는지를 명시적으로 인지한 상태에서 결합을 사용한다.

### 8.2 API 키 보호

provider API 키는 운영체제 보안 저장소에 즉시 암호화 저장된다. 다른 사용자·다른 머신에서 평문으로 읽어내기 어렵다. 모델명·로컬 endpoint 주소 같이 민감하지 않은 항목만 평문으로 보존된다.

### 8.3 Prompt Injection 방어

첨부 파일이나 외부 사양 안에 "이전 지시를 무시하라" 류의 명령형 문장이 포함되어 있어도 명령으로 해석되지 않도록 한다. 사양 블록은 명시적 경계 표시로 *데이터* 임을 표시하며, 파일명·경로 안의 의심스러운 문자열은 라벨로만 처리된다. 비밀 정보가 들어 있을 가능성이 큰 파일(.env 등)은 첨부 자체가 차단된다.

### 8.4 그래프 무결성 보호

LLM 의 발행이 그래프를 직접 갱신하지 않는다는 점이 가장 강한 안전 장치이다. 발행은 트랜잭션 buffer 에 누적되며, 적용 직전의 검증을 통과해야 그래프에 반영된다. 검증 실패는 일관 rollback 으로 처리된다. 사용자는 *부분 적용으로 인한 모델 손상* 을 경험하지 않는다.

## 9. 논의

### 9.1 모델이 본질, LLM 은 채널 — 위계가 흐려지면 무엇이 약해지는가

본 논문의 가장 중심 주장은 §1 에서 미리 던졌고 §4, §6 에서 두 차례 확인되었다. 모델이 본질이고 LLM 은 채널이며, 이 위계가 흐려지면 §4 의 네 활용 전체가 함께 영향을 받는다. 구체적으로는 다음과 같다.

- LLM 이 *식별자 관리* 에 침범하면 round-trip 동형성과 다채널 협업이 약해진다.
- LLM 이 *트랜잭션* 을 직접 다루면 부분 적용으로 인한 그래프 손상 가능성이 생긴다.
- LLM 이 *코드 생성* 을 직접 수행하면 §4.5 의 두 실행 매체 분기 신뢰가 약해진다.
- LLM 이 *모델의 진실 원천* 을 차지하면 GUI·텍스트 편집·외부 도구와의 협업이 좁아진다.

이 네 약화는 모두 같은 뿌리를 가진다 — 본질 자리에 채널이 들어선 결과이다. 책임 경계는 정책 문제가 아니라 시스템의 정합성 문제이다.

### 9.2 단발 발행으로의 진화

LLM 결합 초기에는 LLM 에게 다수의 단일 연산 도구(요소 단위 add/edit/remove)를 노출하는 방식이 자연스러워 보였다. 그러나 한 발화가 수십 회의 도구 호출로 분해되면서, 토큰 비용과 재시도 빈도가 늘고, *부분 적용으로 인한 그래프 손상* 가능성도 커졌다. 현재 설계는 LLM 이 한 번의 DS 언어 모델 문서를 발행하는 *doc-level 단발 발행* 을 주력 진입점으로 두고, 단일 연산 도구는 escape hatch 로만 남긴다. 이 진화는 §6.2 협업 계약과 §4.6 트랜잭션 공통 기반의 자연스러운 귀결이다.

### 9.3 한계 및 향후 과제

- **입력 채널의 확장** — 현재 LLM 입력은 자연어 텍스트가 중심이다. 도면·표·손그림 같은 이미지 입력의 본격 해석은 별도 단계로 다루어지며, 사양서 PDF 파싱은 첨부 수준에 머문다.
- **런타임 측정값 매핑** — 모니터링이 신호의 *해석 격자* 를 제공하지만, 측정값을 모델 어휘로 자동 라벨링하는 깊은 매핑은 본 논문 범위 밖이다.
- **벤더 확장 범위** — Code-gen 의 1차 대상 벤더가 가장 성숙해 있으며, 그 외 벤더 지원은 단계적 확장 영역이다.
- **PC-based control 의 인증** — §4.3 의 Control 매체는 PC OS 등급의 안전성에 의존하므로, 산업 안전 인증이 요구되는 환경에서는 사용 범위를 한정해야 한다.
- **DS 언어의 외부 채택 여부** — DS 언어는 자사의 모델링 언어이다(§3.1). 향후 다른 모델링 도구·시뮬레이터·런타임이 같은 어휘를 채택할지 여부는 본 연구 범위 밖의 생태계 문제이며, 현 단계에서는 표준 호환의 출력(PLC 코드, AAS 자산) 을 통해 외부 인프라와 연결되는 방향을 우선한다.

### 9.4 일반화 가능성

본 사례는 산업 자동화 도메인을 다루지만, 본 논문이 도출한 위계(§6.1) 와 협업 계약(§6.2) 의 원리는 다른 모델 표현 도메인에도 적용될 수 있을 것으로 보인다. 모델이 본질이고 LLM 이 채널인 곳, 그리고 모델로부터 다수의 실행 매체가 분기되는 곳이라면 본 논문의 분석이 그대로 작동한다. 다만 도메인 특수성(안전 등급, 표준 호환, 결정성 요건)에 따라 책임 경계의 *위치* 가 조금씩 달라질 수 있다.

## 10. 결론

본 논문은 산업 현장을 모델로 표현하는 일의 가치를 예측·관찰·직접 실행·표준 배포라는 네 활용으로 정리하였다. 네 활용은 모두 같은 모델에서 분기하며, 그중 직접 실행과 표준 배포는 동일 모델에서 갈라져 나가는 두 실행 매체로서 사용자가 시작품 단계의 짧은 사이클과 양산 단계의 표준 안착을 같은 사양으로 자유 선택할 수 있게 한다. Promaker 가 제공하는 일차적 가치는 이 모델 표현 자체이며, DS 언어는 그 표현이 네 활용 모두에서 같은 어휘로 해석되도록 흐름 의도를 1급으로 다루기 위한 도구이다.

이 토대 위에서 LLM 결합의 기여는 모델의 가치를 새로 만드는 것이 아니라 그 가치에 도달하기 위해 사용자가 지불해야 하는 진입 비용을 낮추는 것으로 정리된다. 모델 어휘 학습의 부담이 사용자의 책임에서 LLM 의 책임으로 옮겨가면서, 시뮬레이션을 돌릴 수 있는 사람, 모니터링용 모델을 만들 수 있는 사람, 시작품을 PC 가 직접 제어할 수 있게 만드는 사람, 양산 사양 변경을 따라잡을 수 있는 사람의 수와 속도가 늘어난다. LLM 은 활용 자체가 아니라 활용의 빈도와 도달 범위를 키운다.

이 두 명제가 함께 성립하려면 모델이 본질이고 LLM 은 채널이라는 위계가 유지되어야 한다는 점은 §6 과 §9 에서 반복적으로 확인되었다. 결국 본 사례가 남기는 작은 명제는 다음 한 줄로 모아진다 — 모델 표현 도구에 LLM 을 결합할 때의 설계 결정은 정책의 문제가 아니라 시스템의 정합성을 어디에 두는가의 문제이며, 그 정합성을 단일 진실 원천(SSOT)·트랜잭션 일관성·결정적 변환의 세 기둥 위에 놓을 때 비로소 진입 장벽을 낮추는 일과 본질을 지키는 일이 서로 충돌하지 않고 함께 작동한다.
