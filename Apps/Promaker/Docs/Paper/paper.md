## 초록

산업 현장은 그 자체로는 실행될 수도, 관찰될 수도, 예측될 수도 없다. 현장이 정형화된 *모델*로 표현되어야 비로소 동일 사양 위에서 **예측(Simulation)**, **관찰(Monitoring)**, **직접 실행(Control)**, **표준 배포(Code-generation)** 라는 네 가지 행위가 일관되게 가능해진다. 본 논문은 이 네 활용을 가능하게 하는 모델 표현의 구체적 형식으로 고수준 모델링 언어인 **DS(Dualsoft) 언어** 를 소개하고, 그 위에 대화형 LLM(Large Language Model)을 결합한 의의를 정리한다. 핵심 논지는 두 가지다. 첫째, 본 사례가 제공하는 일차적 가치는 단일 진실 원천(SSOT)으로서의 모델이며, 위 네 가지 활용은 모두 그 모델에서 분기되어 나간다. 특히 직접 실행과 표준 배포는 *동일 모델에서 분기되는 두 실행 매체* 이다. 둘째, LLM 의 기여는 모델의 가치를 새로 만드는 것이 아니라 그 가치에 도달하기 위해 사용자가 지불해야 하는 *진입 비용을 낮추는 것* 이다. 사용자가 현장 어휘로 말하면 LLM 이 그것을 DS 언어의 모델 어휘로 정규화하므로, 모델링 도구의 학습 곡선이 크게 낮아진다. 본 논문은 이 두 명제를 모델 중심의 위계 위에 배치하여 결합 설계의 일반화 원칙을 도출하고, 자연어 입력으로부터 사람이 읽을 수 있는 YAML 모델 문서, AAS 3.1 자산, 산업용 PLC 프로젝트가 동일 모델에서 일관 산출되는 종단(end-to-end) 동작 사례로 그 원칙을 뒷받침한다.

**키워드**: 산업 자동화, 모델 기반 엔지니어링, DS 모델링 언어, 시뮬레이션, 모니터링, PC-based control, PLC 코드 생성, AAS, LLM, MCP, 진입 장벽

## 1. 서론

### 1.1 산업 현장과 모델의 관계

스마트 팩토리·Industry 4.0 흐름 속에서 공정과 설비를 디지털 자산으로 표현하려는 노력은 표준화와 도구화의 두 축으로 진행되어 왔다. 그러나 그 모든 노력의 출발점은 단 하나로 모인다 — *현장을 모델로 표현하는 일* 이다. 모델이 손에 들어오기 전까지, 산업 현장은 도면·표·사양서·구두 합의 같은 비정형 형태로만 존재한다. 비정형 상태의 현장은 검증하기 어렵고, 시뮬레이션하기 어렵고, 코드로 옮기기 어려우며, 운영 단계에서 의미 있는 형태로 모니터링되기도 어렵다.

반대로 일단 현장이 잘 정의된 모델로 표현되면 사정이 달라진다. 같은 모델 위에서 사용자는 다음 네 가지 행위를 동일한 사양으로 일관되게 수행할 수 있다.

- **Simulation** — 현장이 만들어지기 전에 동작을 *예측* 한다.
- **Monitoring** — 현장이 가동되는 동안 모델 위에서 실제 신호를 *관찰* 한다.
- **Control** — 모델을 PC 프로그램에 직접 적재하여 *그대로 실행* 한다.
- **Code-generation** — 모델로부터 표준 산업용 제어 코드를 생성하여 PLC 가 *표준 환경에서 실행* 하도록 *배포* 한다.

본 논문은 이 네 활용을 가능하게 하는 모델 표현 형식으로 DS 언어를 소개하고, 그 언어가 펼치는 네 활용을 본 논문의 무게중심으로 다룬다. 그 위에 LLM 을 결합했을 때 무엇이 더 가능해지는지, 그리고 결합 시 책임 경계가 어떻게 그어져야 하는지를 차례로 정리한다.

### 1.2 문제 정의

모델 표현의 가치는 앞 절에서 정리한 대로 이미 정해져 있다. 문제는 그 가치에 도달하기까지의 *진입 비용* 이다. 산업 현장의 엔지니어가 익숙한 어휘는 "구역", "실린더", "전진/후진", "공정", "스테이션" 같은 *현장 어휘* 인 반면, 모델링 언어가 요구하는 어휘는 Flow, Work, Call, Arrow 같은 정형화된 *모델 어휘* 이다. 사용자는 모델을 만들기 전에 모델링 언어의 어휘 체계를 먼저 익혀야 하며, 이 학습 곡선이 본질적 가치(앞서 정리한 네 활용)로의 접근을 가로막는 가장 큰 마찰이다.

본 논문은 이 진입 비용 문제를 LLM 으로 완화하는 사례를 보고한다. 다만 그 완화가 **모델의 본질적 가치를 훼손하지 않는 형태** 로 이루어져야 한다는 추가 제약이 핵심 설계 문제로 등장한다. 즉 LLM 에게 코드를 직접 쓰게 하거나 모델의 무결성을 LLM 의 추론에 위임하면 네 활용 모두의 결정성·재현성·안전성이 함께 약해진다. 본 사례는 다음과 같은 세 가지 실무 제약을 동시에 만족시킬 것을 요구한다.

1. **의미 정확성** — LLM 이 생성한 모델이 도메인 의미론(예: 동일 디바이스의 상반된 액션 간 상호 배타성)을 위반하면 안 된다.
2. **트랜잭션 일관성** — 한 번의 사용자 발화가 다수의 그래프 편집 연산으로 분해될 때, 부분 실패가 영구 손상을 남기면 안 된다.
3. **표준 호환성과 가독성** — 산출물은 AAS 환경 및 상용 PLC 엔지니어링 도구에서 그대로 열려야 하고, 동시에 사람이 검토·diff·revert 할 수 있는 텍스트 형태로도 보존되어야 한다.

### 1.3 기여

본 논문의 기여는 다음과 같다.

- 흐름 의도 표현 중심의 고수준 모델링 언어 **DS 언어** 를 정리하고, 그 1급 엔티티·Arrow 의미론·직렬화 형식을 소개한다.
- 산업 모델 표현 도구의 본질적 가치를 **예측·관찰·직접 실행·표준 배포의 네 축** 으로 정리하고, 그중 직접 실행과 표준 배포가 *동일 모델에서 분기되는 두 실행 매체* 임을 보인다.
- LLM 결합의 가치를 "모델의 가치를 새로 만드는 것" 이 아니라 "모델의 가치에 도달하기 위한 *진입 비용을 낮추는 것*" 으로 위치시키고, 이 위계가 흐려질 때 무엇이 약해지는지를 분석한다.
- 자연어 → DS 그래프 → YAML / AAS / PLC 종단 파이프라인을 단일 데스크톱 애플리케이션 안에 통합한 사례를 보고하고, LLM 이 자유 형식 텍스트로 그래프를 직접 출력하지 않고 *선언적 YAML 모델 문서를 doc-level 도구로 단발 발행* 하는 trust boundary 설계를 제시한다.
- 위 요소를 결합한 설계 원리를 사례를 통해 보이고, 그 결과를 "모델이 본질, LLM 은 채널" 이라는 한 줄 위계 위에서 정리한다.

## 2. 배경

### 2.1 모델 표현 도구로서의 Promaker

Promaker 는 데스크톱 환경에서 동작하는 모델 표현·편집 도구이다. 그 중심에는 다음 장에서 소개할 DS 그래프 모델이라는 단일 진실 원천이 있고, 그래프 주변으로 시각 편집기·3D 뷰·시뮬레이터·IO 바인딩·표준 산출 변환기·LLM 채팅 인터페이스가 둘러서 있다. 사용자가 모델을 어떤 채널로 만들든 — 시각 편집, 텍스트 직접 편집, 외부 도구 가져오기, 또는 뒤에서 다룰 LLM 채팅 — 결국 그래프는 동일하며, 모든 활용은 이 동일 그래프 위에서 펼쳐진다.

### 2.2 Promaker 시스템 구성

Promaker 는 다음 네 개의 핵심 구성 요소로 이루어진다.

| 구성 요소 | 역할 |
|---|---|
| LLM Chat View | 사용자 입력·응답 UI, 채팅 턴 관리, 발행 결과 미리보기 |
| MCP In-process Server | LLM 에 도구 노출, nonce 인증, 로컬 루프백 바인딩 |
| DS Store / Model Protocol | DS 그래프 단일 진실 원천 + YAML 직렬화·역직렬화 |
| Exporter (AAS / PLC) | DS → 표준 산출물 변환 (결정적 변환기) |

전체 흐름은 다음과 같다. 사용자가 채팅창에 자연어로 공정을 기술하면, system prompt 에 묶인 모델링 규칙과 함께 LLM 에 전달되고, LLM 은 선언적 YAML 모델 문서 한 편을 발행하는 doc-level 도구를 호출한다. 백엔드는 이름 기반 점-경로와 forward reference 를 두 단계로 해소하여 DS 그래프를 일괄 갱신하고, 검증 실패 시에는 적용 전 상태로 자동 롤백한다. 이후 사용자가 저장을 누르면 동일한 그래프로부터 YAML, AAS 자산, PLC 프로젝트가 생성된다. 같은 모델은 네 활용 중 어느 경로로든 흘러갈 수 있다.

### 2.3 대화형 LLM 의 적성

최근의 대화형 LLM 은 비정형 자연어의 의도를 구조화된 형식으로 변환하는 데에 강한 적성을 보인다. 도메인 어휘를 모델 어휘로 옮기고, 누락된 정보를 사양 단서에서 추론하고, 모호한 부분을 한 번의 질문으로 명확화하는 작업은 LLM 이 잘 수행하는 영역이다. 반면 식별자 무결성, 트랜잭션 일관성, 표준 코드 생성처럼 *결정성과 재현성이 요구되는 영역* 은 LLM 의 강점이 아니다.

### 2.4 모델은 본질, LLM 은 채널

앞 세 절 사이의 관계는 본 논문 전체의 위계를 결정한다. **모델은 본질이고 LLM 은 채널이다.** 본질에 도달하는 채널을 한 가지 더 마련하는 것이 LLM 결합의 의의이며, LLM 이 본질을 대체하거나 본질의 일부를 침범하기 시작하면 본 논문이 다루는 네 활용 전체가 약해진다.

### 2.5 관련 연구

산업 도메인에 LLM 을 적용한 사전 사례는 (i) 태그 명명 규칙으로부터 설비 모델을 추정하는 reverse-engineering 접근, (ii) 자연어 → 사다리 논리(Ladder Logic) 직접 생성, (iii) AAS Submodel 자동 채움 등이 있다. 본 연구는 이들과 달리 **자연어가 우선 고수준 그래프 DSL(DS 언어) 로 변환된 뒤** 네 종류의 활용으로 동시에 투영된다는 점에서 차별된다. 즉 LLM 이 직접 PLC 코드를 쓰지 않고, 검증 가능한 중간 표현(YAML 모델 문서)을 거친 후 결정적 변환기가 코드를 생성한다.

## 3. DS 언어

### 3.1 산업 표준이 아니라 자사의 모델링 언어

본 논문이 다루는 모델 표현의 구체적 형식은 *DS(Dualsoft) 언어* 라고 부르는 고수준 모델링 언어이다. DS 언어는 산업 표준 단체가 정한 규범이 아니라, (주)듀얼소프트가 정의하여 Promaker 에서 사용하는 자사의 모델링 언어이다. 이하 본 논문에서는 단순히 "DS 언어" 로 부른다. 본 절은 그 언어의 설계 의도, 1급 엔티티, Arrow 의 의미론, 직렬화 형식, 그리고 기존 산업 표준과의 자리 관계를 차례로 다룬다.

### 3.2 설계 의도

기존의 산업 표준은 두 가지 층에서 모델 표현을 다룬다. 한쪽은 PLC 측의 제어 코드 규범(예: 사다리, 구조화 텍스트, SFC 등) 이고, 다른 한쪽은 자산 표현 측의 디지털 자산 규범(예: AAS) 이다. 두 층은 각자의 목적이 분명하다. 그러나 *현장 엔지니어가 공정 흐름을 가장 자연스럽게 옮길 수 있는 단위* 라는 측면에서는 두 표준 모두 한걸음 떨어져 있다고 본다. PLC 코드 규범은 *실행 매체에 가까운* 표현이라 흐름의 의도가 매체별 문법 속에 묻히기 쉽고, 자산 규범은 *데이터 모델에 가까운* 표현이라 시간적 흐름이 1급 개념으로 드러나지 않는다.

DS 언어는 이 사이 자리에 놓이는 *흐름 표현 중심* 의 고수준 언어이다. 사용자가 "구역 1 의 작업이 끝나면 구역 2 가 시작한다", "이 실린더의 전진과 후진은 동시에 일어나서는 안 된다" 같은 흐름 의도를 *1급 어휘* 로 직접 적을 수 있도록 의도되어 있다. 이 의도가 다음 장의 네 활용으로 분기될 때 사용자가 *같은 어휘* 를 계속 본다는 점이 본 언어의 핵심 가치이다.

### 3.3 1급 엔티티

DS 언어의 1급 엔티티는 다음과 같이 정리된다.

| 엔티티 | 의미 |
|---|---|
| Project | 프로젝트 루트. 다수의 능동·수동 System 을 보유 |
| System (Active) | 제어 로직을 가진 시스템 |
| System (Passive) | 제어를 받는 물리 디바이스 |
| Flow | 독립적으로 트리거되는 흐름 단위 |
| Work | Flow 내 한 작업 단계 (station). Ready→Going→Finish→Homing 상태머신을 가짐 |
| Call | 디바이스의 한 행위 호출 (`디바이스.행위` 형식) |
| ApiDef | 수동 시스템이 제공하는 행위 정의 |
| ArrowBetweenWorks | Work 간 흐름 제어 |
| ArrowBetweenCalls | Work 내부 Call 간 제어 |

이 집합은 "한 station 에서 무엇이 일어나는가" 를 1급으로 표현할 수 있도록 설계되었다. 사용자는 station(Work) 안에 디바이스 행위(Call) 들을 묶고, station 사이에 Arrow 로 흐름 순서·인터로크를 표현한다. 사용자 입장에서 보이는 어휘가 통상의 현장 어휘와 가깝게 — "구역(=Work)에서 실린더의 전진(=Call) 이 끝나면 다음 구역으로(=Arrow) 진행한다" — 매핑되도록 의도된 것이 본 엔티티 구성의 의도이다.

### 3.4 Arrow 의 의미론

DS 언어에서 Arrow 는 단순한 선이 아니라 *신호의 시간 특성* 을 표현하는 1급 개념이다. 본 언어는 여섯 가지 Arrow 종류를 두 개의 layer 위에 정의한다 — **Work-arrow layer** (같은 능동 System 안의 Work 사이 또는 Work 내부의 Call 사이) 와 **Passive 내부 opposing layer** (같은 수동 디바이스의 상반 행위 쌍 사이). 두 layer 는 같은 종류 값을 공유하지만 의미 차원이 다르다.

| 종류 | layer | 신호 특성 | 의미 |
|---|---|---|---|
| Unspecified | — | — | 연결 없음 / 명시적 미정 |
| Start | Work / Call | rising edge (순간) | 소스 Finish 순간에 타깃이 Ready 라면 Going 으로 전이 |
| Reset | Work-arrow | Going high level (지속) | 소스가 Going 인 동안 타깃이 Finish 라면 Homing 으로 전이 |
| StartReset | Work-arrow | Start + Reset 결합 | 완료 시 시작 + 진행 중 reset 유지 (인터로크) |
| ResetReset | Passive 내부 | 양방향 상호 reset | 동일 디바이스의 상반 행위 쌍 — 상호 배타 |
| Group | UI | 실행 의미 없음 | 캔버스 클러스터링 hint |

Start 신호의 edge-triggered 성질(소스가 Finish 에 머물러 있어도 신호는 1 회만)과 Reset 신호의 level 성질의 비대칭은 capacity > 1 cycle 의 핵심 메커니즘이다. ResetReset 은 위 Work-arrow 의미와는 다른 layer 로, 자연어 입력에서 흔히 빠지므로 모델링 규칙에 "동일 수동 디바이스의 상반된 두 행위는 반드시 ResetReset Arrow 로 연결" 규약을 명시한다. YAML 발행 시 수동 내부의 ADV↔RET 같은 상반 쌍에 대해서는 백엔드가 자동으로 ResetReset 을 채워주므로 LLM 이 이를 별도로 기술할 필요는 없다.

Arrow 의 의미론을 1급으로 두는 이유는, 다음 장의 네 활용(예측·관찰·직접 실행·표준 배포) 모두가 *같은 Arrow 의미* 를 그대로 해석해야 하기 때문이다. 시뮬레이터에서의 Start 와 PC 가 직접 실행할 때의 Start, 그리고 PLC 코드로 변환된 후의 Start 가 모두 동일한 시간 특성을 가져야 "한 모델, 두 실행 매체" 분기 신뢰가 성립한다.

### 3.5 사람이 다루는 표현과 내부 직렬화

DS 언어로 표현된 모델은 사람이 다루기 좋은 두 가지 표현을 함께 가진다. 한눈에 구조를 파악하기 좋은 **Mermaid 다이어그램** 과 정밀한 편집·diff·revert 에 적합한 **YAML 텍스트 표기** 이다. 두 표현은 모두 사람-친화 형식이며, *시각적 한눈 파악은 Mermaid 가, 행 단위의 정밀 편집과 버전 관리는 YAML 이* 담당하도록 역할이 나뉜다. 이하 본 논문에서는 이 두 형식을 별도 수식어 없이 그냥 "Mermaid" 와 "YAML" 로 부른다.

이와 별개로 시스템 내부에서 그래프를 영속화하기 위한 *내부 직렬화* 가 있다 (typed AST 의 JSON 표현). 내부 직렬화와 YAML 표기는 *round-trip 동형* 으로 유지되며, 같은 그래프를 발행 → 다시 읽기 했을 때 텍스트가 동일하다. 이 동형성은 단위 테스트로 강제된다 (`apply(export(M)) ≡ M`). Mermaid 는 YAML / 내부 그래프로부터 *결정적으로 파생되는 시각화 출력* 이며 입력 채널로는 쓰이지 않는다 — 모델 변경의 출처는 항상 그래프 자체 또는 그것의 YAML 표기이다. 이 역할 분담이 다채널 협업(GUI / 텍스트 편집 / Chat) 을 받쳐주는 형식적 토대이다.

YAML 표기에서 모든 참조는 *사람이 읽는 점-경로* (예: `Cyl1.ADV`) 로 표현되며, 내부 식별자(GUID 등)는 텍스트 표면에 노출되지 않는다. 이 비노출은 두 가지를 동시에 만족시킨다. 사용자가 텍스트를 직접 읽고 편집하기 좋은 가독성, 그리고 LLM 채널이 식별자 무결성을 침범하지 않도록 막아주는 책임 경계 보호이다.

YAML 표기의 핵심 스키마는 다음과 같다. 최상위 키는 `protocol` (필수), `project` (선택), `systems` (선택), `patch` (선택) 이다. 능동 시스템은 `kind: active` 와 `flow <Name>:` 블록 안에 `works` (Work 이름 → `calls`) + `arrows` (Work 간 화살표) 를 선언한다. 수동 시스템은 `kind: passive` 와 `device:` (알려진 sugar) 또는 `custom(<이름>)` + `apis:` 목록을 선언한다. 경로 구분자는 `.` 또는 `/`, 엔티티 이름에는 `.` 금지. Arrow 표기는 `A -> B : <Type>` 형식으로 6 종 타입 중 하나를 명시한다. `workDuration`, `opposing` 같은 override 는 기본값과 다를 때만 emit 되어 round-trip 동등성이 유지된다.

### 3.6 본 언어가 어디에 자리잡는가

DS 언어는 산업 표준을 대체하려는 것이 아니다. 표준 PLC 코드 규범과 자산 규범은 산업 인프라의 호환성 측면에서 그 자체로 가치를 가지며, DS 언어는 그 표준들에 *흘려보내질 모델 표현의 출처* 로 자리잡는다. 즉 사용자는 DS 언어로 흐름 의도를 적고, 그 단일 출처에서 PLC 코드와 AAS 자산이 결정적으로 산출된다. *DS 언어는 사용자 측의 표현, 표준은 외부 호환의 출력* 이라는 분업이다. 이 분업이 깨지지 않는 한, DS 언어가 산업 표준 단체의 규범이 아니라는 사실은 표준 호환성에 대한 약점이 되지 않는다.

## 4. Promaker 자체의 장점

### 4.0 전제

본 장은 본 논문의 무게중심이다. 앞 장에서 DS 언어를 통해 현장이 모델로 표현된 상태를 마련했고, 본 장은 그 모델이 손에 있을 때 *동일 사양 위에서 무엇이 가능해지는가* 를 정리한다. 핵심은 네 활용이 모두 *같은 그래프에서 유래한다* 는 점이다. 사용자가 시뮬레이터에서 본 동작과, 현장 모니터링 화면이 보여주는 동작과, PC 가 직접 실행하는 동작과, PLC 에 배포되어 실행되는 동작이 모두 같은 그래프에서 흘러나와야 한다. 그래야 사양 변경 한 번이 네 활용 전부에 그대로 반영되고, 디버깅이 한 모델 위에서 끝나며, 사용자가 *동일한 것을 본다* 는 감각이 유지된다.

본 장은 그 네 활용을 차례로 다룬 뒤, 직접 실행과 표준 배포가 어떻게 동일 모델에서 분기되는 두 실행 매체인지를 비교하고, 마지막으로 네 활용 모두를 받쳐주는 공통 기반을 정리한다.

### 4.1 Simulation

시뮬레이션은 모델이 손에 들어왔을 때 가장 먼저 가능해지는 행위이다. 사용자는 실 설비 없이도 그래프 위에서 흐름의 동작을 단계별로 진행시켜 볼 수 있다. 시뮬레이션의 의미론은 DS 언어의 의미론과 동일한 어휘 위에서 정의된다 — Work 의 상태머신, Arrow 의 시간 특성, 수동 디바이스 내부의 상호 배타 규칙이 그대로 시뮬레이션의 동작 규칙이 된다. 즉 사용자가 모델에서 그린 것과 시뮬레이터에서 본 것 사이에 *의미의 단절이 없다*.

이 단절 없음이 만들어내는 가치는 두 가지다. 첫째, 설비 발주·시운전 이전에 흐름의 오류나 인터로크 누락을 발견할 수 있다. 사양상으로는 그럴듯해 보였던 흐름이 시뮬레이션 위에서 데드락에 빠지거나 동시 동작이 충돌하는 모습을 사용자가 직접 본다. 둘째, 현장에서 발견된 동작 이상을 시뮬레이터로 재현할 수 있다. 모델이 동일하므로 재현이 가능하고, 재현이 가능하면 디버깅이 가능하다.

시뮬레이션은 또한 사용자 교육과 의사 결정 보조라는 부수적 가치도 가진다. 신규 엔지니어는 시뮬레이션을 통해 시스템의 동작 원리를 익히고, 현장 의사결정자는 사양 변경의 영향을 실제 설비를 건드리기 전에 확인한다.

### 4.2 Monitoring

시뮬레이션이 모델을 *예측에 쓰는 것* 이라면, 모니터링은 모델을 *관찰의 격자로 쓰는 것* 이다. 운영 단계에 들어선 설비는 매 순간 수많은 신호를 발생시키지만, 그 신호들이 의미를 가지려면 *해석의 틀* 이 필요하다. 모델은 바로 그 틀의 역할을 한다.

같은 그래프 위에 실 PLC 의 신호를 IO 바인딩으로 매핑하면, 디바이스 별 비트 신호가 비로소 "Cyl1.ADV 가 Going 상태" 처럼 *DS 언어의 어휘로 해석된 사실* 이 된다. Work 의 상태머신이 현장 동작의 진단 격자가 되고, Arrow 가 흐름의 차단·전이를 설명하는 단위가 된다. 알람·로그·OEE(Overall Equipment Effectiveness) 같은 운영 지표가 *이름 있는 모델 요소* 위에서 해석되므로, 이상 발생 시점에 사용자가 보는 화면이 "5 번 비트가 1 로 떴음" 이 아니라 "구역 2 의 실린더 후진이 Homing 단계에서 멈춤" 으로 표현된다.

이 해석의 격자는 자연어 시점부터 현장 태그명까지의 *명명 일관성* 위에서 성립한다. 사용자가 입력에서 사용한 이름이 모델 요소의 이름이 되고, 그 이름이 매크로 치환을 통해 현장 IO 태그명이 된다. 모니터링 화면이 갑자기 새로운 어휘를 들고 나타나는 일이 없으며, 사용자는 같은 어휘로 사양을 쓰고, 같은 어휘로 시뮬레이션을 보고, 같은 어휘로 현장을 관찰한다.

### 4.3 Control

세 번째 활용은 모델을 PC 프로그램이 *직접* 적재하여 in-process 엔진으로 실행하는 것이다. 별도의 코드 생성·다운로드 단계가 없다. 모델 자체가 실행 단위이며, PC 프로세스가 모델의 의미론을 그대로 인터프리팅하여 현장 IO 와 통신한다. 시뮬레이터가 가상의 IO 와 대화한다면, 이 PC-based control 모드는 *같은 인터프리터가 실제 IO 와* 대화한다고 볼 수 있다.

이 모드가 적합한 영역은 분명하다. 소규모 셀, 시작품 단계 설비, 연구·교육용 장비, edge controller, soft control 환경처럼 산업용 PLC 인프라를 별도로 갖추지 않은 상황이다. 산업 PLC 가 제공하는 등급의 안전성·실시간성을 요구하지 않는 대신, *모델 변경 → 즉시 실 동작* 의 짧은 사이클을 얻는다. 모델을 한 줄 고치고 재로드만 하면, 시뮬레이션과 동일한 의미론으로 PC 가 실제 IO 를 흔든다.

이 활용의 가치는 시뮬레이션과 실 동작 사이의 단절이 좁아진다는 점에 있다. 통상의 워크플로에서는 시뮬레이션 통과 → 코드 생성 → PLC 다운로드 → 시운전이라는 긴 사슬을 거쳐야 비로소 "모델대로" 동작하는 설비를 본다. PC-based control 은 그 사슬을 압축하여, 모델을 만든 책상 위에서 그대로 *재컴파일 없는 실 동작* 을 가능하게 한다. 같은 모델이 책상의 시뮬레이션과 현장 PC 의 실제어를 동일 의미로 수행한다.

### 4.4 Code-generation 으로 PLC 배포

네 번째 활용은 모델로부터 PLC 가 실행할 수 있는 표준 코드를 생성하여, 그 코드를 산업용 PLC 에 다운로드해 실행하는 것이다. 실행 주체는 PC 가 아니라 PLC 이며, PC 는 모델링과 배포 단계에서만 관여하고 운영 단계에서는 빠진다. 이 모드는 *양산 라인, 인증을 요구하는 환경, 다중 IO 와 고신뢰가 요구되는 설비* 에 적합하다. 산업 PLC 가 제공하는 등급의 안전성·실시간성·내환경성이 그대로 활용되며, 기존 현장의 엔지니어링 도구(벤더 PLC IDE) 와 운영 도구(HMI, SCADA) 가 그대로 호환된다.

코드 생성에서 가장 중요한 설계 결정은 *LLM 에게 코드 생성권을 주지 않는 것* 이다. 모델 → 코드 변환은 결정적(deterministic) 변환기가 수행한다. 동일한 모델은 항상 동일한 코드를 만들고, 검증된 변환 규칙 위에서만 변환이 일어난다. 이 결정성이 약해지면 안전성(잘못된 코드가 실 설비에 흘러갈 위험), 표준 준수(벤더 코드 규약 위반), 재현성(같은 모델이 매번 다른 코드를 만드는 혼란) 셋이 함께 영향을 받는다. 이 결정의 정당화는 책임 경계 절에서 더 다룬다.

#### 4.4.1 PLC 프로젝트 산출

PLC 산출의 1차 대상은 LS 산전 XGI 프로젝트(`.xml`) 이며, 이는 상용 PLC 엔지니어링 도구가 그대로 열 수 있는 포맷이다. 산출물에는 POU(Program), Function Block 인스턴스, IO 신호 매핑, 진단 메시지가 포함된다. 변환 파이프라인은 (i) IO 신호·주소 추출, (ii) FB 매핑 및 IR(중간 표현) → Rung 코드 방출, (iii) 매핑 결과의 모델 측 영속화 세 단계로 이루어진다. 템플릿 기반 골격과 코드 방출을 혼합한 전략을 사용한다.

템플릿은 어셈블리 임베디드 리소스로부터 사용자 폴더에 추출되며, 사용자가 직접 편집하여 사이트별 조정(예: 통신 설정, 기본 라이브러리)을 할 수 있다. 이후 도구 업그레이드 시에도 사용자 편집은 보존된다. Wizard 모드의 IO 명명에는 매크로 치환(`$(F)`, `$(D)`, `$(A)`) 이 사용되어 Flow/Device/Api 이름이 IO 심볼명에 그대로 반영된다. 예: `Input_$(F)_$(D)_$(A)` → `Input_Run_Cyl1_ADV`. 이로써 자연어 시점부터 PLC 태그명까지의 명명 일관성이 유지되며, 이는 앞서 본 Monitoring 에서 다시 활용된다.

현재 노출된 1차 지원 벤더는 LS XGI/XGK 와 Mitsubishi MX 이며, Allen-Bradley S7 용 프로토콜 모듈이 동봉되어 있으나 UI 노출은 단계적 확장 영역이다.

#### 4.4.2 AAS 표준 자산 동시 산출

같은 모델로부터 AAS(Asset Administration Shell) 3.1 환경 파일이 동시에 산출되어, 외부 시스템과의 디지털 자산 교환이 모델 기반으로 통일된다. DS 그래프의 계층은 다음과 같이 AAS Submodel 트리로 투영된다.

- Project → 최상위 SubmodelElementCollection (SequenceModel Submodel)
- DsSystem → SMC (Flows SML + ApiDefs SML, 능동/수동 구분 플래그 포함)
- Flow → SMC (Works SML + ArrowsBetweenWorks SML)
- Work → SMC (Calls SML + ArrowsBetweenCalls SML)
- Call / ApiCall → SMC (속성들)

각 필드는 Concept Description(CD) 에 일대일로 등록된다. 동시에 IDTA 가 정한 표준 Submodel 인 **Nameplate** (IDTA 02006-3-0), **TechnicalData**, **HandoverDocumentation** (IDTA 02004-1-2) 이 동봉되어 AAS 환경 간 상호 운용성이 보장된다. 디바이스 분리 출력 옵션을 켜면 각 수동 디바이스를 독립 자산으로 분리하여 별도 AAS 패키지로 산출할 수 있다. DS 언어가 사용자 측 표현이고 산업 표준이 외부 호환 출력이라는 분업이 여기서 실제로 동작한다.

### 4.5 한 모델, 두 실행 매체

앞서 본 Control 과 Code-gen → PLC 는 *같은 모델에서 분기되는 두 실행 매체* 이다. 사용자는 동일 사양으로 두 매체를 자유 선택·전환할 수 있다. 두 매체의 성격은 다음과 같이 정리된다.

| 축 | Control (PC 직접 실행) | Code-gen → PLC |
|---|---|---|
| 실행 주체 | PC 프로세스 (in-process 엔진) | 산업용 PLC |
| 산출물 | 없음 — 모델 자체가 실행 단위 | 벤더 PLC 프로젝트 파일 |
| 모델 변경 반영 | 즉시 (재로드) | 재생성 → 다운로드 → 재시작 |
| 적합 영역 | 소규모 셀, 시작품, 연구·교육, edge / soft control | 양산 설비, 인증·표준 환경, 다중 IO |
| 안전 / 실시간 등급 | PC OS 의존 | 산업 PLC 등급 |
| 결정성 보장 위치 | 모델 인터프리터 | 결정적 변환기 + PLC 실행 |
| 사이클 길이 | 짧음 (편집 → 재로드) | 김 (변환 → 다운로드 → 시운전) |
| 인프라 의존성 | PC + IO 인터페이스 | 산업 PLC + 엔지니어링 도구 |

핵심은 두 경로가 **동일 모델에서 분기** 한다는 것이다. 사용자는 시작품 단계에서 PC-based control 로 빠르게 동작을 확인한 뒤, 양산 단계에서 동일 모델을 그대로 PLC 코드로 변환·배포할 수 있다. 두 매체 사이에 *모델을 다시 만들 비용* 이 들지 않는다. 또한 운영 중에 발견된 사양 보강도 한 모델에서 수정한 뒤 두 매체로 다시 흘려보내면 되므로, 매체 별로 따로 유지보수할 필요가 줄어든다.

이 분기 구조는 시뮬레이션·모니터링과 결합되면 더욱 자연스럽다. 시작품을 PC 가 직접 제어하면서 동시에 같은 모델로 시뮬레이션을 돌려 예상 동작과 비교하거나, 양산 PLC 가 돌고 있는 현장의 신호를 같은 모델 위에 매핑하여 모니터링하는 흐름이 같은 어휘 위에서 이어진다. **하나의 모델이 네 가지 활용의 교집합** 이 되는 것이다.

### 4.6 네 활용의 공통 기반

앞서 본 네 활용은 표면적으로는 서로 다른 행위처럼 보이지만, 모두 다음 공통 기반 위에서 성립한다.

- **단일 진실 원천(SSOT)** — DS 그래프 하나가 네 활용 모두의 출처이다. 그래프의 텍스트 직렬화(YAML)도 함께 제공되어 사람이 읽고 편집하고 diff·revert 할 수 있는 형식으로도 보존된다. 모델은 디스크 위의 데이터로 영속화되고, 채널이 무엇이든 결국 같은 그래프를 갱신한다.

- **Cascade 와 트랜잭션** — 사용자가 "실린더 하나를 추가" 한다는 의도를 표현하면, 그래프 측에서는 디바이스 정의, 흐름 안의 호출, 인터페이스 정의, 연결선, 수동 내부 상호 배타 규칙 같은 다수의 요소가 함께 만들어진다. 이 다단 변경은 단일 트랜잭션 경계 안에서 일어나며, 검증에 실패하면 일관되게 원위치로 돌아간다. 부분 적용으로 인한 그래프 손상이 발생하지 않는다. 적용 진입 시점에 snapshot 카운트를 기록해 두었다가 검증에서 오류가 발견되면 누적 연산을 잘라내어 트랜잭션 경계를 형성하는 방식이다.

- **1 변경 = 1 undo** — 사용자 관점의 변경 단위와 시스템 관점의 변경 단위가 일치한다. 시뮬레이션 단계에서 한 변경을 시도해 보고, 결과가 마음에 들지 않으면 한 번의 되돌리기로 직전 상태로 돌아간다. 이 일치는 모니터링·Control·Code-gen 어느 단계에서도 동일하게 유지된다.

- **다채널 협업** — 시각 편집, 텍스트(YAML) 편집, 외부 도구 가져오기, 그리고 LLM 채팅이 모두 같은 SSOT 위에서 동작한다. 한 채널의 변경은 다른 채널에 자동으로 반영되며, 사용자는 가장 빠른 채널을 그때그때 선택해 쓴다.

이 공통 기반이 있기 때문에 한 모델에서 두 실행 매체로 분기되는 구조가 의미를 가진다. 같은 모델 위에서 분기한다는 말은, 그 모델이 분기 전후로 *불변* 임이 보장될 때만 진실이다. SSOT·트랜잭션·undo·다채널 협업이라는 공통 기반이 그 불변을 지탱한다.

## 5. LLM 활용의 장점 — 진입 장벽 낮춤

### 5.0 한 줄 명제

앞 두 장에서 DS 언어로 표현된 모델의 가치는 이미 정해져 있다. LLM 의 기여는 그 가치를 새로 만드는 것이 아니라, 가치에 도달하기 위해 사용자가 지불해야 하는 *진입 비용을 낮추는 것* 이다. 본 장은 이 한 줄 명제를 구체적인 진입 마찰 해소 사례 다섯 가지로 풀어낸 뒤, 그 효과가 네 활용 각각을 어떻게 *증폭* 하는지를 마지막 절에서 정리한다.

### 5.1 모델 어휘를 외울 필요 없음

사용자가 익숙한 어휘는 "구역", "실린더", "전진/후진", "공정 순서" 같은 *현장 어휘* 이다. 그러나 DS 언어가 1급으로 다루는 어휘는 Flow, Work, Call, Arrow, ApiDef 같은 *모델 어휘* 이다. 이 어휘 전환 부담이 모델 표현 도구의 가장 큰 진입 마찰이었다.

LLM 결합 후에는 그 부담이 LLM 쪽으로 옮겨간다. 사용자는 "두 실린더가 순차로 전진한 뒤 다시 순차로 후진" 같은 현장 어휘 한 줄을 입력하고, LLM 이 이를 DS 언어의 모델 어휘로 정규화한다. 사용자는 모델 어휘를 *몰라도* 모델을 만들 수 있다. 모델링 언어의 학습 곡선이 도구 사용 측면에서는 크게 낮아진다. 다만 사용자가 결과 모델을 *읽고 검토하는* 단계에서는 DS 언어의 어휘를 어느 정도는 인지하는 편이 좋다 — 검토 시점에는 우선 Mermaid 다이어그램으로 구조를 한눈에 확인하고 필요할 때만 YAML 텍스트를 들여다보면 되므로, 검토 부담은 입력 부담에 비해 훨씬 작다.

### 5.2 Greenfield 진입의 마찰 제거

백지에서 첫 모델을 만드는 일은 도구 학습 외에도 *시작 자체의 마찰* 을 동반한다. 어떤 메뉴를 먼저 누를지, 어디서부터 그릴지, 어떤 단축키를 외워야 빠른지 같은 운영적 결정들이 백지의 초입을 막아선다.

LLM 채팅 진입점은 이 마찰을 크게 줄인다. 사용자는 채팅창을 열고 사양 한 문장을 입력하면, 그 한 문장으로 모델의 골격이 만들어진다. 시뮬레이션·Control·Code-gen 중 어느 활용으로 진입하더라도, 그 활용이 의지하는 모델이 한 문장으로 손에 들어온다는 점이 중요하다.

### 5.3 Brownfield 점진 편집

LLM 의 진입 비용 절감 효과는 백지 상태에만 한정되지 않는다. 이미 존재하는 모델에 대해서도 "3구역 다음에 4구역 추가, 거기에 실린더 두 개 순차 전진" 같은 의도 표현으로 기존 모델을 보존하면서 점진적으로 변경할 수 있다. 이름 변경, 삭제, 연결 추가 같은 흔한 운영 변경도 모두 같은 진입점으로 처리된다.

이때 1 발화 = 1 변경 = 1 undo 라는 직관적 변경 단위가 유지되므로, 사용자는 점진 편집을 *실험적으로* 시도할 수 있다. 결과가 의도와 다르면 한 번의 되돌리기로 원위치한다. 점진 편집의 안전 그물은 앞 장의 트랜잭션·undo 공통 기반이 그대로 받쳐준다.

### 5.4 GUI / Chat 자유 혼용

LLM 이 들어왔다고 해서 기존 시각 편집(GUI)이 대체되는 것은 아니다. 두 채널은 서로의 강점이 다르다. 미세 위치 조정, 단일 속성 수정 같은 작업은 GUI 가 빠르고, 한 번에 다수 요소를 만들거나 구조를 크게 바꾸는 작업은 Chat 이 빠르다. 사용자는 두 채널을 자유롭게 교대로 쓰며, 어느 채널을 쓰든 결과는 같은 SSOT 에 반영된다.

이 자유 혼용을 가능케 하는 것은 앞서 정리한 *다채널 협업* 기반이다. GUI 에서 사용자가 직접 수정한 내역은 다음 채팅 턴에 LLM 에게 자동 통지되므로, LLM 은 매번 현재 모델 상태를 다시 묻지 않고도 사용자의 GUI 작업을 인지한 채 다음 편집을 이어간다. 두 채널 사이의 *상태 동기화 비용* 이 사용자 입장에서 보이지 않는다. 또한 채팅 턴이 끝나면 LLM 이 발행한 모델이 Mermaid 다이어그램으로 시각화되어 사용자가 적용 결과를 한눈에 검토할 수 있으며, 정밀한 검토가 필요한 경우 YAML 텍스트가 함께 제공된다 — 작은 응답은 채팅 버블에 inline 으로, 큰 응답은 별도 다이얼로그로 분기된다.

### 5.5 LLM provider 다양성

Promaker 는 단일 `IChatClient` 추상화 위에 여러 종류의 LLM 백엔드를 둔다 — Claude CLI, Codex CLI, Anthropic API, OpenAI API, Groq API, 그리고 사내망·오프라인 환경을 위한 로컬 Ollama. 사용자가 어떤 백엔드를 선택하든 *동일한 system prompt 와 동일한 MCP 도구 집합* 이 노출되도록 설계되었으며, API 키는 OS 보안 저장소(예: DPAPI)로 즉시 암호화 저장된다. 동일 협업 계약 위에서 다른 provider 가 만들어내는 결과를 직접 비교할 수 있다는 점은 모델 표현의 결정성을 유지한 채 LLM 측의 선택 자유도를 사용자에게 돌려준다.

### 5.6 진입 장벽 낮춤이 네 활용을 어떻게 증폭하는가

LLM 의 가치는 네 활용 각각에서 다음과 같이 증폭된다.

- **Simulation 증폭** — 시뮬레이션을 *돌릴 수 있는 사람* 의 수가 늘어난다. 모델 어휘 학습이 필요 없으니, 시뮬레이션을 통해 흐름 오류를 잡아내고 사양을 점검하는 일이 더 많은 엔지니어에게 가능해진다.
- **Monitoring 증폭** — 모니터링용 모델을 *만들 수 있는 사람* 의 수가 늘어난다. 현장 신호의 해석 격자를 한 사람이 모델 어휘로 일일이 만들지 않아도, 현장 어휘 입력만으로 격자가 만들어진다.
- **Control 증폭** — 시작품·소규모 셀의 PC-based control 사이클이 짧아진다. "사양 변경 → 모델 수정 → 즉시 실행" 흐름의 첫 단계인 모델 수정이 한 발화로 줄어들면, 짧은 사이클의 가치가 본격적으로 살아난다.
- **Code-gen 증폭** — 양산 단계의 사양 변경이 표준 산업 인프라까지 흘러가는 데 드는 *재모델링 비용* 이 줄어든다. 변경 의도를 한 발화로 표현하면 모델이 갱신되고, 결정적 변환기가 그것을 PLC 코드와 AAS 자산으로 옮긴다.

이 증폭 효과의 공통 원천은 단 하나다 — 모델을 만드는 비용이 낮아지면 *모델 위에 서 있는 모든 활용의 빈도가 높아진다*. 네 활용은 모델이 있어야 가능했지만, 모델을 만드는 일이 비싸면 활용도 드물게 쓰인다. LLM 은 활용 자체가 아니라 *활용의 빈도와 도달 범위* 를 키운다.

## 6. 결합 설계의 책임 경계

### 6.1 한 줄 원칙

LLM 과 Promaker 의 책임 경계는 다음 한 줄로 정리된다.

> **LLM 책임 = 자연어 → DS 언어로의 정규화** (이름·구조·연결 종류 결정).
> **Promaker 책임 = 모델 구성·일관성·트랜잭션·표준 산출** — LLM 이 직접 만져서는 안 되는 영역.

이 경계는 본질(모델) 과 채널(LLM) 의 위계를 그대로 반영한다. LLM 은 DS 언어로 표현된 모델 문서를 *만들 책임* 을 지며, Promaker 는 그 문서를 그래프로 *집행할 책임* 을 진다. LLM 이 집행 영역(코드 생성, 식별자 관리, 트랜잭션)에 침범하기 시작하면 코드 생성의 결정성·표준 준수·재현성, 두 실행 매체 분기 신뢰성, 네 활용 공통 기반이 함께 약해진다.

### 6.2 협업 계약으로서의 선언적 모델 문서

두 책임 사이를 잇는 인터페이스는 DS 언어의 YAML 표기로 작성된 *선언적 모델 문서* 이다. LLM 은 자연어 입력을 받아 이 문서를 한 차례 발행하고, Promaker 는 그 문서를 검증한 뒤 그래프로 반영한다. 이 문서가 "협업 계약" 의 역할을 한다.

선언적 모델 문서가 협업 계약으로 적합한 이유는 네 가지다. 첫째, *LLM 친화성* — 들여쓰기와 의미 구조가 명확해 LLM 의 출력 신뢰도가 높다. 둘째, *round-trip 동형성* — 같은 그래프를 발행 → 다시 읽기 했을 때 텍스트가 동일하므로, 다음 턴에 LLM 이 일관된 출발점에서 작업을 이어간다. 셋째, *내부 식별자 비노출* — 모든 참조는 사람이 읽는 점-경로로 표현되며, GUID 같은 내부 식별자는 LLM 에게 노출되지 않는다. 넷째, *가독성과 결정성의 분리* — 사용자에게 보이는 표기는 가독성 위주이지만, 시스템 내부의 적용은 결정적이다.

LLM 이 한 차례에 발행하는 YAML 모델 문서의 예시는 다음과 같다 (스키마 `promaker/v0`).

```yaml
protocol: promaker/v0

project: M1

systems:
  - system: Controller
    kind: active
    flow Run:
      works:
        Adv:    { calls: [Cyl.ADV] }
        Ret:    { calls: [Cyl.RET] }
      arrows:
        - Adv -> Ret : Start

  - system: Cyl
    kind: passive
    device: cylinder
```

식별자는 모두 사람이 읽는 이름이며, GUID 는 LLM 에게 노출되지 않는다. 백엔드는 1-pass 에서 이름 테이블을 만들고 2-pass 에서 forward reference 를 GUID 로 해소한다. 이로써 LLM 은 그래프 편집의 순서를 신경 쓰지 않고 선언적 사양만 생산하면 된다. Arrow 는 `A -> B : <Type>` 표기로 6 종 (Start / Reset / StartReset / ResetReset / Group / Unspecified) 중 하나를 명시한다. `device:` 키는 `cylinder` / `clamp` / `robot` 같은 알려진 장치 유형의 sugar 이며, 그 외에는 `custom(<이름>)` + `apis:` 목록으로 표현된다.

### 6.3 LLM 에 노출되는 도구 카탈로그

LLM 은 in-process HTTP 서버로 노출된 MCP(Model Context Protocol) 엔드포인트와 통신한다. 외부 침입을 막기 위해 루프백(127.0.0.1) 임시 포트에 바인딩되며, nonce 헤더가 검증된다. 노출되는 도구는 다음과 같이 doc-level 진입점과 read-only 조회로 정리되어 있다.

| 도구 | 방향 | 설명 |
|---|---|---|
| `apply_model_doc(model)` | YAML → 그래프 | 전체 적용. 부분 실패 시 자동 rollback. 정보 미스매치 시 Levenshtein 기반 가까운 후보를 진단 메시지로 반환 |
| `validate_model_doc(model)` | YAML 검증 | dry-run. 그래프를 건드리지 않고 스키마와 제약만 점검 |
| `export_model_doc(path?, depth?)` | 그래프 → YAML/JSON | 부분 export 도 지원 (점-경로 scope + walk 깊이) |
| `json_to_yaml(json)` | 형식 변환 | 검증 없이 텍스트 변환만 수행 |
| `find_by_name` | 읽기 | 대소문자 무시 부분 일치 → 점-경로 |
| `validate_model` | 읽기 | 고아·끊어진 연결·중복 이름 점검 |

부분 export 결과에는 진단 metadata 가 동반되며, view-only 로 표시되어 apply / validate 재입력은 거부된다. 이 카탈로그는 단계적 진화의 결과이다 — 초기에는 21 종에 달하는 단일 연산 도구를 노출했으나, 토큰 비용과 재시도 빈도가 늘어 현재의 6 종으로 응축되었다 (자세한 경위는 논의 절에서 다룬다).

### 6.4 System prompt 의 3-tier 합성

LLM 에 주입되는 system prompt 는 다음 세 계층을 자연 정렬 후 연결하여 생성된다.

1. **Baseline (어셈블리 내장)** — 모델링 규칙의 기본형
2. **Operator (실행 파일 폴더)** — 설치 환경별 보정 가능
3. **User (사용자 폴더)** — 사용자 개인 규칙

Baseline 은 (i) 엔티티 정의, (ii) 자연어 → 엔티티 분해 규칙, (iii) MCP 도구 호출 규약 — 주력 진입점 `apply_model_doc` 사용 패턴 포함, (iv) 첨부물 처리 규칙의 네 문서로 구성된다. 사용자는 Operator / User 계층에 자신만의 규칙을 얹어 도메인 특화 조정을 할 수 있으며, 이는 provider 다양성과 결합되어 같은 모델 문서를 만들어내는 다양한 경로를 형성한다.

### 6.5 LLM 에게 코드 생성권을 주지 않는 세 이유

본 설계의 가장 명시적인 책임 경계는 *LLM 에게 PLC 코드 생성권을 주지 않는다* 는 결정이다. LLM 은 DS 언어로 표현된 모델 문서까지만 만들고, 그 이후의 코드 생성은 결정적 변환기가 담당한다. 그 이유는 세 가지다.

- **안전성** — 잘못된 PLC 코드가 그대로 설비에 흘러가면 물리적 위험을 야기할 수 있다. LLM 의 확률적 출력은 안전 기준의 *상한* 을 보장하기 어렵다.
- **표준 준수** — 벤더 별 PLC XML 사양은 매우 좁고 깊은 규범이며, LLM 이 학습한 일반 코드 분포와 멀리 떨어져 있다. 모든 디테일을 매번 만족시키기 어렵다.
- **재현성** — 동일 모델이 항상 동일 코드를 만든다는 보장이 있어야, 시뮬레이션·Control·Code-gen 사이의 분기 신뢰가 성립한다. LLM 출력의 비결정성은 이 신뢰를 약화시킨다.

이 세 이유는 두 실행 매체 분기가 가능하려면 LLM 에게 코드 생성권을 주지 않는다는 결정이 함께 필요함을 보여준다. 동일 모델에서 두 실행 매체로 분기한다는 주장은 두 매체 사이의 결정성 보장 위에서만 성립한다. LLM 이 코드를 쓰는 순간 그 결정성이 약해지고, 분기의 신뢰가 함께 흔들린다.

## 7. 사용 시나리오

본 장은 네 활용이 LLM 진입 채널과 결합되어 나타나는 전형 시나리오 네 가지를 정리한다.

### 7.1 Greenfield 와 Simulation

빈 프로젝트에서 사용자가 다음과 같이 채팅창에 입력한다.

> "실린더 한 개로 단순 왕복 동작 흐름 하나 만들어줘. 시스템 이름은 Controller, 흐름 이름은 Run."

system prompt 의 분해 규칙과 doc-level 사용 규약이 함께 주입되므로, LLM 은 한 차례의 도구 호출로 앞서 본 형태의 YAML 문서를 발행한다. 규약상 동일 디바이스의 ADV/RET 은 수동 내부에서 ResetReset Arrow 로 자동 연결되므로 LLM 이 이를 별도로 기술할 필요가 없다 (백엔드가 채워준다).

발행 호출은 트랜잭션 buffer 에 누적되며, 적용 직전에 검증 단계를 통과해야 확정된다. 검증 단계에서 다음 사항이 점검된다.

- 모든 Work 는 Flow 에 속한다.
- 모든 Call 의 ApiName 은 해당 디바이스의 ApiDef 집합 안에 존재한다.
- ResetReset 제약이 동일 디바이스의 상반 행위 쌍에 대해 만족된다.

실패 시 누적 연산이 잘려나가 그래프는 적용 전 상태로 되돌아간다. 사용자는 이어서 시뮬레이터를 열어 한 단계씩 진행시켜 본다. 모델 어휘를 직접 다룰 줄 모르는 사용자도 *예측 가능한 흐름* 을 짧은 시간 안에 손에 쥘 수 있게 된다.

### 7.2 PC 직접 제어

소규모 셀이나 시작품 단계에서는 PLC 인프라를 갖추지 않은 채로 빠르게 동작을 확인하고 싶다. 사용자는 위 시나리오의 모델을 그대로 PC 가 적재해 실행한다. 시뮬레이션과 같은 의미론으로 *실제 IO* 가 움직인다. 사양이 바뀌면 한 발화로 모델을 고치고 재로드만 하면 다음 사이클이 시작된다. *재컴파일 없는 실 동작* 의 사이클이 LLM 진입 채널과 결합되어 한층 더 짧아진다.

### 7.3 PLC 배포

양산 라인에 들어가는 단계에서는 같은 모델을 결정적 변환기에 통과시켜 산업 PLC 가 이해할 표준 코드로 옮긴다. 사용자는 모델을 다시 만들지 않는다. 시작품 단계에서 검증된 그 모델이 그대로 양산 코드의 출처가 된다. 사용자는 동일한 그래프로부터 세 종류 산출물을 얻는다.

- `M1.yaml` — 모델 문서. 사람이 검토·diff·revert 가능한 SSOT 텍스트.
- `M1.aasx` — AAS 3.1 환경 파일. 외부 AAS 뷰어에서 Submodel 트리를 확인할 수 있다.
- `M1.xml` — LS XGI 프로젝트 파일. 상용 엔지니어링 도구에서 열어 자동 생성된 사다리 논리와 FB 인스턴스, IO 매핑을 확인할 수 있다.

세 산출물은 동일한 DS 그래프를 출처(SSoT)로 하므로, 향후 그래프가 변경되면 일관되게 재생성된다. 사용자는 YAML 산출물을 직접 편집한 뒤 `apply_model_doc` 으로 재투입함으로써 LLM 을 거치지 않고 그래프를 갱신할 수도 있다.

### 7.4 운영 단계의 Monitoring 과 Patch

현장이 가동되기 시작한 뒤에는 모니터링 화면이 DS 언어의 어휘로 신호를 해석한다. 운영 중에 새 사양이 들어오면, 사용자는 같은 채팅 채널로 점진 편집을 가하고 모델을 갱신한다. 갱신된 모델은 다시 시뮬레이션·Control·Code-gen 의 어느 경로로든 흘러갈 수 있다. *운영 → 변경 → 재배포* 의 큰 순환이 같은 모델 위에서 닫힌다.

## 8. 안전·신뢰

LLM 결합은 외부 시스템(클라우드 LLM provider, 로컬 모델 endpoint 등)과의 상호 작용을 동반하므로, 모델의 본질적 가치를 지키기 위한 안전·신뢰 장치가 함께 설계된다.

### 8.1 단계별 동의

LLM 채팅 첫 진입 시 데이터 전송 동의를 받고, 유료 API 첫 사용 시 비용 동의를 별도로 받으며, 고권한 도구가 결합된 provider 의 경우 추가 동의를 한 번 더 받는다. 거부 시 해당 경로는 비활성화된다. 사용자는 자신의 데이터·비용·권한이 어디까지 노출되는지를 명시적으로 인지한 상태에서 결합을 사용한다.

### 8.2 API 키 보호

provider API 키는 운영체제 보안 저장소에 즉시 암호화 저장된다. 다른 사용자·다른 머신에서 평문으로 읽어내기 어렵다. 모델명·로컬 endpoint 주소 같이 민감하지 않은 항목만 평문으로 보존된다.

### 8.3 Prompt Injection 방어

첨부 파일이나 외부 사양 안에 "이전 지시를 무시하라" 류의 명령형 문장이 포함되어 있어도 명령으로 해석되지 않도록 한다. 사양 블록은 명시적 경계 표시로 *데이터* 임을 표시하며, 파일명·경로 안의 의심스러운 문자열은 라벨로만 처리된다. 비밀 정보가 들어 있을 가능성이 큰 파일(.env 등)은 첨부 자체가 차단된다.

### 8.4 그래프 무결성 보호

LLM 의 발행이 그래프를 직접 갱신하지 않는다는 점이 가장 강한 안전 장치이다. 발행은 트랜잭션 buffer 에 누적되며, 적용 직전의 검증을 통과해야 그래프에 반영된다. 검증 실패는 일관 rollback 으로 처리된다. 사용자는 *부분 적용으로 인한 모델 손상* 을 경험하지 않는다. 또한 LLM 이 한 턴에서 호출할 수 있는 편집 연산 수에는 상한이 설정되어 있어 도구의 폭주를 사전 차단한다.

## 9. 논의

### 9.1 위계가 흐려지면 무엇이 약해지는가

본 논문의 가장 중심 주장은 서론에서 미리 던졌고 앞의 핵심 장들에서 두 차례 확인되었다. 모델이 본질이고 LLM 은 채널이며, 이 위계가 흐려지면 네 활용 전체가 함께 영향을 받는다. 구체적으로는 다음과 같다.

- LLM 이 *식별자 관리* 에 침범하면 round-trip 동형성과 다채널 협업이 약해진다.
- LLM 이 *트랜잭션* 을 직접 다루면 부분 적용으로 인한 그래프 손상 가능성이 생긴다.
- LLM 이 *코드 생성* 을 직접 수행하면 두 실행 매체 분기 신뢰가 약해진다.
- LLM 이 *모델의 진실 원천* 을 차지하면 GUI · 텍스트 편집 · 외부 도구와의 협업이 좁아진다.

이 네 약화는 모두 같은 뿌리를 가진다 — 본질 자리에 채널이 들어선 결과이다. 책임 경계는 정책 문제가 아니라 시스템의 정합성 문제이다.

### 9.2 doc-level 단발 발행으로의 진화

초기 설계는 LLM 에게 21 종에 달하는 단일 연산 도구(`add_project`, `add_flow`, `apply_operations` 등)를 노출했다. 이는 LLM 이 그래프를 점진적으로 빚어가게 했지만, 한 발화가 수십 회의 tool call 로 분해되어 token 비용과 재시도 빈도가 늘어나는 부작용이 있었다. 현재 설계는 LLM 이 한 차례의 선언적 YAML 문서를 발행하는 doc-level 진입점을 주력으로 하며, 단일 연산 도구는 escape hatch 로만 남는다. 사내 측정에서는 같은 시나리오 대비 토큰 사용량과 재시도 횟수가 모두 감소했다. 이 진화는 협업 계약과 트랜잭션 공통 기반의 자연스러운 귀결이다.

### 9.3 트랜잭션 경계와 사용자 경험

`apply_model_doc` 의 단발 적용은 단일 Undo 단위를 만들어 사용자가 "한 번의 채팅 → 한 번의 되돌리기" 라는 직관적인 모델을 가질 수 있게 한다. 또한 YAML 이 텍스트 SSOT 로서 디스크에 보존되므로 사용자는 LLM 없이도 직접 편집·diff·revert 를 통해 모델을 진화시킬 수 있다. 이 두 성질은 진입 장벽 낮춤이 가져온 변경 빈도 증가를 *추적 가능한 형태로* 흡수하는 장치이다.

### 9.4 한계 및 향후 과제

- **입력 채널의 확장** — 현재 LLM 입력은 자연어 텍스트가 중심이다. 도면·표·손그림 같은 이미지 입력의 본격 해석은 별도 단계로 다루어지며, 사양서 PDF 파싱은 첨부 수준에 머문다.
- **런타임 측정값 매핑** — 모니터링이 신호의 *해석 격자* 를 제공하지만, 측정값을 모델 어휘로 자동 라벨링하는 깊은 매핑은 본 논문 범위 밖이다.
- **벤더 확장 범위** — Code-gen 의 1차 대상 벤더가 가장 성숙해 있으며, 그 외 벤더 지원은 단계적 확장 영역이다.
- **PC-based control 의 인증** — PC 직접 실행 매체는 PC OS 등급의 안전성에 의존하므로, 산업 안전 인증이 요구되는 환경에서는 사용 범위를 한정해야 한다.
- **YAML preview confirm/cancel** — 현재는 발행과 적용이 한 턴에 묶여 있으며, 사용자가 적용 여부를 명시적으로 confirm/cancel 하는 인터랙션은 보류 상태이다.
- **DS 언어의 외부 채택 여부** — DS 언어는 자사의 모델링 언어이다. 향후 다른 모델링 도구·시뮬레이터·런타임이 같은 어휘를 채택할지 여부는 본 연구 범위 밖의 생태계 문제이며, 현 단계에서는 표준 호환의 출력(PLC 코드, AAS 자산)을 통해 외부 인프라와 연결되는 방향을 우선한다.

### 9.5 일반화 가능성

본 사례는 산업 자동화 도메인을 다루지만, 본 논문이 도출한 책임 경계와 협업 계약의 원리는 다른 모델 표현 도메인에도 적용될 수 있을 것으로 보인다. 모델이 본질이고 LLM 이 채널인 곳, 그리고 모델로부터 다수의 실행 매체가 분기되는 곳이라면 본 논문의 분석이 그대로 작동한다. 다만 도메인 특수성(안전 등급, 표준 호환, 결정성 요건)에 따라 책임 경계의 *위치* 가 조금씩 달라질 수 있다.

## 10. 결론

본 논문은 산업 현장을 모델로 표현하는 일의 가치를 예측·관찰·직접 실행·표준 배포라는 네 활용으로 정리하였다. 네 활용은 모두 같은 모델에서 분기하며, 그중 직접 실행과 표준 배포는 동일 모델에서 갈라져 나가는 두 실행 매체로서 사용자가 시작품 단계의 짧은 사이클과 양산 단계의 표준 안착을 같은 사양으로 자유 선택할 수 있게 한다. Promaker 가 제공하는 일차적 가치는 이 모델 표현 자체이며, DS 언어는 그 표현이 네 활용 모두에서 같은 어휘로 해석되도록 흐름 의도를 1급으로 다루기 위한 도구이다.

이 토대 위에서 LLM 결합의 기여는 모델의 가치를 새로 만드는 것이 아니라 그 가치에 도달하기 위해 사용자가 지불해야 하는 진입 비용을 낮추는 것으로 정리된다. 모델 어휘 학습의 부담이 사용자의 책임에서 LLM 의 책임으로 옮겨가면서, 시뮬레이션을 돌릴 수 있는 사람, 모니터링용 모델을 만들 수 있는 사람, 시작품을 PC 가 직접 제어할 수 있게 만드는 사람, 양산 사양 변경을 따라잡을 수 있는 사람의 수와 속도가 늘어난다. LLM 은 활용 자체가 아니라 활용의 빈도와 도달 범위를 키운다.

이 두 명제가 함께 성립하려면 모델이 본질이고 LLM 은 채널이라는 위계가 유지되어야 한다는 점은 책임 경계와 논의 장에서 반복적으로 확인되었다. 결국 본 사례가 남기는 작은 명제는 다음 한 줄로 모아진다 — 모델 표현 도구에 LLM 을 결합할 때의 설계 결정은 정책의 문제가 아니라 시스템의 정합성을 어디에 두는가의 문제이며, 그 정합성을 단일 진실 원천(SSOT)·트랜잭션 일관성·결정적 변환의 세 기둥 위에 놓을 때 비로소 진입 장벽을 낮추는 일과 본질을 지키는 일이 서로 충돌하지 않고 함께 작동한다.
