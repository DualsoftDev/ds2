# 31. 등록 에러 태그 기반 신뢰성 지표 (eMTBF · eMTTR) — 2026-09-18

> 상태: 설계 확정, 구현 진행 중. 저장·편집 층은 커밋 `5f563541` 로 완료.
> doc/30 의 리듬축과 **별개 축**이다. 두 축의 이름 규약은 doc/30 §6.1.

## 0. 한 문장

사용자가 **이상알람TAG 로 등록한 신호**를 고장의 정의로 삼고, 그 고장이 **실제로 고쳐진 시각**을
설비의 재가동으로 확인해 평균 고장 간격(eMTBF)과 평균 수리 시간(eMTTR)을 낸다.

## 1. 왜 별개 축인가

doc/30 의 리듬축은 사이클 시간만 본다. 무엇이 고장인지 모르고, 알 필요도 없다. 그래서 그쪽 MTBF 는
"느렸던 사이클의 간격"이다.

이 축은 반대다. **무엇이 고장인지 사람이 선언한다.** 그 선언이 이상알람TAG 이고, 그래서 이 축만이
"이 설비가 왜 섰는가"를 말할 수 있다. 두 축은 경쟁하지 않는다 — 같은 설비에서 리듬축이 늘 더 많이
잡는다(느린 사이클 ⊃ 등록된 고장). 값이 다른 것이 정상이고, 다르다는 사실 자체가 정보다.

**사용자 옵션 기능이다.** 태그를 등록하지 않으면 이 축은 존재하지 않는다.

## 2. 회복 판정 — 세 시각의 순서

```
  발생            해소              재가동            다음 발생
   │               │                 │                  │
   ▼               ▼                 ▼                  ▼
───●───────────────●─────────────────●──────────────────●───▶
   └──────── eMTTR(수리) ────────────┘└─── eMTBF(가동) ──┘
```

| 시각 | 정의 | 출처 |
|---|---|---|
| **발생** | 에러 태그가 매칭 조건에 걸림 | `alert.occurredMs` |
| **해소** | 그 조건이 풀림 | `alert.clearedMs` |
| **재가동** | 묶인 디바이스가 쓰이는 flow 중 **하나라도** 새 사이클 시작 | `cycle(flow, startMs)` |
| **복구** | = 재가동 시각 | 도출 |

- **순서를 강제한다.** 재가동은 **해소 이후** 것만 인정한다. 알람이 걸려 있는데 옆에서 사이클이
  돌았다고 회복으로 치면 안 된다.
- **"하나라도"는 OR 다.** 한 디바이스가 여러 flow 에 걸치는 것이 Ds2 모델의 정상이고
  (`Queries.findConflictingDeviceSystemType` 주석), 회복 판정에서는 그 fan-out 이 오히려 맞다.
- 통계 **귀속**에는 flow 를 쓰지 않는다. 귀속은 태그·디바이스 단위다.

## 3. 상태 — 네 가지

| 해소 | 재가동 | 상태 | 지표 |
|:---:|:---:|---|---|
| ✗ | — | **진행 중** | 밖 |
| ✓ | 대기 | **복구 확인 중** | 밖 (아직) |
| ✓ | ✗ (창 초과) | **재가동 미확인** | 밖 + 경고 |
| ✓ | ✓ | **복구 완료** | eMTTR 분모 |

`재가동 미확인` 이 이 기능의 실질 산출물이다 — 리셋만 누르고 설비는 돌지 않은 건을 잡아낸다.
표현은 사실만 말한다(누구를 탓하지 않는다). 설명은 툴팁에 둔다.

**재가동 확인 창** = 해소 이후 이만큼 안에 재가동이 없으면 미확인. 기본 **박제 R × 2**(사이클 두 바퀴),
설정에서 조절한다. 무한정 기다리면 6개월 뒤 사이클로도 확정이 되어 버린다.

## 4. 계산

```
eMTTR = mean(재가동 − 발생)        − 그 사이 비생산 시간
eMTBF = mean(다음 발생 − 직전 재가동) − 그 사이 비생산 시간
```

- **비생산 차감은 필수다.** 금요일 19시에 고치고 월요일 08시에 라인이 돌면 차감 없이 eMTTR 61시간이
  찍힌다. 수리 시간이 아니라 주말이다. 비생산은 doc/30 §5 가 사이클마다 판정해 두므로 겹치는 구간만 뺀다.
- **분모가 다르다.** eMTBF 의 고장 건수는 **발생 전체**, eMTTR 평균은 **복구 완료 건만**.
  미확정 건을 건수에서도 빼면 고장이 과소 계상되어 eMTBF 가 부풀어 오른다. 화면에 두 모집단을 함께 밝힌다.
- **표본 게이트** — K 미만이면 숫자 대신 `표본 부족 (n=3)`. doc/30 의 K 규약과 같은 어휘.

### 4.1 대상에서 빼는 것

| 대상 | 이유 |
|---|---|
| 모니터링TAG(Info) | 알람이 아니다. `alert` 행 자체가 생기지 않는다 |
| 디바이스 **미지정** · **전역** | 볼 flow 집합이 없다. 미지정은 커버리지가 세고, 전역은 분모에서도 뺀다 |
| `Changed` 매치옵 | 정상 상태 개념이 없어 발화 즉시 해소된다(`isConditionActive` → 항상 false). 지속시간이 뜻을 갖지 못한다 |
| 재발화(dedupe) | 회복 없이 같은 태그가 다시 울리면 1건으로 묶는다 |

## 5. 저장하지 않는다

회복 시각도 상태도 **저장하지 않고 조회 시 도출한다**(doc/30 §9.1-③).

```
alert(발생·해소) + cycle(재가동·비생산) + 설정(디바이스 귀속)  →  조회 시 계산
```

덕분에 **나중에 디바이스를 묶으면 과거 알람도 함께 살아난다.** 박제했다면 안 되는 일이다.
κ 를 바꾸면 과거 사이클이 재라벨되는 것과 같은 성질이다.

재가동 근거인 `cycle` 은 영구 보존이라 원시 신호(`signal`, 롤링)가 지워져도 도출이 유지된다.
디바이스 단위 call OUT↑ 까지 내려가지 않고 **flow 단위**로 보는 덕이다.

## 6. 귀속 정보

`AbnormalAlarm.UserTagDeviceBindings`(DSPilot 설정 JSON). AASX 가 아닌 이유는
`UserTagDeviceBinding` 주석 참고 — 모델의 *사실*이 아니라 모델로의 *참조*이고, Ds2 모델에는
"디바이스가 소유한 상태 비트"를 적을 자리가 없다(디바이스는 동작(API)의 IN/OUT 으로만 정의된다).

키는 **(System 이름, 주소)** 복합키. 세 상태: 항목 없음 = 미지정 · `""` = 전역 · 이름 = 그 디바이스.

## 7. 함정

- `OnCallGoingStarted` 의 timestamp 는 `DateTime.Now`(**Local**)다. `alert.occurredMs`(UTC epoch)와
  직접 비교하면 9시간 어긋난다.
- 분기 우회 — flow 는 돌지만 고장난 디바이스를 건너뛴 분기일 수 있다. flow 단위를 택한 대가이므로,
  회복 근거(어느 flow 가 언제 돌았는지)를 툴팁에 남겨 사후 추적이 가능하게 한다.
- 통신 단절 중 수리가 끝나도 첫 신호는 복구 후에 온다. `linkEvent` 배지로 대조만 하고 숫자는 건드리지 않는다.
- 실측 표본이 얇다(11일 164건). flow·디바이스로 쪼개면 칸당 0~3건이라 K 게이트가 대부분을 가린다.
  초기 화면은 숫자보다 **상태 4분류 표**가 주력이다.
