2. Cycle이란?

Cycle은 같은 기준점이 다시 돌아올 때까지의 시간이다.

CTi = ci+1 − ci
ci = 이번 Cycle이 시작된 시각, ci+1 = 다음 Cycle이 시작된 시각.
예: Cycle 신호가 10:00:00에 한 번 들어오고, 다음 신호가 10:00:12에 들어오면 CT = 12초다.
하루 집계를 시작했는데 이미 Cycle이 진행 중이라면?
그 Cycle의 시작 시각을 이전 기록에서 가져온다. 이전 시작 시각을 찾을 수 없으면 그 부분은 억지로 계산하지 않고 “모르는 시간(UNK)”으로 표시한다.
Cycle이 아직 끝나지 않았다면?
완료될 때까지 기다리지 않는다. 마지막 Cycle 시작 후 지금까지 몇 초가 지났는지 계속 센다.

3. 기준시간 R — “이 설비의 평소 Cycle은 몇 초인가?”

제품별 표준 CT를 사용하지 않는다. 대신 설비가 실제로 반복한 Cycle 시간에서 대표값을 하나 만든다.

R = median(기준으로 사용할 과거 CT)
median = 데이터를 작은 순서로 놓았을 때 가운데 값. 아주 긴 정지 한두 번에 덜 흔들리기 때문에 평균보다 안전하다.
예: 과거 CT가 9.8, 10.0, 10.1, 10.2, 25.0초라면 평균은 크게 올라가지만 중앙값은 10.1초다.

정본 기준 R

한번 기준으로 확정한 값. 과거 OEE를 나중에 몰래 다시 바꾸지 않는다.

최근 기준 R최근

최근 Cycle의 중앙값. 설비 리듬이 바뀌었는지 감시하는 참고값으로만 쓴다.

왜 두 값을 나누는가? 최근 값으로 기준을 계속 바꾸면 설비가 점점 느려져도 기준도 같이 느려져서 “항상 정상”처럼 보일 수 있다.

4. Cycle이 오래 걸리면 시간을 세 구간으로 나눈다

Cycle이 조금 느린 것과, 아주 오래 멈춰 있는 것을 같은 것으로 보지 않는다. 그래서 기준 R을 이용해 두 개의 시간 경계를 둔다.

H가동 = 정상 상태(계수 넘은 CT 없음)
H비가동 = 각 Flow내 work의 기준 time X κ비가동을 넘은 요소가 하나라도 있으면 해당 flow CT는 비가동
H비생산 = κ비생산 × R
H(비가동) = 비가동가 시작되는 경계, H(비생산) = 아주 긴 비활성으로 보는 경계. κ_D와 κ_N은 사용자 입력이 아니라 스펙 버전에 고정한다.
0 ~ H비가동
기준 안의 시간
T가동
H비가동 ~ H비생산
비가동/비가동
T비가동
H비생산 이후
장기 비활성/비생산
T비생산
예: R=10초, H(비생산)=100초이고 다음 Cycle이 130초 뒤에 왔다면 0~15초는 T(가동), 100~130초는 T(비생산)으로 센다. H(비생산) 은 사용자가 조절 가능.
비가동의 경우 work 의 각 기준시간 x H(비가동) 계수를 한 값을 넘은 요소가 하나라도 있으면 해당 CT는 비가동 처리한다. H(비가동) 계수는 기본값 및 사용자 선택 가능.
주의: T(비생산)을 “실제 계획정지”라고 단정하는 것은 아니다. 시간만으로는 주말 정지와 긴 고장을 구분할 수 없다. 여기서 T(비생산)은 단지 시간 규칙상 아주 긴 비활성이라는 뜻이다.

5. 전체 시간은 반드시 한 번만 센다

T = T가동 + T비가동 + T비생산
T(미관측)는 통신 끊김처럼 “기계 상태를 알 수 없는 시간”이다.(시간 계산 요소에서 제외)
같은 1초를 두 상태에 동시에 넣지 않는다. 모든 시간은 T(기준), T(비가동), T(비생산), T(미관측) 중 하나에만 들어간다.

6. 시간 가용률 A시간

A시간 = T가동 / (T가동 + T비가동)
쉽게 말하면 “생산 대상으로 보고 있는 시간 중, 기준 범위 안에 있었던 시간 비율”.

7. 시간 성능률 P시간

P시간 = ΣRi / T가동 P시간 = R x CT개수(지정한만큼) / ΣCTi
Cycle 하나가 정상적으로 끝날 때마다 그 Cycle의 기준시간 R을 한 번 적립한다. 제품 수량은 세지 않는다.
예: R=10초이고 10 Cycle이 완료되면 기준 성과시간은 100초다. 이 10 Cycle의 실제 T(가동)가 120초라면 시간 성능은 약 83.3%다.
P시간가 100%를 넘을 수 있다. 이것은 오류가 아니라 “현재 Cycle이 기준 R보다 빠르다”는 뜻이다. 원시값은 100%에서 잘라내지 않는다.

8. 품질 Q

Q = 사용자 입력 양품률
예: 양품률 98.5% → Q=0.985. Q를 모르면 자동으로 1.0을 넣지 않는다.

9. OEE시간 — 생산 대상으로 본 시간 안에서의 효율

OEE시간 = A시간 × P시간 × Q
= Q × ΣRi / (T가동 + T비가동)
쉽게 말하면: 생산 대상으로 보고 있는 시간 안에서 “기준 리듬대로 Cycle을 얼마나 잘 반복했는가?”에 품질을 곱한 값이다.

10. TEEP시간 — 24/365 전체시간에서의 효율

U시간 = (T가동 + T비가동) / T
TEEP시간 = U시간 × OEE시간
= Q × ΣRi / T
TEEP생산 = T / (T생산 + T비생산)
가장 쉬운 해석: TEEP시간는 결국 “완료한 Cycle들이 벌어들인 기준시간의 합”을 전체 달력시간으로 나눈 뒤 Q를 곱한 값이다.
1년이라고 해서 무조건 24×365를 숫자로 박지 않는다. 생산 ct기준을 사용한다. 실제 구현에서는 평가 시작시각부터 종료시각까지의 실제 경과시간을 사용한다.

11. MT / WT — 설비가 왜 느린지 설명하는 보조 진단

실행 신호 E가 있으면 Cycle 안에서 “실제로 움직인 시간”과 “움직이지 않은 시간”을 나눠 볼 수 있다.

MTi = Cycle 안에서 실행 ON이었던 시간
WTi = CTi − MTi
CTi = WTi + MTi
E가 없어도 OEE시간/TEEP시간는 계산한다. E가 있으면 “Cycle이 느린 이유가 실행시간 증가인지, 비실행시간 증가인지”를 추가로 설명할 수 있다.
WT를 무조건 “실행 전 대기”라고 부르지 않는다. 설비는 실행→대기→실행 순서로 움직일 수도 있으므로 WT는 단순히 실행하지 않은 시간이다.

12. 비가동 이벤트 — 고장이라고 부르지 않는다

Fault/Alarm을 입력으로 쓰지 않으므로 “고장 발생”을 직접 알 수 없다. 대신 H(비가동)를 넘은 사실만 비가동(TO)로 기록한다.

TTR비가동

평균 비가동 지속시간

H(비가동)를 처음 넘은 순간부터 다음 유효 Cycle이 시작될 때까지의 평균.

TBF비가동

평균 비가동 발생간격

한 비가동가 시작된 시각부터 다음 비가동 시작까지의 평균.

금지: TTR비가동/TBF비가동를 실제 MTTR/MTBF라고 단정하지 않는다. 실제 고장 원인을 사용하지 않기 때문이다.

중요: 제품 혼류가 바뀌면 OEE시간가 바뀔 수 있다. 이것은 제품 정규화를 버린 대가다.

14. 데이터 때문에 생기는 대표 사례

6

Cycle 신호 하나를 놓침

자동 복원 금지
실제 10초+10초가 20초 한 Cycle로 보일 수 있다. 하지만 정말 20초 걸린 Cycle일 수도 있으므로 시스템이 마음대로 둘로 쪼개지 않는다.
7

Cycle 신호가 튀어서 두 번 들어옴

전처리 필요
0.05초짜리 가짜 Cycle이 생기면 기준 R도 오염될 수 있다. 수집단에서 기술적인 debounce/deglitch가 필요하다.
8

네트워크가 끊김

Heartbeat 필요
Cycle 신호가 안 오는 것만 보면 기계가 멈춘 건지 통신이 끊긴 건지 모른다. Heartbeat도 없으면 그 시간은 T(미관측)로 둔다.
9

하루 경계에서 Cycle이 걸쳐 있음

이전 시작시각 사용
23:59:58에 시작해서 00:00:06에 끝난 Cycle을 억지로 두 Cycle로 나누지 않는다. 다음 날 집계에는 이전 시작시각을 함께 가져와 정확한 CT를 계산한다.
10

처음 학습한 Cycle이 시운전이라 너무 느림

초기 기준 오염
잘못 잡힌 R은 이후 모든 KPI에 영향을 준다. 최근 R(최근)와 차이가 오래 유지되면 “기준 재검토” 경고를 낸다.

15. 시간만으로는 절대 확정할 수 없는 것

상황왜 못 아는가?스펙의 태도
주말 계획정지 vs 긴 고장둘 다 Cycle이 오랫동안 끝나지 않는 모습일 수 있음둘 다 장기 비활성으로만 표현. 원인 단정 금지.
느린 제품 vs 설비 성능저하제품코드/Recipe를 일부러 사용하지 않음Cycle 리듬 변화만 표현.
Cycle 신호 누락 vs 실제 장주기관측 결과가 똑같이 긴 CT로 보일 수 있음의심 경고는 가능, 자동 복원 금지.
1개 생산 vs 100개 Batch수량을 KPI 입력으로 사용하지 않음생산량 가치가 아니라 Cycle 시간 효율만 측정.
실제 고장 원인Fault/Alarm 정보를 사용하지 않음TO(비가동)만 기록.
최종 정직성 원칙: 이 모델은 원인을 맞히는 모델이 아니다. 제품과 고장정보가 없어도 동일한 시간 규칙으로 설비 리듬을 측정하는 모델이다.

16. 계산이 맞는지 확인하는 기본 규칙

① 시간은 뒤로 가지 않는다.
② 모든 시간은 T(가동)/T(비가동)/T(비생산)/T(미관측) 중 하나에만 들어간다.
③ Cycle이 끝나기 전에는 그 Cycle의 R을 성과로 미리 주지 않는다.
④ Q가 없으면 OEE(시간)/TEEP(시간)를 “미산출”로 둔다.
⑤ 통신이 끊겼는데 기계정지라고 가정하지 않는다.
⑥ 기준 R을 바꿔도 과거 KPI를 몰래 다시 계산하지 않는다.
⑦ A(시간)×P(시간)가 최종 시간효율과 맞는지 검산한다.
⑧ TEEP(시간) = Q×ΣR/T가 항상 맞는지 검산한다.

17. 최종 핵심식만 다시 보기

CTi = ci+1 − ci
R = median(과거 CT)
H비가동 = κ비가동R,   H비생산 = κ비생산R
A시간 = T가동/(T가동+T비가동)
P시간 = ΣR/T가동
OEE시간 = A시간P시간Q
TEEP시간 = QΣR/T
CT = WT + MT — 실행 신호가 있을 때만 사용하는 보조 진단
한 줄 결론: 완료한 Cycle마다 “기준시간 R만큼의 성과”를 적립하고, 실제로 흘러간 시간과 비교해 OEE시간/TEEP시간를 계산한다.

κ_D비가동 시작 경계최종 숫자 확정
κ_N장기 비활성 시작 경계최종 숫자 확정
이 세 값은 현장 사용자가 매번 입력하는 값이 아니다. 소프트웨어 스펙 버전에 고정되는 공통 상수다. 값이 바뀌면 같은 알고리즘이 아니므로 스펙 버전도 바꾼다.
제품을 맞히는 알고리즘이 아니라, 설비의 시간 리듬을 같은 기준으로 재는 알고리즘

사용자가 시간 구간을 정하면 그 안의 유효한 CT를 기준으로 계산한다.
CT는 필수인 HEAD를 기준으로 하고 그 안에서 실측 데이터로 정렬해서 CT를 구한다.( head - head 사이가 ct) tail은 선택으로, 사용자가 mt와 wt를 구분해서 보고 싶을때 사용. mt wt는 oee, teep등에 계산요소가 아니다.
work의 경우를 비가동 판별로 사용. work별 샘플 중앙값x 계수를 넘으면 비가동, 비생산 기준 넘으면 비생산 처리.
T(미관측)의 경우 계산 요소에 들어가지 않는다. 크게 T = T(가동) + T(비가동) + T(비생산) 이다.
