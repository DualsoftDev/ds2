# OEE 정지 구성(가동·고장·유지보수·비생산) 뷰 간 불일치 진단

- 날짜: 2026-07-06
- 데이터 소스: 라이브 dev 인스턴스 `http://localhost:58494` (`/api/oee/summary`, `/downtime`, `/daily`, `/plan-time`)
- 범위: 최근 14일 및 일자별 스캔
- 결론: **버그가 아니라 구조적 문제.** 같은 정지를 세 화면이 *서로 다른 데이터 소스 · 다른 분모 · 다른 분류 기준*으로 계산하고 있어, 같은 사건이 화면마다 완전히 다른 퍼센트로 표시된다.
- 제약: 향후 통일 시 **가용성 A KPI 절대값은 보존**(사용자 확정).

## 0. 한 줄 재현 — "하루 유지보수 84%"

**2026-07-06 (오늘) 한 개 날짜**를, 같은 API로, 세 뷰로 계산한 결과:

| 뷰 | 유지보수 표시 | 근거 |
|---|---|---|
| ③ 정지 구성 도넛 | **84 %** | 정지 이벤트 durationΣ 중 유지보수(isFailure=0) 비중 |
| ① 시간별/일자별 추이 | **≈ 0 %** | 벽시계 하루에서 유지보수 세그먼트가 사실상 안 보임 |
| ② 가용성 누적 정산 | **A = 85 %** (유지보수 개념이 분모에 거의 안 들어옴) | 사이클 ΣCT 기반, 유지보수 귀속분 극소 |

사용자가 본 "하루 84%"는 **③ 도넛의 값**이며, 정확히 재현된다. 문제는 그 84%가 나머지 두 화면 어디에도 나타나지 않는다는 것.

## 1. 세 뷰는 사실 서로 다른 3개의 계산이다

| | ① 시간별/일자별 추이 | ② 가용성 누적 정산 (availComp) | ③ 정지 구성 도넛 (faultDist) |
|---|---|---|---|
| 엔드포인트 | `/api/oee/daily` → `BuildDailySlot` | `/api/oee/summary` (cycle 모드) | `/api/oee/downtime` (이벤트 로그) |
| **데이터 소스** | 정지 **이벤트 로그** 구간 | **사이클 ΣCT** (MT>이상치 룰) | 정지 **이벤트 로그** durationMs |
| **분모** | **벽시계** (슬롯 1시간/1일) | **Σ실측CT + Σ비가동CT** (사이클 시간, flow 합산) | **총 정지 이벤트 시간**(중첩·다flow 합) |
| **고장/유지보수 분류** | kind 기반 (고장=failure+unclass, 유보=planned+other) | idle ΣCT ∩ 유지보수 이벤트구간(`idleMaintCtMs`), 잔여=고장 | 이벤트별 `isFailure` 플래그 직접 |

| **미계측(수신공백)** | 별도 회색 세그먼트 | 캘린더에서 카빙 | 개념 없음 |
| **"가동"의 정의** | 벽시계 **잔여**(정지·비생산·미계측을 뺀 나머지) | **실측 Σ정상CT** (실제 사이클) | (없음) |

## 4. 근본 원인 (3개 축)

### 축 1 — 분모가 셋 다 다르다
- ① 벽시계 슬롯, ② 사이클 ΣCT(flow 합산, 14일에 1,770h), ③ 총 정지 durationΣ(중첩 합).
- 같은 30분 유지보수라도 ①은 "그 시간의 %", ②는 "사이클 시간의 %", ③은 "총 정지의 %"로, 물리적으로 다른 값이 나온다.

### 축 2 — "정지"의 출처가 근본적으로 두 갈래다 (가장 큰 원인)
- **② 가용성의 "비가동"**은 *사이클 ΣCT 룰*에서 파생(동작시간>이상치 / 미완료 폭주 / 무가동). 정지 이벤트 로그를 안 본다.
- **①·③의 "정지"**는 *정지 이벤트 로그*(nocycle / fault-bit / 수동)에서 파생.
- 두 소스는 `idleMaintCtMs`(비가동 ΣCT ∩ 유지보수 이벤트구간 교집합) 하나로만 이어붙어 있다([OeeControllerBase.cs:783](../DSPilot/Controllers/OeeControllerBase.cs#L783)). 교집합이 8.3h밖에 안 되니 이벤트 로그의 유지보수 401h가 가용성에 거의 반영되지 않는다.

### 축 3 — 긴 정지가 "유지보수"냐 "비생산"이냐가 뷰마다 갈린다
- ① 추이는 `BuildDailySlot`에서 비생산(10×CT)을 **먼저 차집합**하고 예산 상한(Take)으로 잘라내므로, 유지보수 이벤트 구간이 비생산·잔여가동에 흡수되어 0.7h로 사라진다([OeeControllerBase.cs:355-363](../DSPilot/Controllers/OeeControllerBase.cs#L355)).
- ② 가용성은 긴 정지를 10×CT 비생산으로 분리해 A 분모에서 통째로 뺀다.
- ③ 도넛은 비생산 개념 자체가 없어 그 긴 정지를 전부 "유지보수/고장"으로 셈한다.
- → 같은 물리적 긴 정지가 ①에선 비생산, ②에선 분모 밖, ③에선 유지보수로 3가지로 계상된다.

## 5. 판정

"유지보수 84%인데 다른 데선 없다/이상하다"는 **데이터·표시 버그가 아니라 세 계산이 서로 다른 질문에 답하고 있기 때문**이다. 직관적이지도, 설명 가능하지도 않은 것이 구조상 당연하다. 통일하지 않는 한 세 화면의 숫자는 계속 어긋난다.

## 6. 통일 방향 (다음 단계 — 본 문서는 진단만, 착수 전 승인 대기)

원칙: **정지 분류의 단일 소스(SSOT)를 두고, 뷰는 그것을 다른 분모로 렌더만 한다. 단 A 절대값은 보존.**

- **SSOT 후보 = 정지 이벤트 로그의 4상태 구간**(가동/고장/유지보수/비생산 + 미계측). 지금 `BuildDailySlot`의 4분해를 정본으로 승격.
- **③ 도넛**을 SSOT의 고장/유지보수 벽시계 합으로 재정의 → 추이 스택 정지부와 자동 일치. (도넛의 다flow duration 중첩 합산 폐기 = 큰 착시 제거.)
- **② 가용성**은 A 값 보존 제약에 따라 **분모 산식(사이클 ΣCT)은 유지**하되, 화면의 고장/유지보수 **분해 표시만** SSOT 구간을 벽시계로 겹쳐 귀속하는 방식으로 교체 → 라벨/비율은 ①·③과 정합, A 숫자는 불변.
- **비생산·미계측**은 세 뷰 공통으로 "가동성 분모 밖" 규칙 하나로 통일.

기대 효과: "추이 스택을 세로로 합치면 가용성 정산, 정지 부분만 떼면 도넛"이라는 한 문장으로 설명 가능.

## 8. 구현 완료 (2026-07-06)

§7 설계대로 구현. 테스트 187/187 통과, 라이브 재대조로 3뷰 일치 확인.

### 변경 요약
- **OeeMath**: `ComputeWallClockAvailability(run, available)` 추가(A = 가동 ÷ 생산가능). `ComputeCycleAvailability`는 TEEP 매트릭스·테스트용으로만 존치.
- **ResolvePlannedWindowsAsync**: 비생산 = 지정만. auto → 14일 학습패턴 창(`OeeNonProdPatternService`, 당일 제외), manual → 지정 창. **당일 10×CT 적용(applyLongStop) 항상 false** (KPI 경로). 호출부 5곳 async 교체.
- **ComputeCycleAggregateAsync**: flow별 벽시계 산출 추가 — 생산가능(=기간−비생산−미계측) 창에서 가동(정상 사이클 ∩ 생산가능), 비가동(생산가능−가동 잔여), 유지보수(비가동 ∩ 유지보수 이벤트). `RunWallMs/AvailableWallMs/DownMaintWallMs` + concat 구간(`RunWallIntervals/DownMaintWallIntervals`) 반환. 라인=flow 합산.
- **BuildSummaryAsync**: A = 벽시계(`availabilitySource="wallclock"`). DTO에 `RunWallMs/AvailableWallMs/DownMaintWallMs` 추가.
- **Daily**: 슬롯별 [가동/고장/유지보수/비생산/미계측] flow 합산(가동·유지보수=concat SumOverlap, 비생산·미계측=전역×flow수, 비가동=잔여). 구 `BuildDailySlot`(이벤트로그 kind 예산배분) 제거.
- **프론트**: `availComp` 단일 벽시계 모드, `faultDist` 도넛 = 서버 비가동 고장/유지보수(다-flow 중첩합·open 추정 폐기), `uptime-oee.html` 칩/노트/단위경고 갱신(세 카드 동일 단위 명시).

### 라이브 재대조 (일자별 — 3뷰 일치 확인)
```
day     도넛유보%  추이유보h  추이가동h | A     fault/maint h
06-26    100%      13.6      94.3     | 87%   0.0/13.6   ← 도넛=추이=정산 모두 유보 13.6h
07-06      0%       0.0      32.5     | 38%   54.0/0.0   ← 신고 케이스: 84%→고장 54h로 통일, 3뷰 0% 유보
```
- 추이 유지보수h = availComp maint h, 추이 가동h = availComp run h, 도넛 유보% = maint/(fault+maint) — 전 날짜 일치.
- 07-06 "유지보수 84%"(구 도넛 착시)는 소멸 — 실제로는 고장 54h(A=38%)이며 세 뷰가 동일하게 표기.
- 06-26 유지보수 396.5h(구 다-flow 중첩합) → 13.6h(실제 벽시계)로 정상화.

### 알려진 함의(설계상 수용)
- 10×CT 폐지로, **지정 비생산(계획/14일 학습)에 없는 실제 off-time은 비가동으로 잡혀 A가 낮아진다**(예: dev 06-27/28 종일 정지 → A=0%). 정직한 결과이며, 계획 비생산 스케줄을 채우거나 학습 데이터가 쌓이면 해소. 프로덕션(상시 데이터)에선 학습 패턴이 주말/야간을 승격.
- TEEP 매트릭스 셀 A는 여전히 `ComputeCycleAvailability`(사이클 기반) — 별 탭(생산효율)이라 이번 통일 범위 밖. 필요 시 후속.

### 열린 질문 (통일 착수 시 결정 필요) — §7에서 확정됨
1. ② 가용성 분모(사이클 ΣCT)와 ①③ 벽시계 분모는 A 보존 제약상 계속 다르다 — 화면에 "분모가 다름"을 명시할지, 아니면 ②를 벽시계 참고값으로 병기할지.
2. 도넛의 다flow 중첩을 union(벽시계)으로 접을지, flow별로 쪼갤지.
3. SSOT 4분해의 예산 상한(Take) 우선순위를 그대로 정본화할지 재검토할지.

## 7. 확정 설계 (2026-07-06 결정) — 벽시계 단일 타임라인

### 7.0 확정된 정책 결정
| 항목 | 결정 |
|---|---|
| **A 재정의** | **푼다.** A = 가동 ÷ 생산가능시간 (벽시계). 기존 사이클 ΣCT 분모 폐기. A 절대값 변경 허용. |
| **비생산 정의** | **지정된 것만** — 계획 창(`ExpandPlannedIntervalsMs`) + 14일 학습 패턴(참고 아닌 정본). **자동 10×CT 룰 폐지.** |
| **라인(다-Flow) 합산** | **Flow별 A의 생산가능시간 가중평균** = `Σ가동 ÷ Σ생산가능시간`. (단순평균이 아니라 가중 — 이래야 도넛·추이의 시간 합산과 A가 수학적으로 정합. 단순평균은 정합 깨짐.) |

### 7.1 단일 타임라인 (SSOT) — flow별 벽시계 구간
```
캘린더_f
 ├─ 비생산_f   = 계획창 ∪ 14일 학습패턴           (당일 데이터 안 씀)
 ├─ 미계측_f   = 수신 공백(§3.4)                   (분모 밖, 회색)
 └─ 생산가능_f = 캘린더 − 비생산 − 미계측
      ├─ 가동_f   = 정상 사이클 구간(runIntervals) ∩ 생산가능
      └─ 비가동_f = 생산가능 − 가동                 (잔여 = 전부 정지)
             ├─ 고장     ← 기본값
             └─ 유지보수 ← 정지 이벤트(isFailure=0) 구간과 겹친 부분만
```
- **비가동 = 생산가능 − 가동(잔여)** 로 정의 → 타일링 완전(구멍/이중계상 없음). 짧은 사이클 간 정지도 비가동에 포함(사용자 모델: "가동 아니면 비가동"). 속도손실은 P가 별도로 잡음.
- "동작시간>이상치" 판정([dtCond](../DSPilot/Controllers/OeeControllerBase.cs#L689))은 **어느 구간이 가동/비가동인지 알아내는 용도로 계속 사용**(runIntervals·idleCalUnion 산출). 바뀌는 건 **A 분모를 사이클 ΣCT → 벽시계**로.

### 7.2 지표 산식
- `생산가능_f`, `가동_f`, `비가동_f(=고장_f+유지보수_f)` — 전부 벽시계 ms.
- `A_f = 가동_f / 생산가능_f`
- **라인 A = Σ가동_f / Σ생산가능_f** (가중평균)
- **P(성능)** = 기존 사이클 기반 유지(`Σ정상Ct·thr` / 가동) — A와 별개 축. 변경 없음.
- **Q(품질)** = 기존 수기/불량 입력 유지. 변경 없음.
- `OEE = A × P × Q`.

### 7.3 세 뷰는 이 타임라인 하나에서 파생
- **① 추이**: 시간대별 `[비생산 / 가동 / 고장 / 유지보수 / 미계측]` 벽시계 스택 — 지금 `BuildDailySlot`을 정본으로 승격(단, 10×CT 비생산 입력 제거, 비가동=잔여로 재정의).
- **② 가용성 정산**: 같은 구간 합계 — `A = 가동/(가동+비가동)`, 비가동을 고장/유지보수로 분해. **①의 세로 합 = ②**.
- **③ 도넛**: 비가동의 고장/유지보수 벽시계 합(flow 합산, 중첩 union). **②의 비가동 분해 = ③**. 다-flow duration 중첩합·open 이벤트 추정 폐기.

## 9. 정책 개정 (2026-07-08) — 비생산 = 당일 판정 + 사용자 오버라이드

§7 의 "비생산=지정만(계획창/14일 학습, 당일 데이터 미사용)"을 개정한다. 근거(오너 결정): 14일 학습창이
사용자 생산 패턴(불규칙 휴무·스케줄 변경)을 모두 대응할 수 없고, 비가동/비생산 경계가 다소 어긋나도
**의미상 당일 판단이 더 맞으며**, 당일 실측 파티션은 TEEP(캘린더 분모)와 정합된다. 7/6 기각의 최대 근거였던
블랙아웃 흡수는 §3.4 미계측 분리(P0)가 이미 구조적으로 제거했다.

- **병행 모델(같은 날 후속 확정)** — 당일 10×CT 장시간 정지 판정은 **항상 켜짐**(`applyLongStop=true` 상시), 수동
  지정 시간대(PlannedStops)는 **추가로 "무조건 비생산"으로 자르는 보조 규칙**(창 안=가동/정지 불문 지표 밖).
  구 자동/수동 배타 토글(PlannedStopsAuto, POST planned-stops/auto) 폐기 — "점심만 추가"가 "점심 빼고 전부
  고장으로 봐라"가 되는 함정 제거. Source=auto|both. 14일 학습창의 KPI 적용은 폐기(auto-pattern 참고 존치).
  수동 지정의 존재 이유 = 느린 CT 설비(임계=10×CT 가 커서 점심도 미승격)·임계 미만 반복 짧은 휴게.
  UI = 통합 24h 타임라인 한 트랙에 자동 인식(점선)+수동 지정(남색 솔리드, 겹침은 차집합으로 남색 우선) 구분
  표시, [수동 추가] 버튼 → 편집 모드(드래그 생성/이동/조절, [적용] 저장).
- **사용자 오버라이드(신규)** — 정지 이벤트 로그 팝업을 [비가동]/[비생산] 탭으로 분리(한 테이블 혼합 금지,
  보내기 성공 시 대상 탭 자동 이동) + 행별 [→ 비생산]/[→ 비가동] 버튼. **왕복 분류 보존**: 비생산으로 보낼 때
  이전 비가동 분류(유지보수 등)를 prev*(prevReasonCode/prevCategory/prevIsFailure) 컬럼에 스태시, 비가동 복귀
  시 복원(스태시 없으면 기본 고장) — 유지보수→비생산→비가동 = 유지보수 유지.
  `POST /api/oee/downtime/reclassify` 가 `classifySource='manual'` + `reasonCode='non_production'`(또는 고장)으로 확정하고,
  `ComputeCycleAggregateAsync` 가 이를 양방향 우선 적용(비생산 강제 카빙 / 자동 승격 억제). 기존 고장/유지보수
  체크(수동 분류)도 자동으로 '비가동 확정' 오버라이드가 된다(호환). 합성 행(over-cycle)은 reclassify 시
  실제 이벤트 행으로 materialize. '비가동으로 보내기' 시 겹치는 자동 감지 로그(oeeNonProdDetectionLog) 청소.
- **집계 2-패스** — 비생산(지정 창+당일 승격+오버라이드)이 루프에서 확정된 뒤 생산가능 창·flow별 가동/비가동
  벽시계를 산출 → 승격된 비생산이 벽시계 A 분모에서도 빠진다(§7 도입 당시엔 applyLongStop=false 라 무관했던 지점).
- **정지 구성(도넛) = 고장/유지보수/비생산 3분할** — `NonProdWallMs`(기간 클립·미계측 차감 ×flow수) 추가.
  비생산 분류 이벤트는 정지 KPI(기간 정지·순위·MTBF 계열)에서 제외.
- **'생산 요일(휴무)' 기능 제거** — UI·API(`PUT planned-stops/excluded-weekdays`)·설정(`ExcludedWeekdays`)·분모 주입
  전부 삭제. 쉬는 날은 사이클이 없어 당일 10×CT 규칙이 자동으로 비생산 처리(기존 설정 키는 ExtensionData 로 무해 보존).
- 3뷰 항등식(§7.3)은 유지 — 파티션 정의만 바뀌고 추이·정산·도넛은 여전히 한 타임라인에서 파생.
- `ComputeCycleAggregateAsync`: 자동 10×CT 분기(`IsLongStopNonProduction`) 제거, 벽시계 `생산가능/가동/비가동` 구간 산출 추가. `normalCtMs`는 P용으로 존치.
- `BuildSummaryAsync`: A 산식을 벽시계로 교체(사이클 ΣCT 분모 제거). `availabilitySource` 폴백 체인(shift/auto/calendar) 정리 — 벽시계 A는 계획 비생산 스케줄이 곧 분모라 폴백 단순화.
- `availComp`(JS): cycle/fallback 2모드 → 단일 벽시계 모드.
- `faultDist`(JS 도넛): `this.downtime` duration합 → 서버가 주는 비가동 고장/유지보수 벽시계 합 사용.
- `BuildDailySlot`: 비생산=지정만, 비가동=잔여로 재정의. Take 우선순위 단순화.
- **폐기**: `IsLongStopNonProduction`(10× 룰) 및 관련 감지 로그 materialize, `idleMaintCtMs` 임시 교집합(→ 정식 분류로 승격), OeeMath 관련 테스트 갱신.
- **리스크**: 계획 비생산 창이 부실하면(주말/야간 미등록) A 폭락 → 14일 학습 패턴을 정본 폴백으로 자동 적용해 완화.
