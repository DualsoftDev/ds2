## Backend: Cycle/Flow analysis services
**Purpose:** Server-side computation behind the static cycle-time-analysis and flow/dashboard pages — detecting cycle boundaries from raw PLC rising edges, deriving per-cycle MT/WT/CT, tracking live Flow metrics, and rendering Gantt SVG/Excel exports. It is the bridge between the SQLite PLC log + F# Ds2.Core domain and the Alpine/Chart.js frontend.

**Files & roles:**
- DSPilot/Services/CycleAnalysisService.cs (1231) — God class: flow lookup, IO-event→Gantt building, signal-segment timeline building, lane assignment, plus a whole unused gap/device/bottleneck analysis subsystem. Also hosts the public `GanttChartData`/`GanttChartItem` DTOs.
- DSPilot/Services/FlowMetricsService.cs (602) — Live MT/WT/CT cycle-state machine (`OnCallGoingStarted`/`OnCallFinished`), boundary resolution, running-average accumulators, DB writes + history insert.
- DSPilot/Services/IFlowMetricsService.cs (58) — Interface for the above (only partially honored; see smell #4).
- DSPilot/Services/CycleTimeChartExporter.cs (575) — WYSIWYG Excel (.xlsx) + CSV exporter from the client-supplied `CycleExcelModel`; owns its own span/idle math.
- DSPilot/Services/CycleTimeChartRenderer.cs (245) — Static SVG-string Gantt builder (Blazor-era; see smell #6).
- DSPilot/Services/CycleRecomputeService.cs (350) — Background job re-deriving `dspFlowHistory` from raw edges on boundary change; well-factored, the model the others should follow.
- DSPilot/Services/CycleDerivation.cs (101) — Pure functions for edge→cycle decomposition + averages; shared by recompute + CallTestController. The one clean, testable seam.
- DSPilot/Services/FlowAnalysis/FlowAnalyzer.cs (257) — Pure C# DAG analysis (rep-work, Head/Tail, cycle detection) ported from F#.
- DSPilot/Services/Statistics/CallStatisticsTracker.cs (112) — Sliding-window per-Call stats tracker. **Dead code** (no DI registration, no caller).

9. **[LOW] Polarity convention duplicated as scattered comments, not a named constant** — DSPilot/Services/CycleAnalysisService.cs:68,364,482,1004-1010; CycleRecomputeService.cs:257; CycleDerivation.cs:14-18. The healthy core is the pure, shared `CycleDerivation` + the well-structured `CycleRecomputeService`; those are the pattern to extend. ## Backend: Simulation engine + DB lifecycle services
**Purpose:** Hosts the live monitoring pipeline — the F# Ds2.Runtime engine (passive inference of Work/Call states from PLC tag signals), Welford cycle-time statistics, the in-memory dashboard snapshot fed to SignalR/Blazor, and the in-place lifecycle (AASX reload, DB rebuild, cache invalidation) that lets all of the above re-initialize without a server restart.

**Files & roles:**
- DSPilot/Services/SimulationEngineService.cs (821) — God service: wraps the F# EventDrivenEngine + RuntimeModeSession + PassiveInference, owns Welford stats, raw SQLite plcTag bootstrap, flow-sync debounce, event channel consumer, and engine teardown/reset.
- DSPilot/Services/DspDbService.cs (664) — Polls plc.db every 1s + 300ms progress timer, maintains the in-memory `DspDbSnapshot`, merges event-channel patches, computes progress rate, and exposes `OnDataChanged`/`OnStructuralChange`.
- DSPilot/Services/DatabaseLifecycleService.cs (424) — Orchestrates the four reset flavors (InvalidateCaches / RebuildDatabase / ReloadAasx / ReloadAndResync) behind a single `SemaphoreSlim` gate.
- DSPilot/Services/DsProjectService.cs (216) — Owns the singleton F# `DsStore`, AASX load + SHA256, and thin C# wrappers over `Queries.*`.
- DSPilot/Services/AasxFileWatcherService.cs (279) — FileSystemWatcher (SHA256-debounced) that auto-triggers lifecycle reload/resync on external AASX changes.
- DSPilot/Services/PlcDatabaseMonitorService.cs (208) — Alternate polling-based tag-change detector that broadcasts `CallStateChanged` over SignalR directly.
- DSPilot/Services/DemoModeService.cs (68) — 3h demo gate + `.demo-bypass` marker file.
- DSPilot/Services/IDatabasePathResolver.cs (35) — DB-path abstraction (unified vs split).
- DSPilot/Services/ThemeService.cs (29) — Scoped dark/light toggle.
- DSPilot/Services/DashboardEditService.cs (13) — Scoped edit-mode toggle flag.

**Key smells (ranked, worst first):**

1. **[HIGH] God class with 7+ mixed concerns** — DSPilot/Services/SimulationEngineService.cs:27-821 — One class owns engine lifecycle, raw SQLite DDL/DML (`BootstrapPlcTags`, `SeedCallStatsFromDb`), Welford math, flow-state debouncing, an event-channel consumer, and per-event DB+SignalR fan-out. `HandleCallStateChangeAsync` (592-684) alone does 5 numbered steps across three subsystems. Refactor: extract `CallStatsAccumulator` (Welford + seed, 365-409/686-718), `PlcTagRegistrar` (the SQLite bootstrap/register code, 231-363), and a `FlowSyncDebouncer` (416-465) as collaborators; leave SimulationEngineService as a thin coordinator.

2. **[HIGH] Leaky abstraction — consumers cast to / depend on concrete `DspRepositoryAdapter`** — DSPilot/Services/SimulationEngineService.cs:640 and DSPilot/Services/DatabaseLifecycleService.cs:68,77,168,262,289,334,389,392 — `IDspRepository` (Repositories/IDspRepository.cs:9-92) declares none of `SyncFlowStateAsync`, `InvalidateRunningStatsAsync`, `RecomputeAveragesFromCurrentBoundaryAsync`, `PruneByFlowNamesAsync`, `InsertAasxChangeLogAsync`, `GetAllFlowNamesAsync`, `ClearFlowHistoryAsync`, `ResetCallStatisticsAsync`; the engine does a runtime `is Adapters.DspRepositoryAdapter repo` cast. The interface is effectively dead for these paths. Refactor: promote the lifecycle/sync methods onto `IDspRepository` (or a focused `IDspMaintenanceRepository`) and inject that concrete type explicitly, deleting the cast.

3. **[HIGH] Raw SQLite/DDL embedded in an engine service (leaky layering + duplication)** — DSPilot/Services/SimulationEngineService.cs:231-300, 308-363, 371-409 — Hand-built `SqliteConnection`/`conn.Execute`/`conn.Query` and an identical `INSERT INTO plcTag … ON CONFLICT(address) DO NOTHING` block appears twice (272-277 and 338-343); this is data-access that belongs behind a repository and contradicts the Repositories/* layering used elsewhere. Refactor: move plcTag upsert+cache-load and the call-stats seed query into a `PlcTagRepository`/`IDspRepository` method; the engine consumes typed results only.

4. **[MED] `DspDbService.TryRefresh` is a 200-line method with manual ADO and three overlapping merge passes** — DSPilot/Services/DspDbService.cs:381-585 — Hand-rolled `ExecuteReader` column mapping (412-457), then three sequential O(N) rebuild loops (going-progress seed 465-491, GoingCount-protection 500-525, change-detection + flow-hold 527-563), each allocating fresh immutable `CallState`/`FlowState` records. Hard to test and easy to break when a column changes. Refactor: replace the two readers with Dapper (already a dependency, used in SimulationEngineService) into DTOs, then extract `MergeProgress`, `ProtectGoingCount`, and `DetectChanges` private methods.

5. **[MED] Pervasive immutable-record clone-with-one-field-changed duplication** — DSPilot/Services/DspDbService.cs:148-161, 177-190, 269-285, 345-358, 509-522, 552-560, 614-622 — The same ~12-property `new CallState { … }` / `new FlowState { … }` copy appears seven times because the models lack `with`-expression support / copy helpers. Refactor: make `CallState`/`FlowState` C# `record` (or add `With(...)` mutators) so call sites become `call with { ProgressRate = x }`, eliminating ~80 lines of error-prone field-by-field copies.

6. **[MED] Vestigial split-mode abstraction (dead branch + dead config)** — DSPilot/Services/IDatabasePathResolver.cs:8-35, DSPilot/Adapters/DatabasePathResolverAdapter.cs:15-28, DSPilot/Services/DspDbService.cs:18-20,67-71 — `IsUnified` is hardcoded `true` and all three path getters return the same shared path; `DspDbService`'s `_flowTable`/`_callTable` "split mode" fields (commented "Flow/Call in split mode") are always `dspFlow`/`dspCall`. The split-mode concept is documented everywhere but unreachable. Refactor: collapse to a single `string SharedDbPath` (or keep one resolver method), delete `IsUnified`/`GetPlcDbPath`/`GetDspDbPath` and the table-name fields, removing misleading dead surface area.

7. **[MED] Two competing tag-change → CallState pipelines with contradictory polarity** — DSPilot/Services/PlcDatabaseMonitorService.cs:100-192 vs DSPilot/Services/SimulationEngineService.cs:181-222 — Both are registered (Program.cs:121,131). The monitor service polls plcTagLog and broadcasts `CallStateChanged` with its own edge→state mapping (157-166: InTag rising="Done", OutTag rising="Going"), while the engine path infers state via F# PassiveInference; the project's own memory notes this InTag/OutTag polarity is contradictory between the live engine and analysis. Maintaining two sources of truth for the same event is a correctness-and-maintenance hazard. Refactor: confirm which path is authoritative (engine/hub) and either delete `PlcDatabaseMonitorService` or demote it to a pure plcTagLog ingester with no `CallStateChanged` broadcast and no embedded polarity logic.

8. **[MED] Four near-duplicate lifecycle methods with copy-pasted boilerplate** — DSPilot/Services/DatabaseLifecycleService.cs:58-113, 123-201, 208-242, 249-372, 379-421 — Each public method repeats the same `_gate.WaitAsync(0)`/try/finally/`RebuildResult`/`SendAsync("DatabaseRebuilt")`/`_dspDbService.Reset()` scaffold; the AASX-load-failure check and audit-log try/catch are copied verbatim. Refactor: extract a private `RunGatedAsync(string op, Func<Task<RebuildResult>> body)` wrapper for the gate+try/catch+logging, and helpers `BroadcastRebuilt()` / `SafeInsertAuditLog(...)`, shrinking each method to its unique steps.

9. **[MED] Hidden fire-and-forget continuation chains for flow-state debounce** — DSPilot/Services/SimulationEngineService.cs:416-465 — `Task.Delay(...).ContinueWith(async _ => …)` with manual CTS bookkeeping in a `Dictionary` guarded by a separate lock; the `async` lambda inside `ContinueWith` returns a discarded `Task` (unobserved). This is brittle and untestable. Refactor: replace with an `await Task.Delay(token)` debounce helper (or a small `Debouncer` utility shared with AasxFileWatcherService's identical pattern at 86-111), and drop `ContinueWith`.

10. **[LOW] Duplicated debounce + DI-via-`IServiceProvider` service-locator in the watcher** — DSPilot/Services/AasxFileWatcherService.cs:86-111, 139, 179, 224 — The CTS-debounce block duplicates the engine's pattern (#9), and the watcher resolves `DatabaseLifecycleService`/`BlueprintService` through `_services.GetRequiredService<>()` (service locator) rather than constructor injection. Refactor: inject the dependencies directly (no captive-dependency risk since both are singleton/transient here) and share the extracted `Debouncer`.

11. **[LOW] `DsProjectService.GetAllCalls` triple-nested N+1 query walk** — DSPilot/Services/DsProjectService.cs:159-171 — Iterates all flows → all works → all calls calling `Queries.*` repeatedly; fine at current scale but a latent hotspot and obscures intent. Refactor: add a single `Queries.allCalls(store)` to the F# side (or memoize), keeping the C# wrapper a one-liner.

12. **[LOW] Engine event handlers reference Promaker/version jargon and dead-code comments** — DSPilot/Services/SimulationEngineService.cs:130,162,503,511 — Comments like "v12 P4 / P5 … SignalHub 발행으로 sink 교체" and the empty `WriteTag` switch case (503) document intentions not in code; mild TODO debt. Refactor: convert lingering "P5 예정" notes to tracked issues and remove the no-op comment-only switch arm.

**Overall assessment:** The subsystem works and is unusually well-commented about *why* (race fixes, debounce rationale, restart continuity), but its maintainability is dragged down by two oversized God classes (`SimulationEngineService`, `DspDbService`) that mix engine orchestration, raw SQLite data-access, statistics math, and snapshot merging in single 600–800-line files, plus an `IDspRepository`/`IDatabasePathResolver` abstraction layer that no longer abstracts anything (concrete casts, hardcoded unified mode, dead split-mode branches). The single most valuable refactor is #2/#3 combined: pull all hand-written SQLite out of `SimulationEngineService` into the repository and make `IDspRepository` actually expose the methods its consumers call — this removes the leaky concrete cast, eliminates the duplicated plcTag upsert, and is the prerequisite that makes the God-class decomposition (#1) and `TryRefresh` cleanup (#4) safe and testable.

- DSPilot/Services/PlcTagLogWriterService.cs (142) — `BackgroundService` batching `plcTagLog` INSERTs via an unbounded channel with drop-tracking.
- DSPilot/Services/PlcIoDataService.cs (105) — thin async wrapper over `IPlcRepository` for tag-history queries.
- DSPilot/Services/PlcConnectionStatusTracker.cs (80) — singleton cache of per-adapter PLC connection status fed by the SignalR hub subscriber.
- DSPilot/Services/OeeUserTagPollerService.cs (389) — `BackgroundService` deriving OEE downtime onset/clear, cause classification, and production/reject counts from UserTag time-series; includes nested static `OeeCounterDelta`.

**Key smells (ranked, worst first):**

1. **[HIGH] Leaky layering — raw SQLite access scattered across "service" classes** — PlcDebugService.cs:80-393 (all queries) and OeeDowntimeStateMachine.cs:155-206 (`ReadLastCyclePerFlowAsync`). These services hand-build connection strings, write SQL, parse readers, and own bespoke datetime parsing — yet a `Repositories/` layer (`IPlcRepository`) and `Infrastructure/SqliteDateTimeHelpers` already exist, and the peer `OeeUserTagPollerService` correctly goes through `IPlcRepository` edge/range methods. Data access concerns belong in repositories. Refactor: move `PlcDebugService`'s 5 queries into a `IPlcDebugRepository` (or extend `IPlcRepository`) and `ReadLastCyclePerFlowAsync` into `IPlcRepository` / a `dspFlowHistory` repo; leave the services as orchestration only.

Refactor: a single `SqliteConnectionFactory.OpenReadOnly(path)` / `OpenReadWrite(path)` helper in `Infrastructure/`, used everywhere a raw connection is still needed.

3. **[HIGH] Duplicated DateTime parsing/formatting with three conflicting conventions** — PlcDebugService.cs:262-282 (`ToSqliteDateTime`/`ParseSqliteDateTime`, local-time roundtrip), OeeDowntimeStateMachine.cs:198-206 (`ParseRecordedAt`, `TrimEnd('Z')` + AssumeUniversal), vs the shared SqliteDateTimeHelpers.cs:13-29. Refactor: consolidate to one helper module with explicitly named variants (e.g. `ParseUtcNoSuffix` vs `ParseLocalRoundtrip`) and delete the private copies, so the convention is documented in one place.

4. **[MED] `BackgroundService` poller skeleton duplicated 4×** — OeeUserTagPollerService.cs:79-101, OeeDowntimeStateMachine.cs:59-79, UserTagAlertService.cs:86-120, UserTagAlertAggregationService.cs:27-45 all repeat the same `LogInformation(start) → StartupDelay → while(!cancelled){ try Tick; catch log; Delay }` pattern, each with its own const `PollInterval`/`StartupDelay` and try/catch shape. Refactor: extract a small `PeriodicPollerBase : BackgroundService` (template method `TickAsync`, configurable interval/startup/error policy); subclasses implement only the tick body. Behavior-preserving and shrinks each file noticeably.

5. **[MED] `BuildFlowSystemMap` copy-pasted verbatim across the two OEE state machines** — OeeUserTagPollerService.cs:286-301 and OeeDowntimeStateMachine.cs:209-224 are byte-for-byte identical except the log prefix. Refactor: move to a shared `FlowSystemResolver`/extension on `DsProjectService` (the natural owner of flow→system resolution) and inject it into both pollers.

6. **[MED] `ProcessFaultBitsAsync` is an overlong, deeply-nested method mixing 4 concerns** — OeeUserTagPollerService.cs:135-202 handles fault-address normalization, system-name resolution, onset insertion+logging, and clear matching in one ~70-line method with foreach-in-foreach + per-edge awaits. Refactor: split into `DetectFaultOnsets` and `ClearOpenFaults`, and pull address normalization into a tiny helper; keeps each unit independently readable/testable.

7. **[MED] Per-row sequential DB INSERT inside the poll loop** — UserTagAlertService.cs:300-321 inserts each new alert with its own awaited `InsertAlertAsync` call (the comment acknowledges "트랜잭션 누적은 단순화"). Combined with the unconditional per-sample `LogInformation` at :275-279 (one info log *per tag sample every 750ms*, fired even when not matching), this is a maintainability/log-noise smell. Refactor: add a batch insert on `IUserTagAlertRepository`, and demote the per-sample log to `LogTrace` (keep the per-poll summary at :344).

8. **[MED] Excessive hidden mutable state + coarse lock in `UserTagAlertService`** — UserTagAlertService.cs:31-44 holds 7 mutable fields (two definition collections kept in sync, `_lastValueByAddress`, a `LinkedList` queue, `_lastCheckedLogId`, flags) guarded by one `_stateLock` that is taken inside the per-log loop at :254-259. The two parallel definition representations (`_definitions` list + `_definitionsByAddress` map) must be hand-kept consistent. Refactor: encapsulate definitions in an immutable snapshot object swapped atomically (already half-done via `defsSnap`), and isolate the alert ring-buffer into its own small thread-safe type.

9. **[LOW] `PlcDebugService` mutable singleton `_currentDbPath` set by an HTTP upload path** — PlcDebugService.cs:15, 64-75 (`SetDatabasePath`). A singleton service (Program.cs:77) carries request-mutated global state pointing at a temp-uploaded file, so concurrent `/plc-debug` users clobber each other's DB. Refactor: make the DB path a per-call parameter (or a scoped session object) rather than instance state.

10. **[LOW] F# `Ds2.Core` types leak through the service surface / verbose interop** — PlcToCallMapperService.cs:20-24 stores `Models.CallMappingInfo` holding raw F# `Call`/`ApiCall`, and UserTagAlertService.cs:262-273 inlines `LoggingHelpers.UserTagHelpers.parseValueType/parseMatchOp/shouldFire` + `FSharpOption<string>` construction directly in the hot loop. ## Cross-cut: Frontend architecture & componentization
