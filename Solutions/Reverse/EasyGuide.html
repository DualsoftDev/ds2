Ds2.Reverse 쉬운 안내서

컴퓨터가 PLC 로그만 보고 공장 라인 구조를 자동으로 그리는 법

한 줄로 말하면

공장에서 매일 쏟아지는 스위치 ON/OFF 기록 만 보고, 어떤 동작이 어떤 동작을 일으키는지 자동으로 그림을 그려주는 프로그램입니다.

왜 만들었나?

공장 라인에는 수많은 센서와 모터가 있습니다. 어떤 센서가 켜지면 모터가 돌고, 모터가 멈추면 다음 단계가 시작되고... 이런 흐름을 사람이 일일이 그리면 며칠~몇 주가 걸립니다.

그런데 PLC 라는 자동화 장치는 매일 모든 신호의 ON/OFF 시각을 자동 기록합니다. 이 기록을 컴퓨터가 분석해서 "아, A 가 켜진 뒤 항상 B 가 켜지는구나" 하고 인과관계를 찾아낼 수 있다면? 그게 이 프로그램입니다.

비유: 당신이 한 마을에 처음 갔습니다. 매일 아침 닭 울음 → 해 뜸 → 사람들 일어남 → 빵집 열림 의 순서로 일어납니다. 한 달간 관찰하고 나서 "닭이 울면 곧 해가 뜨고, 그 다음 빵집이 연다" 라는 인과 그림을 그릴 수 있죠. 이 프로그램은 그걸 자동으로 합니다.

어떻게 작동하나?

1로그 수집
PLC 가 매 사이클마다 모든 신호의 ON 시각을 기록합니다. 예: "10:00:00.123 — 컨베이어 START", "10:00:00.456 — 로봇 READY", ...
2관계 후보 만들기
PLC 프로그램 (또는 사용자가 준 힌트) 에서 "이런 관계가 있을 것 같다" 는 후보 화살표를 추출합니다.
예: 컨베이어.START → 로봇.READY
3로그로 검증
각 후보 화살표가 실제 인과인지 통계로 확인합니다.
"컨베이어가 켜진 뒤 정말 항상 로봇이 켜졌는가?" "시간 간격이 일정한가?"
4그림 그리기
검증 통과한 화살표만 모아서 Promaker 가 그릴 수 있는 모델 파일을 만듭니다.

가장 중요한 질문: 인과인가? 우연인가?

닭이 울고 해가 떴어요. 닭이 해를 뜨게 한 건가요?
아니죠. 닭이 울든 안 울든 해는 뜹니다. 이걸 "상관만 있고 인과는 없다" 고 합니다. 컴퓨터가 이 둘을 구분하지 못하면 잘못된 그림을 그립니다.

그래서 4가지 시험을 봅니다

시험 의미 통과 기준
충분성 (Sufficiency) A 가 켜지면 B 도 켜지는가? 85% 이상
필요성 (Necessity) B 가 켜지기 전에 A 가 켜졌나? 85% 이상
안정성 (Stability) 시간 간격이 항상 비슷한가? 변동 30% 이내
표본 크기 (Sample) 관찰 횟수가 충분한가? 5회 이상
4개 시험을 모두 통과해야 "진짜 인과" 로 인정합니다. 하나라도 떨어지면 그림에서 빼버립니다.

PLC 코드의 깊은 관계까지 본다

PLC 코드는 보통 이렇게 생겼습니다:

A AND B  →  C 켜짐
C AND Y  →  D 켜짐

여기서 D 가 켜지려면? C 가 켜져야 하고, C 가 켜지려면 A 와 B 모두 켜져야 합니다. 결국 D 는 A, B, Y 모두에 의존합니다.

비유: 영희가 빵을 사려면 (D) 빵집이 열려야 (C) 합니다. 빵집이 열리려면 빵 굽는 사람 (A) 과 빵 재료 (B) 모두 있어야 합니다. 따라서 영희의 빵 구매는 A, B, Y 의 깊은 사슬에 의존합니다.

Ds2.Reverse 는 이런 사슬을 5단계 깊이까지 자동 추적합니다.

AND 와 OR 의 차이 — 강한 의존 vs 약한 의존

AND 의 강한 의존

C = A AND B
A 와 B 모두 켜져야 C 켜짐.
강도 = 1.0 (모두 필요)

OR 의 약한 의존

C = A OR B
A 또는 B 중 하나만 켜져도 C.
강도 = 0.5 각각 (절반 기여)

5개 변수의 OR (예: C = A OR B OR D OR E OR F) 면 각 변수의 강도가 0.2 밖에 안 됨. 임계값 0.3 미만이라 후보에서 자동 제외. 진짜 인과인지 알기 어려운 약한 신호는 그림에서 빼버립니다.

두 가지 화살표

일반 화살표 (Start)

A 가 끝나면 B 가 시작.
예: 컨베이어 멈춤 → 로봇 시작

A  →  B

그룹 화살표 (Group)

A 와 B 가 동시에 일어남 (병렬).
예: 양쪽 실린더가 동시에 후진

A  ↔  B
시간 간격이 거의 0 (50ms 이내) 이고 항상 같이 발화하면 자동으로 그룹으로 인정.

그림으로 보는 예시

이런 PLC 로그가 들어왔다고 합시다

시간 0초   A 켜짐
시간 0.1초   B 켜짐
시간 0.5초   C 켜짐 D 켜짐 ← 동시 발화
시간 5초   A 켜짐 (다음 사이클)
시간 5.1초   B 켜짐
...

알고리즘이 분석한 결과

A→B→C↔D

A 가 B 를 일으키고, B 가 C 를 일으키며, C 와 D 는 동시에 발화 (그룹).

어떻게 잘못된 것을 걸러내나?

케이스 1: 우연의 일치

X 가 매번 랜덤한 시각에 켜짐

X 가 켜진 후 5초 안에 가끔 Y 도 켜짐.
잘못된 알고리즘: X → Y 라고 표시 ✗

Ds2.Reverse

X 가 켜진 후 Y 가 켜지는 비율이 20% 밖에 안 됨 (85% 미달) → 버림.

케이스 2: 같은 타이머로 같이 돌아가는 외부 신호 (혼동변수)

S 가 매 사이클마다 켜짐. Y 도 외부 타이머로 따로 켜짐.

S 와 Y 가 항상 비슷한 시각에 발화함.
잘못된 알고리즘: S → Y 라고 오해 ✗

Ds2.Reverse

S 와 Y 사이 시간 간격이 매번 크게 달라짐 (변동 50% 이상). 안정성 시험 통과 못함 → 버림.

케이스 3: 사이클이 짧을 때 옆 사이클로 새는 신호

한 사이클이 2초인데 검출 시간창이 3초.

이전 사이클의 A 가 다음 사이클의 B 와 매칭됨.
잘못된 알고리즘: 가짜 인과 ✗

Ds2.Reverse

사이클 길이를 알면 자동으로 시간창을 사이클 안으로 줄임 (사이클 × 70%). 다른 사이클로 새는 신호 차단.

얼마나 잘 맞나?

151
합성 테스트 시나리오
100%
정확도 (Precision)
100%
재현율 (Recall)
시나리오는 10가지 구조 패턴 (체인, 분기, 합류, 그룹, 긴 체인, 사이클 후보 등) + 5가지 통계 도전 (드물게 발화, 다중 발화, 시간 흐름 변화, 비결정적 순서, 부분 인과) + 10가지 PLC 로직 패턴 (단순 AND, 단순 OR, AND of OR, 재귀 2~5단계, NOT 포함, 약한 OR drop, 복합) + 15가지 캐파 패턴 (1~20 token 동시 흐름, jitter, bottleneck, oscillation) 으로 구성.

캐파 (라인 동시 처리 용량)

실제 PLC 라인은 보통 여러 token (workpiece, 차량 body 등) 이 동시에 흐릅니다. 예: 캐파 5 라인은 5개 token 이 각 station 에 분산되어 있음.

비유: 식당의 주방 — 캐파 1 이면 손님 한 명씩 음식 만든 후 다음. 캐파 5 면 5명 손님의 음식을 동시에 단계별로 만듭니다 (재료 손질→조리→플레이팅 각각 다른 손님). 같은 시각에 "재료 손질" 단계가 5번 일어남.

왜 어려운가?

한 변수 (예: S1.START) 가 한 사이클에 N 번 발화. token 들이 interleave 됨. "방금 S1 이 켜진 게 어느 token 의 신호인지" 알기 어렵습니다.

Bottleneck (병목)

S2 stage 처리 시간이 길어 token 들이 queue 대기.
첫 token: S1 → S2 lag = 200ms
대기 token: S1 → S2 lag = 500ms
→ lag 가 두 봉우리 분포 (bimodal)

Bimodal Stability 인정

두 봉우리가 명확히 떨어져 있고, 각 봉우리 안 변동이 작으면 진짜 bottleneck 인과로 인정.

가짜 (외부 timer) 분포는 봉우리 내부도 흩어져 있어서 자동 제외.

알고리즘 발전 이야기

시작
스위치 켜짐/꺼짐 만 보고 그림을 그리려 했더니, 16개 중 2개만 그려짐. 이름 매칭이 안 맞아서.
1단계
이름 끝부분 (suffix) 으로 매칭 + GUID 형식 ID 사용 → 그림은 그려졌으나 무한 루프 발생.
2단계
사이클을 끊는 알고리즘 (Kahn) 추가 → 무한 루프 해결, 하지만 가짜 인과 여전.
3단계
로그 통계로 인과 검증 (4가지 시험) 추가 → 가짜 인과 차단. 합성 테스트 F1=1.0 달성.
4단계
F# 로 정식 솔루션 작성 (실 DS2 코드와 연동). 101 시나리오 테스트 자동화.
5단계
다른 차원 추가 (통계/시간 도전) → 사이클 누설 발견 → 사이클 길이 hint 적용으로 해결.
현재
126개 시나리오 모두 정확히 인식. xunit 자동 회귀 21개 통과.

아직 못하는 것

  • 시간이 지나면서 천천히 변하는 인과 — 처음엔 0.1초, 점점 0.7초 느려지는 경우. 통계 안정성 시험에 떨어짐.
  • 한 B 가 여러 A 중 하나에 의해 트리거 (선택적 인과) — 각 A 의 필요성이 50% 라 인정 안 됨.
  • 로그 없이 PLC 코드만으로 정확한 그림 — 로직 정보는 후보 제공만, 검증은 로그 필수.

한 줄 요약

PLC 로그 + 후보 화살표 → 4가지 인과 시험 → 진짜 인과만 남은 자동 모델 파일 생성. 일이 며칠씩 걸리던 게 몇 초로.
