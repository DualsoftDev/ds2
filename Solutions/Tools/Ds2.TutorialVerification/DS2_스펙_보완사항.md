# DS2 스펙 보완사항

**패턴 수를 늘리기 전에 논리 완료, 시간 계산, 감지의 뜻을 일치시키는 것이 우선입니다.** 이번 실행에서는 기존 다섯 패턴을 조합해 100편의 대표 모델을 만들었습니다. 아래는 코드와 실행 기록으로 확인한 차이 및 이번 모델에서 외부가 맡은 책임입니다. DS2 본체 코드는 수정하지 않았습니다.

[검증 결과](모델_검증결과.md) · [100개 모델](README.md) · 전체 자료

## 1. 센서 없는 논리 요청도 대상 Work 완료로 끝나게 한다 — 우선 수정

설계 원칙은 “Call은 다른 시스템을 지시·관찰하고, 대상 Work가 끝나면 논리 요청도 끝난다”입니다. 그러나 현재 V2는 SensingType이 Virtual이 아니면 InTag를 요구합니다. 91개 모델의 논리 API 187건이 이 검사에 걸립니다.

080 비교에서 대상 준비 Work는 1 ms에 끝났습니다. Simulation의 Call도 1 ms에 끝났지만 Control의 동일 Call은 200 ms 동안 Going으로 남았습니다. 센서 없는 논리 동작에 가짜 센서를 추가하는 해결은 사용하지 않았습니다.

**권고:** 완료 근거를 ‘대상 Work’와 ‘외부 입력’으로 명확히 구분하고, 입력 없는 논리 호출은 대상 Work 완료로 끝나도록 정적 검사·Simulation·Control 규칙을 맞춥니다. Virtual(T)의 시간 완료를 논리 완료의 우회로 사용하지 않습니다. 기존 센서 API의 외부 입력 의미는 보존해야 합니다.

완료 기준은 새 요청의 대상 실행인지, 이미 끝난 상태를 관찰하는지까지 포함합니다. 새 동작 요청은 이전 Finish를 새 완료로 잘못 받지 않아야 하고, SkipIfCompleted 관찰은 의도한 완료를 재사용할 수 있어야 합니다.

근거: `Core/Ds2.Core/V10Validation.fs:28`, `Runtime/Ds2.Runtime/Engine/Core/Commands/WorkConditionChecker.fs:251`, 080, [모드 비교 기록](probes/summary.json).

## 2. 상위 Work의 예상 시간을 실제 완료 대기로 쓰지 않는다 — 우선 수정

100개 파일 모두 Call을 가진 Work에는 Duration을 직접 쓰지 않았습니다. 물리 시간은 마지막 Work에만 있습니다. 그런데 현재 엔진은 호출 대상들의 시간에서 상위 Work 시간을 계산하고 그 시간을 최소 완료 조건으로 사용할 수 있습니다.

034에서 A 처리 20 ms와 B 처리 30 ms를 순서대로 배치하고 하나를 생략했습니다. A 제품은 Call들이 50 ms에 모두 끝났지만 상위 Work는 80 ms에 끝났습니다. B 제품은 마지막 Call이 222 ms에 끝났지만 상위 Work는 242 ms에 끝났습니다. 수행하지 않은 작업 시간까지 기다리는 결과입니다.

**권고:** 계획 화면의 예상 시간과 실행 완료 조건을 분리합니다. Call을 가진 Work는 이번 회차에서 필요한 Call과 조건의 완료로 끝내고, 생략된 Call의 물리 시간을 더하지 않습니다. Call 없는 Work의 Duration만 직접 동작 시간으로 적용합니다. 관찰 Call 여러 개가 같은 대상을 보더라도 물리 시간을 중복 합산하지 않는 규칙을 추가합니다.

인수 기준: A만 수행하면 20 ms, B만 수행하면 30 ms인 대상들의 선택 예에서 상위가 50 ms 계획값 때문에 더 기다리지 않아야 합니다. 준비·입력 대기·리셋 소요는 각자의 실제 이벤트로 분리해서 표시합니다.

근거: `Runtime/Ds2.Runtime/Engine/Core/SimIndex/Build.fs:138`, `Runtime/Ds2.Runtime/Engine/Core/SimIndex/Algorithms.fs:181`, [034 모델](verified/models/034.ds2.sdf), ZIP의 `verified/evidence/034/events.json`.

## 3. Latch 감지와 Virtual 감지의 완료 기준을 확정한다 — 우선 수정

| 진단 | 현재 관측 | 확정할 뜻 |
|---|---|---|
| Latch(10), 첫 입력 false를 5 ms에 공급 | 15 ms에 완료 | 어떤 값 변화든 인정할지, 조건에 맞는 감지만 기억할지 |
| Latch(10), 첫 입력 true를 5 ms에 공급 | 15 ms에 완료 | 감지한 시점부터 지연을 셀지, 마지막 변화부터 셀지 |
| Normal(10), true→false→true | 마지막 true 뒤 10 ms에 완료 | 안정 시간과 흔들림 취소 의미 |
| Virtual(10), 대상 Work 40 ms | 두 모드 모두 Call 10 ms 완료 | 대상 작업 중인데 요청 완료가 가능한 의도인지 |
| Virtual(100), 대상 Work 40 ms | Simulation 40 ms, Control 100 ms | 시간과 대상 완료 중 빠른 쪽으로 끝낼지, 모드 간 의미를 맞출지 |

**권고:** Latch는 ‘새 입력이 있었다’와 ‘기대한 입력을 감지했다’를 분리해 명세합니다. 현재 코드의 입력 epoch 증가만으로 감지로 읽는 부분은 false도 완료하는 결과를 만듭니다. 어떤 값이든 첫 변화가 의도라면 그 이름과 설명을 바꾸고, 조건 만족 감지가 의도라면 InputSpec 만족을 함께 확인해야 합니다.

Virtual(T)는 물리 동작 시간의 두 번째 정의가 되지 않도록 역할을 제한하고, Simulation과 Control의 표를 스펙에 넣습니다. 사용자 원칙대로 물리 시간은 leaf Work Duration, Call 옵션 시간은 출력 폭·감지 확인 정책으로 구별합니다. 모드 차이는 확인된 사실이며 어느 쪽이 최종 정답인지는 이 문서가 임의 확정하지 않습니다.

근거: `WorkConditionChecker.fs`의 `WaitOutputPlus`, `WaitInputStable`, `WaitInputLatched`, 079, [비교 기록](probes/summary.json).

## 4. 사양·판정값이 언제 이번 제품의 값이 되는지 적는다 — 명세 강화

값 없는 조건은 대상 Work 완료로 대신 읽을 수 있다는 원칙을 유지합니다. 다만 그것만으로 A/B 사양이나 OK/NG 측정값이 새로 들어왔다고 해석하지 않습니다. 값에 따른 선택은 이번 값 도착을 먼저 확인하고 선택이 끝날 때까지 값을 유지해야 합니다.

035에서 값 도착 AutoAux 하나만 빼면 네 제품이 모두 B로 처리됩니다. 현재 예제는 시험기가 사양값과 도착 신호를 넣습니다. 제품 Token의 필드를 조건 입력으로 자동 전달하는 기능을 구현했다고 주장하지 않았습니다.

**권고:** 값의 생산자, 제품 번호, 유효한 회차, 도착 표시, 마지막 사용자를 입력 규약에 둡니다. 같은 A·A나 OK·OK도 새 응답으로 인정되어야 합니다. 제품별 Work 생략과 모든 제품의 공통 품질 Call 생략은 별개의 설계 예로 유지합니다.

## 5. Flow의 제품 수와 제품을 넣는 책임을 구분한다 — 명세 강화

Flow는 Work의 컨테이너이면서 한 제품의 흐름을 나타냅니다. 제품 Flow 네 개를 네 제품 동시 처리 의도로 설계할 수 있습니다. 이것을 구현하려면 누가 빈자리와 다음 받기를 확인하는지도 필요합니다.

이번 시험은 공급기가 Ready, 제품표 칸, 해당 흐름의 빈 상태, 이전 제품 종료를 확인했습니다. 안정 시점의 한 Flow에는 고유 제품이 최대 한 개입니다. 이것만으로 엔진이 임의 투입을 항상 거절하거나 고정 자리 교환 중 모든 중간 순간의 수를 제한한다고 말하지 않습니다.

**권고:** 공급 허용 조건과 용량 판정 시점을 명시하고, 고정 자리 Flow와 이동 받침 Flow를 구별합니다. 별도 Flow Token 이동 모델을 추가할 필요는 없습니다. 제품표는 기존 Work Arrow를 따릅니다. 049처럼 한 받기 Flow에 여러 출발 방향의 Work를 둘 수 있지만 한 자리의 사용 허가는 모델에서 정해야 합니다.

## 6. 완료 이벤트와 생산량의 뜻을 분리한다 — 명세 강화

022에서 Ignore 용접 Work도 Token Complete 이벤트를 냅니다. 같은 제품이 실제 Sink에서도 Complete가 됩니다. 모든 Complete를 합하면 제품 세 개를 여섯 개로 셀 수 있습니다.

**권고:** 보조 전달 종료, 제품의 최종 종료, 실제 장치 실행, 생략, 초기 Finish를 결과 화면에서 구분합니다. 생산량은 선언한 Sink와 고유 제품 번호를 기준으로 집계합니다. 회전 회차·운반 회차·배치 수·배치 안 부품 수도 서로 다른 단위로 표시합니다.

## 7. 모델 안에서 한 일과 외부에서 한 일을 표시한다 — 명세 강화

- 반복: 064는 최대 세 회를 펼친 모델입니다. 큰 N을 동적으로 반복하는 표준 카운터가 필요하면 증가·비교·새 제품 초기화·종료를 최소 조합으로 정의합니다. 새 설비마다 패턴 이름을 만들 필요는 없습니다.
- 차례: 057는 모델 내부의 순환 차례입니다. FIFO와 우선순위는 별도 요구입니다. 동시에 요청했다는 이유로 실행 순서를 약속하지 않습니다.
- 재작업: 050의 재검사 결과 변경은 외부입니다. 재시도 상한을 어디서 관리할지 표시합니다.
- 조립: 089의 C 번호 생성과 A/B 대응은 외부 공급기입니다. TokenSpecs는 대응 정보를 저장하지만 그 자체가 자동 병합 동작을 실행하지 않습니다.
- 묶음: 088은 배치 단위 Token입니다. 부품별 추적이 필요하면 자식 제품의 생성·종료 책임도 정합니다.

**권고:** 모델 전달물에 구조 파일과 함께 입력 시나리오, 단위, 초기 상태, 외부 책임을 포함합니다. 런타임이 자동 처리하는 기능을 늘릴 때도 먼저 이 경계를 명세합니다.

## 8. 정적 검사·모의 실행·제어 진단을 따로 보여 준다 — 도구 보완

100개 Simulation 통과가 100개 정적 통과 또는 실제 설비 운전 승인을 의미하지 않습니다. 검사 결과에 각각의 상태를 둡니다. Source에 앞 연결이 있는 재작업·회전은 사용 가능한 순환인지 실제 오류인지 경고를 구분해 읽어야 합니다.

자동 배치의 Group·회귀 연결에서 Work 사각형이 겹치는 경우를 확인해 이번 모델의 좌표만 정리했습니다. 편집기의 자동 배치에도 겹침 검사를 추가하면 처음 여는 모델을 읽기 쉬워집니다. 런타임 의미를 바꾸는 문제와는 구분합니다.

## 적용 순서

1. 논리 완료, 상위 시간, Latch·Virtual의 뜻을 확정하고 기존 모델로 회귀 검증합니다.
2. 제품값 유효성, 공급·용량, 생산량 집계의 규약을 문서와 결과 화면에 반영합니다.
3. 실제 필요가 확인된 반복·차례·제품 변환 기능만 기존 다섯 패턴의 조합 또는 작은 매크로로 보완합니다.

StartReset처럼 반복되는 관계를 짧게 표현하되, 펼쳤을 때 Start·Reset과 완료 조건이 명료하게 남아야 합니다. 패턴의 수보다 한 제품의 실행 경로와 각 상태의 의미가 먼저입니다.
