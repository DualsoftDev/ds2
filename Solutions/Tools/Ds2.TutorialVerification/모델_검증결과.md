**네이티브 SDF 100개를 만들고, 현재 DS2 Runtime으로 실행한 뒤, 저장 파일 그대로 재실행했습니다. Simulation 100개 통과, 정적 검사 9개 통과·91개 미통과입니다.** 미통과 원인은 센서 없는 논리 Call에도 입력 주소를 요구하는 V2 규칙이며 숨기지 않았습니다.

## 무엇을 실행했나

`C:\ds\ds2\Solutions`의 Ds2.Core, Ds2.Editor, Ds2.Runtime을 현재 소스로 빌드했습니다. 공식 편집·저장 API로 만든 파일을 새 Store에 읽어 `EventDrivenEngine`에서 실행했습니다. CSV 해석기나 자체 흉내 엔진으로 대신 검사하지 않았습니다.

제품 공급은 `SeedToken`과 `StartSourceWork`, 입력은 `InjectIOValue`, 시간 진행은 `AdvanceSimulationTo`를 사용했습니다. Work나 Call 상태를 강제로 완료시키는 함수는 사용하지 않았습니다. 각 실행은 20,000 ms 상한 안에서 확인했고, PLC·실제 설비·네트워크 어댑터는 연결하지 않았습니다.

## 반례를 어떻게 확인했나

같은 저장 모델과 같은 입력을 사용하고 한 조건만 바꿨습니다. SDF를 비교해 변경 지점이 조건 한 군데뿐인지도 검사했습니다.

| 글 | 한 가지 변경 | 검출 결과 |
|---|---|---|
| 022 / 095 | 용접의 잡기 완료 AutoAux 제거 | 잡기가 끝나기 전에 가공 시작 |
| 035 | 이번 값 도착 AutoAux 제거 | A·A·B·B가 모두 B로 잘못 처리됨 |
| 052 | 한 사용자의 반납 대기 조건 제거 | 20,000 ms에 전체 처리 실패, 제품 3개 잔류 |
| 064 | 두 번째 Call의 생략 방향 뒤집음 | 필요한 2회 대신 1회 수행 |

반례 파일은 정상 모델 100개와 섞지 않고 ZIP의 `negative`에 두었습니다. 반례가 실패해야 시험이 성공입니다.

## 감지와 모드 비교

079·080 파일을 바탕으로 메모리 입력만 사용하는 별도 비교를 실행했습니다. 이것은 제어 모드의 코드 의미를 비교하는 진단이며 실제 제어기 운전 인증이 아닙니다. [비교 기록](probes/summary.json)을 함께 제공합니다.

- Latch(10): 시작 뒤 5 ms에 첫 입력 false를 넣어도 15 ms에 Call 완료가 발생했습니다. 첫 true도 같은 결과입니다.
- Normal(10): 5 ms true → 8 ms false → 20 ms true이면 30 ms에 완료합니다.
- Virtual(10), 대상 40 ms: Simulation과 Control 모두 Call이 10 ms에 끝났습니다.
- Virtual(100), 대상 40 ms: Simulation은 40 ms, Control은 100 ms에 Call이 끝났습니다.
- 무입력 논리 Call: 대상은 1 ms에 완료됩니다. Simulation의 Call은 1 ms에 끝나지만 Control은 200 ms 창 안에서 끝나지 않습니다.

## 전부 검증했다고 말하지 않는 부분

100개는 글에 대응하는 대표 실행 예입니다. 가능한 모든 입력 조합과 모든 기계 변형의 완전한 검증은 아닙니다. 단순 인계 파일이 실제 리프트의 모든 센서를 구현했다거나, 반복 상한 3의 파일이 무한 반복을 구현했다고 설명하지 않았습니다. 각 글의 ‘직접 실행한 모델’에서 축소 범위와 외부 책임을 확인할 수 있습니다.

제품 공급은 준비·빈자리·이전 제품 종료를 확인한 시험기가 맡았습니다. Flow 수만으로 엔진이 용량을 자동 제한한다는 검증은 아닙니다. 제품 수는 이벤트 처리 뒤 안정된 상태에서 센 값이며 동시 교환 중 모든 중간 콜백의 고정 자리 수까지 보장하지 않습니다.

회전 네 파일과 재작업 한 파일의 Source 선행 연결 경고는 원문 그대로 기록했습니다. Ignore Work의 보조 Complete 이벤트와 실제 Sink 생산 종료도 구분했습니다.
