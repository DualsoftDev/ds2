# csvForAI — 자동차 차체라인 전용 지침

> 차체라인 전용 csvForAI 작성 지침 — 최종본.
> 규칙의 근거는 현장 PLC(`plc.ir.json` · `sx_field_log.sqlite`)·조립작업서·DS2 엔진 실측이다.

> **이 지침은 RH 유닛 기준이다.**
>
> 차체라인은 같은 설비가 좌우로 놓인다 — PLC 에도 `S507L_*` 과 `S507R_*` 이 쌍으로 있고
> 주소가 갈린다(`%QX2.31`/`%QX3.31`, `%QX5.23`/`%QX5.43`). 실측 자료
> (`동작시간분석.xlsx` · `sx_field_log.sqlite`)가 **RH 만** 담고 있으므로
> 모든 시간·주소·산출물을 RH 로 맞췄다. LH 는 대칭일 것으로 보이지만 **확인하지 않았다** —
> LH 를 적을 때는 주소를 다시 확인하고, 시간은 RH 값을 가져다 쓰되 그 사실을 주석에 남겨라.
>
> **«LH/RH» 가 두 뜻으로 쓰인다.** 헷갈리면 안 된다:
>
> | 쓰임 | 예 | 뜻 |
> |---|---|---|
> | **유닛** | `S507L_…` / `S507R_…` | 라인 좌우에 놓인 **다른 설비** |
> | **위치** | `클램프LH전` / `클램프RH전` | **한 지그 안**의 좌우 클램프 |
>
> 앞은 모델을 통째로 나누는 기준이고, 뒤는 한 Work 안의 Call 이름일 뿐이다.


이 문서는 [CSV_FOR_AI_GUIDE.md](CSV_FOR_AI_GUIDE.md)의 **차체라인 부속 지침**이다.
문법은 그쪽에 있고, 여기에는 차체라인에서만 통하는 **모델링 판단**을 적는다.

적용 대상: 차체 조립(FLR · SIDE INR/OTR · ROOF · ROOF RAIL · BB · BC · MF · FRT DR · TAIL GATE)의
지그 셀 · 용접 셀 · 반송 구간.

근거: `D:\조립라인` 조립작업서 12종 · 표준설비리스트(케이스 240건) · S507 펜더장착 RH 실측
(PLC 래더 3,185코일 · IO 정본 259태그 · 실측 사이클 61.1s).

## 핵심 열 줄

**2,700줄 중 이 열 줄이 값어치의 대부분이다.** 나머지는 걸렸을 때 찾아라.

1. 헤더는 `Kind,Name,Type,Detail,Time,InTag,OutTag` 일곱 칸. **IO 는 `API` 행에만** 적는다
2. **먼저 «배선 전인가 후인가» 를 정하라.** 배선 전이면 감지를 전부 `Virtual(n)` 로 내린다 —
 `Normal`·`Latch` 감지에 InTag 가 `?` 면 엔진이 Call 을 **영영 완료시키지 않는다**
3. **leaf 판정은 InTag 가 가른다** — 있으면 «지금 값», 없으면 «그 Work 가 끝났는가».
 **읽기 전용 API 를 leaf 로 쓰면 InTag 를 반드시 채워라**(`?` 면 «항상 참» 이 되어 조건이 조용히 뒤집힌다)
4. **평소 꺼져 있는 비트**(이상총괄·판정 워드)는 감지도 `Virtual` — `Latch` 면 그 Work 가 영영 선다
5. **빈 칸 ≠ `?` ≠ 값.** 모르면 `?`, 원래 없으면 빈 칸. **지어내지 마라 — `?` 는 결함이 아니다**
6. 적기 전에 **«이번 차체가 무엇이든 반드시 도는 Call» 목록을 Call 단위로** 만들어라 —
 Group 전달자 · `AutoAux` 가 기다릴 대상 · `ComAux` 자리 셋이 전부 그 하나에서 나온다
7. **생략은 `AutoAux` 에게 완료가 아니고 `Group` 멤버에게는 완료다.**
 생략될 수 있는 Work 는 `Start` 사슬이 아니라 **`Group` 동반자 + `Ignore`**, 전달자는 생략되지 않는 공용 Work
8. **고정과 작업은 직렬이 아니라 `Group` + Call `AutoAux`**(단 차종 분기로 고정이 갈리면 두 Work — §13-B) — «전진 완료» 라는 더 작은 사실로 고리를 끊는다
9. **`&` 와 `|` 는 한 괄호에 못 섞고, Call DAG 에는 괄호를 못 쓴다.**
 층은 괄호로 나누고, 같은 종류 `COND` 두 줄은 **누적 AND** 다
10. **배출 → 앞단 전부 `Reset` + 투입 ← 배출 `Reset`.**
 `Start`/`Reset` 은 Flow 를 넘기지 마라 — 넘겨도 되는 것은 `ResetReset` 뿐이다

## 처음 읽는 사람에게

**혼자 처음부터 적지 마라 — 세 역할로 나눠라.** 실무에 넣을 때의 순서다:

| 누가 | 무엇을 읽고 | 무엇을 내놓나 |
|---|---|---|
| **제어 엔지니어** | 「처음 읽는 사람에게」 · §형식 · §0 · §1 · §12 · §13-A0 | **머리말 주석 넷** — ① 배선 전/후 ② 주소 출처 ③ 주 시간 출처 ④ «반드시 도는 Call» 목록 |
| **적는 사람(또는 AI)** | 그 머리말 + **전문** | CSV |
| **리뷰어** | §9 를 주제별로 · §10 을 증상 색인으로 | 통과/반려 |

**첫 역할이 정하는 넷이 나머지 전부를 결정한다.** 건너뛰고 혼자 적으면
«지침에 없어 스스로 정한 것» 이 주석 없이 모델에 녹아들어 —
**뒤에 오는 사람이 진짜와 가짜를 구분할 수 없게 된다**(§12).

**먼저 정할 것 하나: «배선 전인가 배선 후인가».**
이 선택이 `API` 행의 Type 을 전부 바꾸고 `COND` 의 뜻을 뒤집는다(§1 사다리).
주소를 모르면 배선 전, IO 리스트가 있으면 배선 후다.

**차례에서 §형식 → §0 → §1 → §13-A0 넷을 먼저 읽고,
«이번 차체가 무엇이든 반드시 도는 Call» 목록을 적은 다음에 첫 줄을 쓰기 시작하라.**
전달자·`AutoAux` 대상·`ComAux` 자리 **세 판단이 전부 그 목록 하나에서** 나온다.
(§1 을 먼저 읽는 것은 **Call 이름을 지을 어휘**가 거기 있기 때문이다.)

**배선이 끝난 단계라면** §13 의 「leaf 판정」·「ON 창이 겹치는가」·「판정 비트는 언제 꺼지는가」
세 절을 그 목록 옆에 펴 두어라 — 배선 후에만 나타나는 함정이 그 셋에 모여 있다.

다 적은 뒤에는 **§9 점검표**를 주제별로 끊어 훑고, **§10 은 증상 색인**으로 쓴다.

## 형식 — 이 문서만 읽고도 쓸 수 있게

세부는 `CSV_FOR_AI_GUIDE.md`·`CSV_FOR_AI_SCHEMA.md` 에 있다. 여기서는 **적을 수 있을 만큼**만 둔다.

**헤더는 이 일곱 칸 그대로다**(순서·이름 고정):

```
Kind,Name,Type,Detail,Time,InTag,OutTag
```

| Kind | Name | Type | Detail | Time | InTag/OutTag |
|---|---|---|---|---|---|
| `SYS` | 시스템 이름 | `Active` / `Passive` | — | — | — |
| `FLOW` | Flow 이름 | — | — | — | — |
| `WORK` | `Flow.Work` | 역할(아래) | Call DAG | **Call 없을 때만** | — |
| `ARROW` | 출발점 | 관계(아래) | 도착점(`;` 로 여럿) | — | — |
| `API` | `디바이스.액션` | `Action/Sensing` | 공란 | 동작 시간 | **여기만 쓴다** |
| `COND` | 소유자 경로 | `AutoAux`/`ComAux`/`SkipAction` | 조건식 | — | — |

**IO 는 `API` 행에만 적는다.** 다른 Kind 의 6·7열은 비운다.

### 최소 예제 — 모든 Kind 가 한 번씩

```
Kind,Name,Type,Detail,Time,InTag,OutTag
SYS,용접셀,Active,,,,
SYS,지그,Passive,,,,
FLOW,차체,,,,,
WORK,차체.고정,Source,지그.전진 > 지그.후진,,,
WORK,차체.배출,Sink,,3S,,
ARROW,차체.고정,Start,차체.배출,,,
ARROW,차체.배출,Reset,차체.고정,,,
ARROW,차체.고정,Reset,차체.배출,,,
API,지그.전진,Latch/Normal,,600MS,%MX1.2051.03,%QX5.43.0.04
API,지그.후진,Normal/Normal,,600MS,%MX1.2051.04,%QX5.43.0.05
COND,차체.고정.지그.후진,AutoAux,지그.전진,,,
```

`Ignore`·`Finish`·`SkipAction` 까지 쓰면 이렇게 된다(2열 교대 + 차종 분기):

```
WORK,차체A.반입,Source,반송.투입 > 반송.원위치,,,
WORK,차체A.고정,,지그A.전진 > 지그A.후진,,,
WORK,차체A.용접,Ignore,로봇.용접 > 로봇.원위치,,,
WORK,차체B.고정,Source+Finish,지그B.전진 > 지그B.후진,,,
ARROW,차체A.반입,Start,차체A.고정,,,
ARROW,차체A.고정,Group,차체A.용접,,,
ARROW,차체A.고정,ResetReset,차체B.고정,,,
COND,차체A.용접,SkipAction,/판정.KA4,,,
```

- `Ignore` — Group 동반자. 토큰을 넘기지 않는다(전달자는 `차체A.고정`)
- `Source+Finish` — 「토큰이 여기서 생긴다 + 초기 상태가 Finish」. 먼저 도는 쪽을 정한다
- `SkipAction` — 참이면 **건너뛴다**. `/` 로 부정해 «KA4 가 아니면 건너뛴다» 를 적었다

- **`Active` System 은 반드시 한 행 있어야 한다** — 그 이름이 모델 이름이 된다.
 나머지 디바이스는 전부 `Passive` 다
- `Passive` System 의 Flow·Work 는 **매퍼가 자동으로 만든다.** 직접 적지 않는다

### WORK 의 역할 (Type 열)

| 값 | 뜻 |
|---|---|
| (공란) | 보통 Work |
| `Source` | 토큰이 **여기서 생긴다**. 사슬의 첫 Work |
| `Sink` | 토큰이 **여기서 끝난다**. 사슬의 마지막 Work |
| `Ignore` | 토큰을 **넘기지 않는다**. Group 동반자에 쓴다(전달자는 하나뿐) |
| `Finish` | TokenRole 이 아니라 **초기 상태가 Finish** 라는 표시(재무장 복귀측) |

조합은 `+` 로 — `Source+Sink` · `Source+Finish` · `Ignore+Finish` 모두 된다(실측 확인).
`Finish` 는 TokenRole 이 아니므로 **어느 역할과도 겹칠 수 있다.**

### ARROW 의 관계 (Type 열)

| 값 | 뜻 |
|---|---|
| `Start` | A 완료가 B 시작 조건 |
| `Reset` | A 기동이 완료된 B 를 다음 실행에 쓸 수 있게 한다 |
| `StartReset` | `A Start B` + `B Reset A` 를 한 줄로 |
| `ResetReset` | 양방향 Reset(번갈아 쓰는 두 자리) |
| `Group` | 함께 시작하고 전원 완료를 기다린다. **출발점이 전달자** — 비-Ignore 는 하나뿐 |

- **`Work` 완료 = 그 안의 Call 이 전부 완료**(생략된 것은 빼고). `;` 나열도 같다
- **전달자는 TokenRole 과 무관하다** — `Sink` 가 전달자를 겸해도 된다(토큰을 넘긴 뒤 없앤다)

**Call 레벨(4마디)에는 `Start` 와 `Group` 만 쓸 수 있다**(`AI008`).

### COND 의 소유자와 종류

- Name 이 **2마디**(`Flow.Work`)면 Work 조건, **4마디**(`Flow.Work.디바이스.액션`)면 Call 조건
- **`AutoAux`·`ComAux` 는 Call 전용이다.** Work 에 적으면 `AI014` 로 거부된다.
 Work 에 걸 수 있는 것은 `SkipAction` 하나뿐이다

**같은 Call 에 같은 종류를 두 줄 적으면 «누적(AND)» 이다**(실측 확인 — Condition 이 둘로 남고
엔진이 AND 로 모은다). 덮어쓰기가 아니다. 길어지면 줄을 나눠도 뜻이 같다:

```
COND,차체.용접.로봇.타점,ComAux,라인상태.운전준비,,,
COND,차체.용접.로봇.타점,ComAux,/라인상태.이상총괄,,, ← 위와 AND
```

**단 `&` 와 `|` 를 섞어야 할 때는 한 줄에 괄호로** 적어라 — 줄을 나누면 전부 AND 가 된다.

- **`;` 로 여럿 적기**: `ARROW` 의 도착점과 `WORK` 의 Call 나열에 쓴다.
 **앞뒤 공백은 있어도 없어도 같다** — 읽기 좋은 쪽으로 하되 한 파일 안에서는 통일하라
 - **`Group` 한 줄에 대상을 여럿 적으면 «한 묶음» 이다**(실측 확인 — 간선 여럿으로 펼쳐져
 하나의 그룹집합이 된다). 쌍을 여럿 만들려면 **출발점을 달리해** 줄을 나눠라
- **Call DAG**(WORK 의 Detail): `A > B` 는 «A 끝나고 B», `A ; B` 는 «둘 다, 순서 없음».
 `>` 가 `;` 보다 **세게 묶는다** — `A > B ; C` 는 «(A→B)» 와 «C» 다
 - **괄호는 쓸 수 없다**(`AI065`). «A·B 를 동시에 낸 뒤 C» 를 한 줄로 못 적는다 —
 `A ; B ; C` 로 나열하고 **C 의 `AutoAux` 에 `A & B`** 를 걸어라
- **ARROW 끝점**: 2마디(`Flow.Work`)면 Work 레벨, 4마디(`Flow.Work.디바이스.액션`)면 Call 레벨
### Action/Sensing 의 값 — 무엇을 내보내고 무엇을 읽는가

`API` 행 Type 열은 `동작/감지` 두 칸이다. 왼쪽이 **내보내는 방식**, 오른쪽이 **완료를 읽는 방식**이다.

| 값 | 동작(왼쪽) | 감지(오른쪽) |
|---|---|---|
| `Normal` | 출력을 켜고 동작이 끝날 때까지 둔다 | 입력이 서면 완료 |
| `Latch` | 출력을 **켠 채 유지**한다(클램프 물림) | 입력이 서면 **유지**해 읽는다 |
| `Virtual` | **출력이 없다** — 읽기 전용이거나 논리만 | 시간이 지나면 완료로 본다 |
| `Pulse(n)` | `n` 동안만 켰다 끈다 | 짝이 되는 감지는 **`Virtual(100)`** — 답이 없는 지령이다 |

**`Latch`·`Virtual` 감지에는 시간이 따라붙는다** — `Virtual/Latch(30)`.
**괄호 안 숫자의 단위는 ms 다**(`Latch(30)` = 30ms, `Pulse(500)` = 500ms).

**숫자는 «얼마나 기다려 줄 것인가» 다.** 정밀한 값이 아니라 관행이면 된다:

| 자리 | 값 |
|---|---|
| 센서·판정 비트 감지 | `Latch(30)` / `Virtual(100)` |
| 논리만 있는 Call(답이 없는 지령) | `Virtual(100)` ~ `Virtual(200)` |
| 일방 지령 출력 | `Pulse(500)` |
| **배선 전 액추에이터 감지** | `Virtual(100)` |

`Virtual` 이 동작 쪽에 오면 **OutTag 를 비운다** — 센서·버튼·판정 비트가 그렇다.

### 빈 칸 · `?` · 값 — 셋은 뜻이 다르다

| 적는 법 | 뜻 | 언제 |
|---|---|---|
| **빈 칸** | 그런 것이 **없다** | `Virtual` 동작의 OutTag(출력이 없다) · **일방 지령(`Pulse`)의 InTag — 답이 원래 없다** |
| **`?`** | **아직 모른다** | 배선 전이라 주소를 못 정했다 · 시간을 못 구했다 |
| 값 | 안다 | 배선이 끝났거나 자료가 있다 |

**`Time` 열도 같다.** 일방 지령(`Pulse`)처럼 **물리 duration 이 원래 없는** Call 은
`?`(숙제)가 아니라 **빈 칸**으로 둔다 — 500ms 기본값이 들어가지만 논리 Call 이라 문제가 없다.
«모르는 것» 만 `?` 다.

빈 칸과 `?` 를 바꿔 쓰면 안 된다. **없는 것을 `?` 로 적으면 «채워야 할 숙제» 가 되고,
모르는 것을 빈 칸으로 적으면 «없어도 된다» 가 된다.**
- **조건식**: `&`(AND) `|`(OR) `/`(부정) `(…)`(묶음). leaf 는 `디바이스.액션`
 - **한 괄호 안에서 `&` 와 `|` 를 섞을 수 없다**(`AI052`). 우선순위가 아니라 **금지**다 —
 `A & B | C` 는 거부된다. 층을 괄호로 나눠라: `A & (B | C)`
 - 부정은 leaf 앞에 `/` — `/라인상태.이상총괄`
- **시간**: `100MS` · `1S` · `3584MS`. 모르면 `?`.
 **소수는 못 쓴다** — `36.4S` 가 아니라 `36400MS` 로 환산한다(용접 «타점 × 2.6s» 는 반드시 소수가 된다)
- **IO**: `[심벌@]주소[:자료형][=값]`. 모르면 `?`. 예 `T축거리@%IW6.21.2:INT=1200`
- **주석**: 줄 맨 앞 `#`. 헤더는 **1행**에 두고 주석은 그 뒤에 붙인다
- **버전 선언 줄은 없다.** 헤더 일곱 칸이 곧 형식 선언이다
- **행 순서에 뜻이 없다.** Work 사이 관계는 전부 `ARROW` 로 적는다

## 0. 목표 수준

한 셀의 CSV를 다 적었을 때 **다음이 전부 담겨야** 한다. 하나라도 빠지면 실물을 못 돌린다 — **단 그 셀에 있는 것만이다**(인덱스 없는 셀은 인덱스 항목을 뺀다).

```
차종 분기 KA4 / MV / RJ 처럼 차종마다 다른 지그가 선다
다점 확인 클램프 하나에 리드스위치가 여럿 → **판정 비트 하나로 적는다**(§4)
 ※ 배선 전이면 유예 — IO 를 볼 수 있을 때 성립한다
로봇 핸드셰이크 PLC 가 «가능» 을 내고 로봇이 «완료» 로 답한다
인덱스 회전 8분할 테이블의 각도별 스테이션
재무장 배출이 앞단을 전부 리셋해 다음 제품을 받는다
```

S507 실측 기준 한 셀 규모: **유닛 36 · Work 14 · 사이클 61s**. 이보다 훨씬 작으면 무언가 빠진 것이다.

규모를 스스로 가늠하는 법 — 적고 나서 세어 본다:

| 항목 | 지그 셀 1개 기준 | 모자라면 의심할 것 |
|---|---|---|
| `SYS` Passive | 8~40 | 차종 분리를 안 했거나 센서를 뺐다 |
| `WORK` | 8~16 | 하한 미달이면 **뭉갠 것인지 «접은» 것인지** 보라 — §1 입도·§13-B 대로 접으면 줄어드는 것이 맞다 |
| `API` | 10~80 | 복귀(RET)를 안 적었다 |
| `ARROW` | Work 수 + 재무장 | 재무장을 빠뜨렸다 |
| 사이클 합 | 40~90s | 시간을 `?` 로만 두었다 |

**세는 단위와 기준**:
- `ARROW` 는 **«행» 이 아니라 «간선»** 으로 센다 — `;` 로 몰아 적으면 행 수가 훨씬 적어진다
- `WORK` 상한은 **«차종·사양 분기 전» 기준**이다. §13-A2 대로 적으면 차종 3종이면 고정 3개,
 OK/NG 분기면 2개가 **강제로** 생긴다 — 그만큼은 상한에 더해서 보라
- `SYS`·`API` 도 **차종 수만큼 곱해진다** — 차종 3종 × 지그 2종이면 SYS 6 · API 12 가 강제로 생긴다
- `SYS`·시간 범위도 «지그 셀 하나» 기준이다. 라인이나 복합 셀은 §12 로 가라

차종 3종이면 클램프·핀 계열이 **3배**가 된다. S507 이 유닛 36인 이유가 그것이다.

## 1. 설비 어휘 — 표준설비리스트 8분류

차체라인 설비는 이 여덟으로 갈린다. `SYS` 행의 이름과 `API` 행의 액션을 여기서 고른다.

### 배선 전이라면 감지를 `Virtual` 로 두어라 — `Normal`·`Latch` 는 InTag 를 요구한다

엔진이 불변식으로 선언한다(`RuntimeSemantics.fs:86` — «≠Virtual ⇒ InTag required»):

```fsharp
| SensingType.Virtual n, _ -> Some (WaitOutputPlus (call, n)) // 태그 없어도 완료
| SensingType.Normal None, Some tag -> Some (WaitInput tag)
| SensingType.Latch n, Some tag -> Some (WaitInputLatched (tag, n))
| _, None -> None // 트리거 없음
```

**`Virtual` 만 태그 없이 완료된다.** `Normal`·`Latch` 감지에 InTag 가 `?` 면
완료 트리거가 서지 않고, 엔진은 **Call 을 완료시키지 않는다**
(`WorkConditionChecker.fs:266` — «trigger 가 없어도 device(rx) 로 Call 완료 금지»).
**시간으로 넘어가지 않는다** — **주소를 모르는 단계에서는 감지를 `Virtual(n)` 로 두어라.**
배선할 때 실주소를 채우며 `Normal`·`Latch` 로 바꾼다.

**§1 의 세 표(어휘·복귀·평소 값)는 «배선 후» 기준이다.** 배선 전에는 이렇게 내려 둔다:

| 설비 | 배선 후(표 기준) | **배선 전** |
|---|---|---|
| 실린더 ADV | `Latch/Normal` | `Latch/Virtual(100)` |
| 실린더 RET · 로봇 · 서보 | `Normal/Normal` | `Normal/Virtual(100)` |
| 센서·판정 비트 | `Virtual/Latch(30)` | `Virtual/Virtual(100)` |
| 일방 지령 | `Pulse(500)/Virtual(100)` | 같다 |

**동작(왼쪽 칸)은 그대로 두고 감지(오른쪽)만 `Virtual` 로 내린다** —
설비가 무엇인지는 배선과 무관하기 때문이다. 머리말에 «배선 시 되돌릴 Type» 을 적어 두어라.


### 평소 «꺼져 있는» 비트는 감지도 `Virtual` 이어야 한다

이 지침이 두 규칙을 동시에 가르쳤는데 **함께 지키면 반드시 멈추는 모델**이 나왔다:

- §12 — 이상·비상정지는 **총괄 비트**를 읽어라(`M_이상총괄` 은 참일 때 «이상»)
- §9·§12 — **조건 전용 API 도 어느 Work 가 Call 해야 한다**(`AI-W9`)

`이상총괄` 은 정상 운전 중 **0** 이다. 이것을 `Virtual/Latch(30)` 으로 Call 하면
**감지가 «입력이 설 때까지» 기다리므로 그 Work 가 영영 서지 않는다.**
파서 경고도 그래프 검증도 통과한다 — «문법은 맞지만 현실과 어긋나는» 부류다.

**규칙**: 조건으로만 읽는 비트 중 **평소 꺼져 있는 것**은 감지를 `Virtual` 로 둔다.

```
✗ API,라인상태.이상총괄,Virtual/Latch(30),,100MS,%MX1.1052.00, ← 영영 안 선다
✓ API,라인상태.이상총괄,Virtual/Virtual(100),,100MS,%MX1.1052.00,
```

`Virtual` 감지는 **시간이 지나면 완료로 본다**. Call 은 지나가고, 값 자체는 조건이 읽는다
(§13 — 조건에서 `/라인상태.이상총괄` 로 부정한다).

**가르는 기준은 «평소 값» 이다** — §1 어휘표도 이 기준으로 두 줄로 갈라 놓았다:

| 신호 | 평소 | 감지 |
|---|---|---|
| 안착센서·클램프 전진단 | 동작하면 **켜진다** | `Latch(n)` — 서는 것을 기다려도 된다 |
| 이상총괄·비상정지총괄 | 정상이면 **꺼져 있다** | `Virtual(n)` — 기다리면 안 된다 |
| 운전준비·자동모드 | 준비되면 켜진다 | `Latch(n)` |
| **값을 읽는 워드**(알람코드·위치값) | «정상이 0» 이거나 값이 변한다 | **`Virtual(n)`** — 특정 값을 기다리면 안 된다 |

### 원위치를 Call 사슬에 둘 것인가 Group 으로 묶을 것인가

예제는 `로봇.용접 > 로봇.원위치` 처럼 **사슬**에 두고, 점검표는 «Sub 를 Group 으로» 라 한다.
둘 다 맞다 — **가르는 것은 «다음 동작이 그 원위치를 기다리는가» 다**:

| | 어디에 |
|---|---|
| 다음 동작이 **그 자리를 비켜야** 할 수 있다(간섭) | **Call 사슬**(`작업 > 원위치`) — 택트에 들어간다 |
| 비켜도 그만이다(다음 공정이 다른 자리) | **Group 동반자 + `Ignore`** — 택트에서 빠진다 |
| **다음 차체가 그 자리를 기다린다**(셔틀 원점·반전 복귀) | **Call 사슬** — 다음 사이클이 못 시작하므로 택트에 들어가는 것이 맞다 |

**간섭이 있으면 사슬이 맞다** — 택트가 늘어나는 것이 실제이기 때문이다.
**단 사슬은 «같은 Work 안» 에서만 쓸 수 있다.** 간섭하는 둘이 다른 Work(Group 동반자)라면
사슬로 못 적으니 **뒤 동작의 `AutoAux` 에 «앞 동작 + 그 원위치» 를 걸어라**:

```
COND,차체.헤밍.헤밍로봇.진입,AutoAux,도포기.도포 & 도포기.원위치,,,
```
**차종 분기가 섞여 사슬로 못 적으면**(괄호 금지 — `AI065`) `;` 나열 + `AutoAux` 로 순서를 주어라.
택트는 같다 — 순서를 어디에 적었는가의 차이일 뿐이다.
지침 예제가 사슬인 이유도 로봇이 차체 위에 있기 때문이다.
**§11 이 «Sub 를 Group 으로» 라 한 것은 작업서가 Sub 로 적은 것**(다른 로봇의 원위치)을 말한다.

### 다점 동작을 Call 로 펼 것인가 묶을 것인가

용접 타점·볼트 체결·클램프처럼 **같은 동작을 여러 점에 반복**하는 자리다.

| 펴라(Call 여럿) | 묶어라(Call 하나) |
|---|---|
| 점마다 **조건이 다르다**(사양에 따라 한 점만 생략) | 조건이 같다 |
| 점마다 **순서가 뜻을 갖는다**(대각선 조임) | 순서가 없거나 동시다 |
| 점마다 **다른 설비**가 한다 | 한 설비가 연속으로 한다 |

**그 밖에는 묶어라** — `런너.본체결`(4점 19160MS) 하나면 된다.
점 수는 **시간에만** 반영한다 — **동작마다 타당이 다르다**(§8): 용접 2.6s · 너트런너 4.79s.

**펴야 하는 대표 자리는 «사양에 따라 한 점만 더 죄는» 경우다**(§13-A2 Call SkipAction).

### 디바이스를 어디서 끊을 것인가 — 현장 심벌이 답한다

§2 는 «차종마다 SYS 를 나눠라», §14 예제는 «한 디바이스에 API 4개». 둘이 부딪쳐 보인다.
**답은 현장 PLC 심벌에 있다.** 이름이 이미 계층을 갖고 있다:

```
RH_UPPER_SOL_KA4_1차클램프_ADV
└유닛┘ └종류┘ └차종┘ └부위─┘└동작┘
```

| 심벌 마디 | 모델에서 |
|---|---|
| 유닛 + 종류 (+차종) | **`SYS` 이름** — `RH상부클램프` · 차종이 갈리면 `KA4_상부클램프` |
| 부위 + 동작 | **API 이름** — `1차ADV` · `1차RET` · `2차ADV` … |

**하나의 솔레노이드 블록·하나의 서보 유닛이 `SYS` 하나다.** 그 안의 실린더 넷은 API 여덟(짝)이다.
r14 가 그 모양이다 — `상부클램프.1차ADV`·`1차RET`·`2차ADV`…

**심벌을 볼 수 없으면**: **«한 제어기가 묶어 움직이는 것» 을 하나로 본다.**
같은 밸브 블록에 물린 클램프 넷은 `SYS` 하나, 별도 유압 유닛을 쓰는 프레스는 따로.

**§2 의 «차종마다 나눠라» 는 «차종 마디가 심벌에 있으면» 이라는 뜻이다** —
차종 마디가 없는 공용 설비(기준핀·반송)는 하나로 둔다.

### 차종이 갈려도 «공용» 인 설비가 있다

§2 는 «차종마다 지그가 다르다» 고 하지만 **전부 다른 것은 아니다.**
차체를 처음 받는 자리와 마지막으로 확인하는 자리는 **차종과 무관**하다:

| 공용 | 차종별 |
|---|---|
| 기준핀 · 안착센서 · 반입/반출 컨베이어 | 차종 지그 · 차종 클램프 · 게이지 |
| 압착·리프트 같은 «받치는» 설비 | 형상을 잡는 설비 |
| 라인 상태 · 조작반 | — |

**이 공용 설비가 §13-A2 의 «전달자» 자리다.** 차종 고정 셋이 모두 생략될 수 있어도
기준핀은 반드시 돌므로 토큰을 넘길 수 있다. **차종 분기를 적기 전에 공용 설비부터 세워라.**

### 복귀(RET)의 Type — 실린더가 복동인지 단동인지가 정한다

지침 안에서 한때 `Virtual/Normal` 과 `Normal/Normal` 이 갈렸었다.
**답은 설비에 있다**:

| 실린더 | 복귀를 무엇이 미나 | RET 의 Type | OutTag |
|---|---|---|---|
| **복동** (코일 2개) | **복귀 코일** | `Normal/Normal` | **있다** |
| 단동 (스프링 복귀) | 스프링 | `Virtual/Normal` | 비운다 |

**차체라인은 거의 전부 복동이다.** 현장 PLC 에서 확인했다 —
`RH_UPPER_SOL_KA4_1차클램프_ADV` `%QX5.43.0.04` 옆에
`…_RET` `%QX5.43.0.05` 가 **나란히 있다**. 전진 코일과 복귀 코일이 둘 다 있다는 뜻이다.

**주소를 볼 수 있으면 세어 보라** — `SOL` 출력이 ADV/RET 둘 다 있으면 복동이다.
볼 수 없으면 **복동으로 가정하라**(`Normal/Normal`). 클램프가 스프링으로 풀리면
공기가 빠졌을 때 차체를 놓치므로, 차체라인에서 단동 클램프는 드물다.

**이 표는 «설비» 가 아니라 «API» 단위로 읽어라.**
**이 행이 `Virtual` 감지이고 조건 leaf 로 쓰인다면 InTag 를 반드시 채워라**(§13).
동작 API(`ADV`·`RET`·작업·원위치)는 `?` 여도 «그 동작이 끝났는가» 로 정확히 읽힌다. 한 설비가 두 줄에 걸칠 수 있다 —
갭계측기는 «지령을 받는 계측기»(`검사` = `Normal/Normal`)이면서
«값을 읽는 워드»(`판정코드` = `Virtual/Virtual(100)`)다.

| 분류 | 대표 설비 | 표준 API | ActionType / SensingType |
|---|---|---|---|
| 위치결정·클램프 | 클램프 · 핀 · 래치 | `ADV` `RET` | `Latch/Normal` · 복귀는 아래 |
| 구동 — 실린더·모터 | 실린더 · 모터 | `ADV` `RET` · `전진` `후진` | `Latch/Normal` |
| 구동 — **서보** | 인덱스서보 · 슬라이드서보 | **`PRG{n}_{차종}` `원점`** | `Normal/Normal` — **왕복 2개로 적지 마라**(§12) |
| 반송 — **수평 왕복** | 슬라이드 · 셔틀 · 트랜스퍼 | `ADV` `RET` · 서보면 `PRG{n}_{자리}` `원점` | `Latch/Normal` |
| 반송 — **수직 승강** | 리프트 · 승강테이블 | **`상승` `하강`** | `Latch/Normal` · **시간 실측 없음 → `?`**(§8) |
| 반송 — **연속반송** | 컨베이어 · 체인 | **`기동` `정지`** | `Normal/Normal` · **시간 실측 없음 → `?`** |
| 반송 — **반전·회전** | 반전기 · 턴테이블 · 회전지그 | **`{각도}_TURN` `{각도}_RETURN`** | `Normal/Normal` · **인덱스와 다르다** — 각도가 «자세» 다 |
| 회전 **락·언락** | 회전락 · 인덱스락 | `락` `언락` | **락 = `Latch/Normal`**(물고 있어야 한다) · **언락 = `Normal/Normal`** |
| 조립·가공 | 용접건 · 너트런너 · 도포 | `START` `체결확인` | `Normal/Normal` |
| 성형·프레스 | 헴프레스 · 클린칭 | `가압` `상승` | `Normal/Normal` · 목표값은 쓰기 API 의 OutTag `=값` |
| 성형 — 로봇 패스 | 로울러헤밍 · 심용접 | `프리헴1` `메인헴` · `원위치` | `Normal/Normal` · 시간은 `?`(§8) | `Normal/Normal` · 목표값은 OutTag `=값` |
| 접합 — 용접 외 | 레이저브레이징 · 실러 · 접착 | `브레이징` `도포` | `Normal/Normal` |
| 사상·마무리 | 그라인더 · 버핑 · 사상로봇 | `사상` `원위치` | `Normal/Normal` |
| 공급·피더 | 너트피더 · 볼트피더 · 파츠슈트 | `공급` `공급확인` | `Latch/Normal` · 확인은 `Virtual/Latch(30)` |
| 유체·재료 공급 | 실러펌프 · 접착제탱크 · 에어가압 | `가압기동` `가압정지` · **`압력NG코드`** | `Normal/Normal` · 판정 워드는 `Virtual/Virtual(100)` |
| 조립·가공(용접) | `SPOT` · `PED` · `HDL'G` | `타점` `반입` `반출` | `Normal/Normal` |
| 검사·계측 — **동작하면 켜지는 것** | 근접센서 · 안착센서 · 전진단 | `DETECT` `PARTON` | `Virtual/Latch(30)` |
| 검사·계측 — **평소 꺼져 있는 것** | 차종판정 · 이상총괄 · 비상정지총괄 | `{차종}` `이상총괄` | **`Virtual/Virtual(100)`** |
| 검사·계측 — **지령을 받는 계측기** | AUTO CHECK · 갭계측기 · 비전검사 | `검사` `원위치` | `Normal/Normal` (측정 시작 지령이 있다) |
| 검사·계측 — **판정 결과** | 위 계측기의 판정 | `판정코드` `판정OK` | **`Virtual/Virtual(100)`** — 평소 꺼져 있다 |
| 셋업 | 지그 교체 · 차종 전환 | `{차종}_차종` | `Normal/Virtual(200)` |
| 배출·집적 | 취출 · 낙하방지 | `ADV` `RET` | `Latch/Normal` |
| 본체·구조물 | 프레임 · 펜스 | 모델에 넣지 않는다 | — |

**본체·구조물은 CSV 에 넣지 않는다.** 움직이지 않는 것은 제어 대상이 아니다.

**`sensor` 표기는 v1 에서 모델을 바꾸지 않는다.** 파서가 받아들이지만 매퍼가 쓰지 않아
`AI-W10` 경고가 난다. 단일 API 디바이스의 `DONE` 더미는 센서에도 필요하기 때문이다(§7 참조).
문서용 표시로만 쓰고, 그것으로 무언가 달라지리라 기대하지 마라.

### 조립작업서의 설비 약어 (실측 — `3-장비&작업자` 시트)

작업서는 설비를 이 약어로 적는다. `SYS` 이름에 그대로 쓰면 현장 용어와 어긋나지 않는다.

| 약어 | 뜻 | 성격 |
|---|---|---|
| `SPOT` | 스팟 용접 로봇 | 로봇이 건을 들고 차체로 간다 |
| `PED` | 페데스탈 건(고정식) | 건이 고정, 로봇이 차체를 들고 간다 |
| `HDL'G` | 핸들링 로봇 | 반입·반출 전담 |
| `T/C` · `T/R` | 팁 체인저 · 팁 드레서 | 용접건 정비 — 사이클 밖 |
| `SEALER` | 실러 도포 | 도포 시간이 길다(8~20s) |
| `BOLTING` | 볼팅(너트런너) | 체결확인 신호가 따로 있다 |
| `각인` · `BRAZ'G` · `벤딩` | 각인 · 브레이징 · 벤딩 | 공정 특화 |
| `AUTO CHECK` | 자동 검사 | 판정 결과가 분기를 만든다 |

`T/C`·`T/R` 은 **모델에 넣지 않는다.** 용접건 정비는 생산 사이클이 아니라 보전 주기에 돈다.

## 2. 차종 분기 — 가장 먼저 정하는 것

차체라인은 한 셀에서 **여러 차종**을 흘린다. 차종이 다르면 **지그가 다르다**.

```
SYS,KA4_1차클램프,Passive,,,,
SYS,MV_1차클램프,Passive,,,,
SYS,RJ_1차클램프,Passive,,,,
```

**같은 «1차클램프» 로 합치지 마라.** 주소가 따로 있고 래더도 따로 제어한다.
S507 실측에서 이것을 합쳤다가 태그 48개가 통째로 사라진 적이 있다 — 같은 API 에 두 번째
태그가 오면 앞의 것만 남는다.

차종 선택 자체는 로봇이 알린다:

```
API,차종판정.KA4,Virtual/Virtual(100),,100MS,%IX3.30.0.12,
API,1호기RT.MV_차종,Normal/Virtual(200),,,,%QX4.01.5.14
API,1호기RT.RJ_차종,Normal/Virtual(200),,,,%QX4.01.5.13
```

### 차종 분기와 사양 분기는 다르다

둘을 섞으면 모델이 두 배로 부풀거나, 반대로 빠져야 할 공정이 남는다.

| | 차종 분기 (KA4 / MV / RJ) | 사양 분기 (도어유 / 도어무) |
|---|---|---|
| 무엇이 다른가 | **지그가 물리적으로 다르다** | **같은 설비**, 공정만 가감 |
| 표현 | `SYS` 를 나눈다 | `SkipAction` 으로 건너뛴다 |
| 근거 | 주소가 따로, 래더도 따로 | 작업서 두 시트의 공정 순서가 같다 |

작업서 실측(233/43 도어유 vs 도어무):

```
공정 순서 같다 (취출 → QR → 정렬 → 로딩 → 실링 → 언로딩 → 클램프 → 용접)
실링 시간 26s(도어유) vs 33s(도어무)
추가 공정 도어무에만 «S/OTR ASSY 언로딩» · «지그 언클램프»
```

사양은 이렇게 적는다 — 판정 신호 하나를 두고 **건너뛸 Work 에** `SkipAction` 을 건다:

```
SYS,사양판정,Passive,,,,
API,사양판정.도어유,Virtual/Virtual(100),,100MS,%IX3.00.0.01,
WORK,차체.ASSY언로딩,,로보트1.ASSY언로딩,,,
COND,차체.ASSY언로딩,SkipAction,사양판정.도어유,,,
```

«조건이 서면 건너뛴다» 이므로 `도어유` 가 참일 때 그 Work 를 지나친다.
반대로 걸고 싶으면 그룹 부정을 쓴다 — 속성 패널에서 «불만족 시 건너뜀» 으로 토글한다.

**시간이 다른 것은 분기가 아니다.** 실링 26s/33s 처럼 값만 다르면 둘 중 긴 쪽(보수적)이나
주력 사양 값을 쓰고 `#` 주석에 다른 값을 남긴다. 시간 때문에 Work 를 쪼개지 마라.

## 3. 로봇 핸드셰이크 — 규칙으로 못 맞추는 자리

> **IO 리스트가 없어도 API 는 짝으로 적어라** — 주소를 모르는 것과 구조를 모르는 것은 다르다.
> §12 「«추측하지 마라» 와 «응답을 읽어라» 는 부딪히지 않는다」를 보라.

PLC 가 «해도 된다» 를 내보내고 로봇이 «했다» 로 답한다. **둘이 한 쌍**이다.

```
API,5호기RT.셋팅안착,Normal/Normal,,?,%IX4.05.1.11,%QX4.05.4.09
 └ 안착완료(로봇→PLC) └ 안착가능(PLC→로봇)
```

**쌍을 이름으로 추측하지 마라.** S507 실측에서 1·3호기는 `IN_기동OK` 가 `OUT_1차_진입OK` 와
짝인데, 5호기는 같은 `IN_기동OK` 가 `OUT_자동기동` 과 짝이다. 설계자만 아는 사실이다.
IO 리스트가 있으면 그것을 따르고, 없으면 `?` 로 두고 주석에 «확인 필요» 를 남겨라.

방향은 주소가 정한다 — `%QX` 가 PLC 출력(가능), `%IX` 가 PLC 입력(완료)이다.

### 답이 없는 지령도 있다

`작업완료_RST` 처럼 **출력만 있고 입력이 없는** 신호가 있다. 로봇이 답하지 않는 일방 지령이다.
Action 은 펄스로, Sensing 은 가상으로 둔다 — 기다릴 확인 신호가 없기 때문이다.

```
API,RT5호기.작업완료RST,Pulse(500)/Virtual(100),,,,%QX4.05.4.08
 └ InTag 가 비어 있다
```

`Virtual` 을 쓰지 않고 `Normal` 로 두면 오지 않을 확인을 영원히 기다린다.

### API 행만 적고 부르지 않으면 사라진다

`API` 행을 적어도 **어느 `WORK` 도 그 Call 을 부르지 않으면 ApiDef 가 만들어지지 않는다.**
디바이스 캐스케이드가 Call 을 기준으로 설비를 세우기 때문이다.

```
API,RT5호기.자동기동,Normal/Normal,,2S,%IX4.05.0.12,%QX4.05.4.13 ← 적었지만
 부르는 WORK 가 없으면 없는 것
```

IO 주소까지 적어 놓고 모델에는 없는 상태가 되므로, 파서가 `AI-W9` 경고로 알린다.
**경고가 뜨면 둘 중 하나다** — 그 API 를 쓰는 Work 를 빠뜨렸거나, 애초에 불필요한 행이다.

## 4. 다점 확인센서 — 먼저 «판정 비트» 를 찾아라

클램프 하나에 리드스위치가 여럿 달린다. 실제 현장에서 확인했다 —
`RH_UPPER_RS_KA4_1차클램프_RET1`~`RET5`, **RET 쪽만 5개**다.

### 1순위 — PLC 가 만든 판정 비트를 쓴다

**거의 언제나 이 방법이다.** 현장 PLC 는 리드스위치를 AND 해서 이름 붙인 비트를 이미 갖고 있다:

```
%MX1.2051.04 S507R_M_KA4_1차클램프_후진단 ← 다섯을 AND 한 결과
```

그러면 API 는 하나로 끝난다:

```
API,상부클램프.1차RET,Normal/Normal,,602MS,%MX1.2051.04,%QX5.43.0.05
```

**리드스위치 다섯을 모델로 옮기지 마라.** .000초**다(수집 해상도 209ms).
조건으로 AND 를 재현해도 결과가 같다. 다점의 목적은 «동시 확인» 이 아니라
**«하나가 죽었을 때 검출»** 이고, 그 검출은 PLC 가 판정 비트를 만들며 이미 한다.

### 2순위 — 판정 비트가 없을 때만 조건으로 엮는다

신설 설비라 아직 판정 로직이 없거나, IO 리스트만 있고 PLC 를 못 볼 때다.

```
# 대표는 API 의 InTag
API,클램프.RET,Normal/Normal,,1S,%MX1.2051.04,%QX5.43.0.05

# 나머지 확인점을 센서 API 로 세운다 (조건 leaf 는 Device.Api 여야 하므로)
SYS,클램프확인,Passive,,,,
API,클램프확인.RET2,Virtual/Latch(30),,100MS,%IX5.41.0.08,
API,클램프확인.RET3,Virtual/Latch(30),,100MS,%IX5.41.0.09,

WORK,차체.전수확인,,클램프확인.RET2 ; 클램프확인.RET3,,,
COND,차체.전수확인.클램프확인.RET2,AutoAux,클램프확인.RET3,,,
```

. 쪼개지지 않는다.

**이 방법을 쓰면 주석에 이유를 남겨라** — «판정 비트를 찾지 못해 직접 엮었다».
나중에 PLC 를 볼 수 있게 되면 1순위로 바꿔야 하기 때문이다.

### 서로 다른 부품의 2점은 다른 이야기다

`PXS_KA4_FDR_PART1` 과 `PART2` 는 **부품 두 개**를 각각 본다.
같은 실린더를 여러 각도에서 보는 다점 확인과 다르다 — 이쪽은 **조건 AND 가 맞다**(§12).

## 5. 인덱스 회전 — 각도가 곧 스테이션

8분할 인덱스 테이블은 각도마다 다른 공정이 선다.

```
API,인덱스.0_KA4_TURN,Normal/Normal,,7260MS,%MX1.1073.04,%QX3.32.0.01
API,인덱스.135_D_RETURN,Normal/Normal,,7260MS,?,?
API,인덱스.180_RJ_TURN,Normal/Normal,,7260MS,?,?
API,인덱스.270_D_TURN,Normal/Normal,,7260MS,?,?
```

각도는 **API 이름에** 넣는다. 별도 열이 없고, 각도별로 다른 Work 가 걸리기 때문이다.

### 언락 → 회전 → 락 은 한 묶음이다

회전할 때마다 이 셋이 되풀이된다. **하나라도 빠지면 테이블이 돌다 멈추거나 파손된다.**

```
WORK,캐리어.언락,,인덱스락.언락,,,
WORK,캐리어.KA4회전,,인덱스서보.0_KA4_TURN,,,
WORK,캐리어.락,,인덱스락.락,,,
ARROW,캐리어.언락,Start,캐리어.KA4회전,,,
ARROW,캐리어.KA4회전,Start,캐리어.락,,,
```

**Work 사이 `Start` 는 «A 완료» 를 보장한다**(형식 절 — Work 완료 = 안의 Call 전부 완료).
그러니 Work 를 나눠 이었다면 조건이 따로 필요 없다.

**배선 후에는 한 겹 더 있다.** `Start` 가 보장하는 것(«언락 Work 가 끝났다»)과
leaf 가 읽는 것(«지금 락이 빠져 있는가»)은 **다른 사실**이다 — 끝난 뒤에 다시 물렸을 수 있다.
**움직이면 위험한 자리**(회전·승강 전의 락 상태)는 배선 후에도 조건을 남겨라.

**조건이 필요한 것은 «한 Work 안» 이다.** `;` 로 나열한 Call 과 `Group` 동반자에는
**순서가 없다** — 언락·회전·락을 한 Work 에 `;` 로 두면 동시에 나간다.
**같은 Work 안에서 순서를 주려면 `>` 사슬이나 Call `AutoAux` 로 못 박아라.**

```
COND,캐리어.KA4회전.인덱스서보.0_KA4_TURN,AutoAux,인덱스락.언락,,,
COND,캐리어.KA4작업.KA4_지그.클램프,AutoAux,인덱스락.락,,,
```

락 상태로 돌리면 테이블이 파손되고, 돌아가는 중에 클램프하면 간섭이 난다.

### 같은 락/언락 API 를 여러 번 부른다

8분할이면 회전이 여러 번이고 그때마다 같은 락·언락을 쓴다. **Work 는 늘고 API 정의는 하나다.**

```
WORK,캐리어.언락,,인덱스락.언락,,, ← 1회전
WORK,캐리어.언락2,,인덱스락.언락,,, ← 2회전 같은 API
WORK,캐리어.언락3,,인덱스락.언락,,, ← 3회전
API,인덱스락.언락,Latch/Normal,,500MS,%IX3.31.0.01,%QX3.31.0.01 ← 정의는 한 줄
```

가 ApiDef 2개를 공유한다.
**API 행을 회전 횟수만큼 복제하지 마라** — 같은 이름으로 적으면 정의가 덮어써져 `AI067` 오류다.

### 각도 = 차종 스테이션

S507 실측 각도 구성:

```
0° KA4 TURN 135° D RETURN
180° RJ TURN 270° D TURN
315° MV RETURN
```

`TURN` 은 작업 위치로 보내는 회전, `RETURN` 은 원위치로 되돌리는 회전이다.
각도마다 다른 차종 지그가 서므로, 그 각도에서 도는 Work 는 해당 차종 지그만 부른다.

## 6. Flow 개수 = Capa — 차체라인은 대개 1이 아니다

Flow 는 **동시에 보유하는 차체 수**다. 스테이션 수도, 공정 수도 아니다.

**지그 셀 하나**라면 보통 Capa 1 이다 — 한 대를 고정하고 작업한 뒤 내보낸다.

```
FLOW,차체,,,,, ← 셀 1개 = 차체 1대
```

**라인 전체**라면 다르다. 차체라인은 파이프라인이라 여러 대가 동시에 흐른다.
SIDE OTR COMPL LINE 은 스테이션이 7개지만, 동시에 물려 있는 차체는 그보다 적다 —
버퍼와 이송 구간이 있기 때문이다. 작업서의 **UPH 와 택트**로 가늠한다:

```
동시 보유 대수 ≈ 라인 총 소요시간 ÷ 택트타임
```

각 Flow 는 **제 Source·Sink·재무장을 따로** 갖는다. 한 Flow 의 배출이 다른 Flow 를 리셋하지 않는다.

```
FLOW,차체A,,,,,
FLOW,차체B,,,,,
WORK,차체A.투입,Source,,,,
WORK,차체A.배출,Sink,,,,
WORK,차체B.투입,Source,,,,
WORK,차체B.배출,Sink,,,,
ARROW,차체A.배출,Reset,차체A.투입;차체A.안티스패터,,,
ARROW,차체B.배출,Reset,차체B.투입;차체B.키2용접,,,
```

자세 변경(회전·승강)은 같은 차체이므로 Flow 를 늘리지 않는다.

## 7. 재무장 — 차체라인에서 빠뜨리기 쉬운 곳

배출이 앞단을 전부 리셋해야 다음 차체를 받는다. **한 줄로 몰아 적는 것이 읽기 쉽다.**

```
ARROW,제품.배출,Reset,제품.투입;제품.클램프;제품.용접;제품.검사,,,
ARROW,제품.투입,Reset,제품.배출,,,
```

두 번째 줄을 잊으면 배출 자신이 재무장하지 않아 한 대만 흘리고 멈춘다.

**주의**: 투입(Source)으로 되돌아오는 것은 반드시 `Reset` 이다. `Start`/`StartReset` 을 걸면
자동 시작이 막혀 «Source 인데 선행 있음» 경고가 난다.

### 파이프라인에서 Flow 경계의 Source 는 «받는 자리» 다

스테이션마다 Flow 를 두면 두 번째 Flow 부터는 «투입» 이 없다 — 앞 스테이션이 넘겨 준다.
**그 자리의 Source 는 «안착 확인» 이 맡는다.**

§10 의 «센서 Work 를 Source 로 만들지 마라» 는 **투입 Work 가 따로 있는데도**
센서를 Source 로 세운 경우를 말한다. 경계에서는 안착 확인이 곧 투입이므로 해당하지 않는다.

```
WORK,차체B.투입,Source,ST2안착센서.안착확인,,, ← 앞 스테이션이 놓은 것을 확인하는 자리
WORK,차체A.배출,Sink,반송.송출 > 반송.원점,,, ← 앞 Flow 는 자기 Sink 로 닫는다
```

물리적 인계는 **같은 설비를 양쪽이 부르는 것**으로 표현된다(§13-C).

### ResetReset 은 Flow 를 가로질러도 된다

2열 병렬 지그는 차체라인에서 가장 흔한 구조인데, 여기서 규칙 셋이 서로 다르게 읽힌다:

- §6 — Flow 수 = 동시 보유 차체 수 → 2열이면 **Capa 2**
- §7 예제 — ResetReset 을 **한 Flow 안**에서 걸었다
- §10 — «Flow 를 가로지르는 재무장» 을 실수로 적었다

**실측으로 갈랐다. 가로질러도 된다**(적재 OK · Source 선행 0 · 토큰 도달불가 0):

```
FLOW,차체A,,,,,
FLOW,차체B,,,,,
ARROW,차체A.용접,ResetReset,차체B.로딩,,, ← Flow 를 가로지른다
```

**가르는 기준은 «토큰이 넘어가는가» 다**:

| 무엇을 가로지르나 | 되나 | 왜 |
|---|---|---|
| `Start` / `Reset` 으로 다른 Flow 의 Work 를 이음 | **안 된다** | 토큰이 그 선을 따라 **샌다** |
| `ResetReset` | **된다** | **자리의 교대**일 뿐 토큰을 옮기지 않는다 |

§10 이 금지하는 것은 앞쪽이다 — «배출 → 다른 Flow 의 투입» 같은 연결.
**`ResetReset` 은 «내가 비었으니 너를 쓸 수 있다» 는 말이지 «너에게 넘긴다» 가 아니다.**

한쪽에 `Finish` 를 주어 먼저 도는 쪽을 정한다(§13-C 의 비대칭 반납 조건과 같은 이치다).

### 병렬 2열 지그 — 상호 재무장(ResetReset)

차체라인은 두 자리를 번갈아 쓰는 일이 잦다. A 가 용접되는 동안 B 는 로딩한다.
**두 자리가 서로를 리셋**해야 끊김 없이 돈다 — 이것이 `ResetReset` 이다.

```
ARROW,차체.A용접,ResetReset,차체.B로딩,,,
```

A 용접이 시작되면 B 로딩 자리가 비워지고, B 로딩이 시작되면 A 용접 자리가 비워진다.
한 줄이면 족하다 — 양방향이므로 반대 줄을 또 적지 마라.

**한쪽은 초기 상태를 `Finish` 로 두어야 첫 사이클이 선다.** 둘 다 Ready 면 서로를 기다린다.

```
WORK,차체.B로딩,Finish,반입로봇.B반입,,,
```

`Finish` 는 TokenRole 이 아니라 «초기 상태» 표시다. `Source`/`Sink` 와 달리 토큰을 만들거나
없애지 않는다.

### ResetReset 은 설비 안에도 자동으로 생긴다

.
나머지 6개는 디바이스 캐스케이드가 만든 **설비 내부 쌍**이다.

```
[트윈지그셀] 차체.A용접 → 차체.B로딩 ← 내가 적은 것
[지그A] 클램프 → 언클램프 ← 동작/복귀 쌍
[센서A] PARTON → DONE ← 단일 API 라 DONE 더미
```

**단일 API 디바이스는 `DONE` 더미를 받는다.** 반복 동작하려면 재무장할 상대가 있어야 하고,
ApiDef 의 Tx/Rx 를 갈라 «동작 송신 ~ 완료 수신» 을 만들기 위해서다. 센서도 마찬가지다 —
`DONE` 이 보이더라도 잘못된 것이 아니다.

## 8. 시간 — 실측이 있으면 실측을 쓴다

### 시간은 세 종류이고, 소유자가 다르다

DS2 CORE 명세 `CHK.TIME_ROLE` 이 가르는 셋이다 — **합치면 안 된다**:

| 종류 | 누가 갖나 | CSV 어디에 |
|---|---|---|
| **물리 duration** | 말단 Work (장치가 실제로 움직인 시간) | `API` 행의 `Time` 열 |
| **정책 시간** | ApiDef 의 출력·센싱 정책 | `Latch(30)` · `Pulse(500)` 처럼 **Type 열 안** |
| 상위 예상 시간 | 호출하는 쪽의 기대 | v1 에 자리가 없다 — 적지 마라 |

`API,지그.전진,Latch/Normal,,600MS,…` 에서
`611MS` 는 **실린더가 움직인 물리 시간**이고, `Latch` 는 **출력을 유지한다는 정책**이다.
같은 행에 붙어 있어도 다른 것이다.

**Call 이 있는 Work 에 시간을 또 적지 마라.** 파서가 `AI021` 로 막지만, 막히는 이유를 알아야 한다 —
장치의 시간은 말단 Work 가 이미 갖고 있고, 두 번 적으면 같은 시간을 이중 정의하게 된다.

### 시간에는 출처가 둘 있고, 둘은 같은 것을 재지 않는다

| | 무엇을 재나 | 예: 클램프 |
|---|---|---|
| **조립작업서** 「시간」 열 | 사이클 **설계값** — 확인·여유를 포함한다 | **5.0s** |
| **PLC 신호 실측** ON 유지 | 신호가 켜져 있던 **실제 시간** | **0.61s** |

**8배 차이가 난다. 둘 다 맞다.** 작업서는 «이 공정에 이만큼을 배정한다» 이고,
실측은 «실제로 이만큼 걸렸다» 이다. 어느 쪽이 틀린 것이 아니다.

- **동작을 재현하는 모델**(시뮬레이션·인과 검증)에는 **실측**을 쓴다
- **택트를 검증하는 모델**에는 **작업서**를 쓴다 — 여유가 들어 있어야 현장과 맞는다

섞어 쓰면 안 된다. 한 모델 안에서 **주 출처를 정하고**, 어느 쪽인지 머리말 주석에 적어라.
**한 출처가 전부를 덮지 못할 때가 있다**(용접 셀은 센서 시간이 작업서에 없다) —
그때는 빌려 오되 **빌린 행을 주석에 밝혀라.** 몰래 섞는 것만 금지다.

**빌려도 되는 범위는 «같은 기구» 까지다.** 실린더 값을 다른 실린더에 쓰는 것은 되지만,
**8분할 인덱스 7.26s 를 180° 반전기에 빌리는 것은 안 된다** — 각도도 관성도 다르다.
**기구가 다르면 `?` 가 정직하다.**
**반대로 «자료 없음» 목록에 이름이 있어도 «같은 기구» 면 빌려라** —
게이트 스토퍼는 솔레노이드 실린더이므로 0.60s 를 쓸 자격이 있다. **목록은 공정 이름이지 기구가 아니다.** 빌린 근거가 «둘 다 회전한다» 뿐이면 빌린 것이 아니라 지어낸 것이다.

| 센서 감지 | 100MS | — | 사실상 즉시 |

### 택트는 실측 로그의 «중앙값» 이다

2일치 현장 로그(`sx_field_log.sqlite` · 259태그 · 128,605샘플)에서 재었다:

| 기준 신호 | 상승 횟수 | **중앙값** | 평균 | 최대 |
|---|---|---|---|---|
| `RUN_SFT2_ADV` (런너 사이클) | 733 | **52.0s** | 62.6s | 598s |
| `RT_IN_기동OK` (로봇 사이클) | 665 | **64.8s** | 76.8s | 599s |

**평균을 쓰면 안 된다.** 최대 598초는 점심·정지 구간이고, 평균은 그것에 끌려 올라간다.
중앙값은 흔들리지 않는다. 2차종 이상이 섞이는 신호(`1차클램프_ADV` 중앙값 134s)는
그 차종이 올 때만 동작하므로 **택트가 아니라 «그 차종의 도래 간격»** 이다.

측정 전에 정하라 — **무엇의 주기를 재는가.** 설비 주기와 차종 도래 간격은 다르다.

### 자료가 없는 공정 — `?` 가 절반이어도 모델은 선다

**두 출처 어디에도 없는 공정이 있다.** 아래가 그 목록이다:

| 없는 것 | 왜 |
|---|---|
| 수직 승강 · 연속반송 · 게이트 | 실측 태그가 RH 지그·로봇 계열뿐이다 |
| 반전·턴테이블 | 인덱스(8분할 수평)와 각도·관성이 다르다 |
| 유체 가압·토출 · 실러 퍼지 | 작업서에 행이 없다 |
| 각인 · 사상 · 버핑 · 집진 | 〃 |
| 레이저 브레이징 · 계측기 복귀 · 계측 워드 읽기 | 〃 |

**이 계열이 주인공인 셀은 Time 의 절반이 `?` 가 된다. 그것이 정상이다.**

**할 일 셋**:
1. **지어내지 마라.** «차종 셋을 같은 값으로» 같은 통일도 자료가 없으면
 **«자료 없음» 을 숫자로 위장한 것**이다 — `?` 가 정직하다
2. **머리말에 «`?` 가 N 개이고 무엇인지» 를 적어라.** 받는 사람이 무엇을 채워야 하는지 안다
3. **시간 축 점검(§0 사이클 합 · §9 Main 누계)은 유예한다** — 사후 변명이 아니라 **사전 선언**이다

**`?` 는 결함이 아니라 «아직 모른다» 는 정직한 기록이다.**
구조(Work·Arrow·Call·조건)는 시간 없이도 전부 설 수 있고, **그것이 이 형식의 값어치다** —
배선 전에 모델을 세우고 배선하면서 채운다.

### 작업서 설계값 — PLC 실측에 없는 공정

§8 앞 표는 S507R(정렬·볼트체결) **PLC 실측**이라 용접·실러·검사가 없다.
아래는 **조립작업서**(SIDE OTR · FLR)에서 가져온 값이다 — **출처가 다르므로 섞지 마라**(위 표 참조).

| 동작 | 작업서 값 | 근거 |
|---|---|---|
| 용접 1타 | **2.6s** | FLR F113 «19타 49.4s» |
| SPOT 스테이션 1곳 | 12~20s | 타점 수 × 2.6s + 이동 |
| PED 스테이션 1곳 | 8~15s | 로봇이 차체를 들고 간다 |
| HDL'G 반입/반출 | 3~5s | 편도 |
| 실러 도포 | 8~20s | 도포 길이에 비례 (구조용 장척은 26~33s) |
| 자동 검사 | 5~10s | 측정 점수에 비례 |
| 로딩 / 언로딩 | 8~10s | FLR F113 |
| 클램프 / 언클램프 | 5s / 3s | FLR F113 (확인·여유 포함한 설계값) |

**프레스 성형·헤밍·계측기 워드 읽기는 어느 자료에도 없다.** 지어내지 말고 `?` 로 두어라.

### 실측이 뒤집은 것 세 가지

1. **인덱스 회전은 «3~5s» 가 아니라 7.3s 다.** 2배 가까이 틀렸다.
2. **슬라이드를 하나의 범위로 묶을 수 없다.** 긴 것 4s, 짧은 것 0.9s — 4배 차이다.
 디바이스 이름에 `L`/`T` 가 붙어 있으면 다른 물건이라는 뜻이다.
3. **로봇 이동은 «2~6s» 가 아니라 12~15s 다.** 티칭 경로만이 아니라 안전 감속이 들어간다.
4. **용접 1타는 «0.8~2s» 가 아니라 2.6s 다.** FLR F113 이 19타에 49.4초다.
 타점 수가 작업서에 적혀 있으면(「LHD/RHD:19」) 나누어 타당을 구할 수 있다.

### 실측 태그가 다 «동작 시간» 인 것은 아니다

DS2 디자인 패턴 Ver110 이 경고하는 함정이다 — **Call 경과 시간을 장치의 동작 시간으로
옮기지 않는다.** 신호가 켜져 있던 시간에는 대기와 상태 유지가 섞여 있을 수 있다.

실측 표에 최소·최대가 있으면 **폭(최대−최소)으로 가를 수 있다**:

| 폭 | 뜻 | 쓰는 법 |
|---|---|---|
| **평균의 0.25배 미만** | 순수 동작 | 평균을 그대로 쓴다 |
| 0.25 ~ 1배 | 대기가 섞였다 | **최소값**을 쓴다 |
| **평균을 넘는다** | 상태 유지 신호 | **평균을 쓰지 말고 최소값을 써라** |

**이 폭 규칙은 «PLC 실측» 전용이다** — 작업서 설계값에는 폭이 없다.
주 출처가 작업서면 §9 의 «폭» 점검은 **유예**한다.

S507R 실측으로 확인한 결과:

- `1차_진입OK` 12.32s, 폭 0.57 (**0.05배**) → 반복성 있는 동작. 그대로 쓴다
- `작업완료_RST` 30.3s, 폭 51.1 (**1.69배**) → 상태 유지. 평균 대신 **최소 10.3s** 를 쓴다
- `차종_KA4` 54s, 폭 81 (**1.50배**) → 사이클 내내 켜져 있는 상태. 동작이 아니다

**짧은 동작은 절대 폭도 함께 보라.** 0.9초 동작의 폭 0.65초는 비율로 0.69배지만
절대값은 0.65초라 측정 산포에 가깝다. **폭이 1초 미만이면 순수 동작으로 본다.**

### 평균을 믿으면 안 되는 자리

`로봇 작업 완료` 는 평균 30.3s 인데 실측 범위가 **10.3~61.4s — 6배**다.
차종·사양마다 타점 수가 다르기 때문이다. 이런 항목은

- 모델에는 평균을 적되 **주석에 [min~max] 를 남긴다**
- 택트를 계산할 때 **평균이 아니라 최대**를 쓴다 (설비는 최악의 차종도 넘겨야 한다)

**ADV 와 RET 은 거의 같다** (실측 0.611 vs 0.602 — 차이 9ms).
**그러나 늘 그런 것은 아니다** — 같은 표의 인덱스 락/언락(0.61/0.71)과
L슬라이드 전진/후진(3.58/4.03)은 실측이 갈린다. **기구가 다르면 다르다.**
**짝 동작 시간을 굳이 다르게 «지어내지» 마라** — 규칙은 «지어내기» 에만 걸린다.
**출처가 이미 갈라 놓았으면 그대로 옮겨라**(작업서 «클램프 5s / 언클램프 3s» 는 갈린 실측이다).
근거 없이 둘을 다르게 적을 때만 문제다 — 그때는 둘 다 같은 값(0.60s)으로 둔다.

적을 수 없으면 `?` 로 두어라. 비우면 500ms 가 들어가는데, 그것이 맞는 경우는 드물다.
`?` 가 남기는 `AI-W2` 는 지우지 않아도 되는 경고다(§14).

## 9. 자가 점검 — 내보내기 전에

항목이 많다. **주제별로 끊어서** 보라 — 위에서부터 훑으면 뒤가 흐려진다.

### 규모와 구조 — 무엇을 몇 개로 나눌 것인가

```
□ FLOW 행 개수가 «동시에 물리는 차체 수» 와 같은가 (스테이션 수가 아니다)
□ 차종마다 SYS 행이 따로 있는가 (합치지 않았는가)
□ LH/RH 가 «유닛» 인지 «한 지그 안의 위치» 인지 구분했는가 (이 지침은 RH 유닛 기준)
□ 본체·구조물을 넣지 않았는가
□ 차종 분기는 SYS 로, 사양 분기는 SkipAction 으로 나눴는가 (뒤바꾸지 않았는가)
□ Flow 를 복사했다면 ARROW 의 Flow 이름을 전부 치환했는가 (A 와 B 가 섞이지 않았는가)
□ 같은 디바이스를 Flow 마다 똑같이 다뤘는가 (AI-W12)
□ IO 주소가 API 마다 다른가 (복사해 붙이지 않았는가 — AI-W13)
 ※ 주소를 전부 `?` 로 두었다면 IO 관련 점검은 **유예**한다. 미적용은 실패가 아니다
□ 서보를 왕복 2개가 아니라 «프로그램 번호» 로 적었는가 (§12)
□ 영역 문자(%I/%Q/%M)가 실제 PLC 와 맞는가 (숫자만 가져오지 않았는가)
□ InTag 에 raw 센서 대신 «전진단/후진단» 판정 비트를 썼는가
 ※ 조건 leaf 로 쓰는 API 는 특히 — raw 신호면 «끝난 순간 꺼져» 조건이 무너진다(§13)
□ 디바이스를 «유닛+종류» 로 끊었는가 (부위·동작은 API — §1). 차종 마디가 있는 것만 ×차종 (한 차종을 빠뜨리지 않았는가)
```

### 흐름 — 토큰이 돌아오는가

```
□ **Flow 마다** Source 와 Sink 가 하나씩 있는가 (모델 전체가 아니라 Flow 기준 — Capa 2 면 2쌍)
□ 배출 → 앞단 전부 Reset 이 있는가
□ 투입 ← 배출 Reset 이 있는가 (자기 재무장)
□ 원위치를 **제자리**에 두었는가 — 간섭이 있으면 Call 사슬, 없으면 Group 동반자(§1)
□ 번갈아 쓰는 두 자리에 ResetReset 을 걸고 한쪽에 Finish 를 줬는가
□ Flow 를 가로지른 것이 `ResetReset` 뿐인가 (`Start`/`Reset` 이 넘으면 토큰이 샌다 — §7)
□ 고정과 작업을 직렬로 늘어놓지 않고 Group + Call AutoAux 로 적었는가
```

### 조건 — 무엇을 기다리는가

```
□ 인덱스 회전 앞에 언락이 있는가
□ 회전마다 언락→회전→락 세 Work 가 다 있는가 (Work 로 나눴으면 순서는 보장된다 — 배선 후 «움직이면 위험한 자리» 만 조건을 남겨라 §5)
□ 다점 확인센서에 PLC 판정 비트를 먼저 찾아봤는가 (없을 때만 조건으로 엮는다 — §4)
□ SkipAction 조건에 (R)/(F) 를 쓰지 않았는가 (엔진이 접어 버려 의미가 없다)
□ Work 조건에 SkipAction 만 썼는가 (AutoAux/ComAux 는 Call 전용 — AI014)
□ 생략될 수 있는 Work 의 완료를 조건으로 걸지 않았는가
□ Group 전달자가 «생략되지 않는» Work 인가 (동반자는 생략돼도 된다 — §13-A2)
□ 공유 장치를 쓰는 조건에 «반납 완료» 를 따로 걸었는가
□ 공유 설비의 API 를 함부로 나누지 않았는가 (같은 동작이면 하나 — §13-C)
□ 반납 조건을 한쪽에만 걸었는가 (양쪽 대칭이면 첫 사이클에 멈춘다 — §13-C)
□ 라인 전체에 걸리는 허가 조건(자동운전·안전문·비상정지)을 ComAux 로 모았는가
 ※ 그 Work 에서 **반드시 실행되고 먼저 도는** Call 에 건다. 생략될 수 있으면 대안 전부(§13-C)
```

### Call 과 Group — 한 Work 안에서

```
□ 같은 락/언락 API 를 회전 횟수만큼 복제하지 않았는가 (Work 만 늘린다)
□ Call Group 을 건 자리에 실제로 옮길 선행이 있는가
□ 동시에 나가야 하는 Call 을 Group 으로 묶었는가 (`;` 나열은 선행을 못 물려받는다)
```

### 시간 — 어느 시계를 읽었는가

```
□ 시간을 모르는 곳에 ? 를 넣었는가 (빈 칸으로 두지 않았는가)
□ Main 체인의 누계가 작업서 택트와 맞는가 (단순 합계와 다르다)
 ※ 시간에 `?` 가 하나라도 있으면 이 항목은 **유예**한다 — 누계를 낼 수 없다
□ 실측 자료가 있으면 추정 대신 실측을 썼는가 (§8)
□ **주 출처**를 정하고, 다른 출처에서 **빌린 행을 주석에 밝혔는가**(§8 — 몰래 섞는 것만 금지다)
□ 실측 태그의 폭을 보고 «동작 / 대기 / 상태» 를 갈랐는가
□ 택트를 평균이 아니라 중앙값으로 구했는가 (정지 구간이 평균을 끌어올린다)
□ 머리말에 주소 출처(실주소 / 예시 / 미정)를 밝혔는가
□ 물리 duration(Time 열)과 정책 시간(Latch/Pulse)을 섞지 않았는가
□ 편차가 큰 동작에 [min~max] 주석을 남겼는가
```

### IO 와 표기 — 배선으로 이어지는가

```
□ 로봇 API 에 지령(OutTag)과 응답(InTag)을 모두 적었는가
□ 차종 판정 신호를 실제 계열(PXS 등)에서 찾았는가
□ «동시» 를 말하기 전에 측정 해상도를 확인했는가
□ 이상·알람을 옮겨 적지 않고 «총괄» 비트로 읽었는가
□ 평소 꺼져 있는 비트의 감지를 `Virtual` 로 두었는가 (`Latch` 면 영영 안 선다 — §1)
□ **조건에서만 쓰는 API 도 어느 Work 가 Call 하는가 (AI-W9 — 자주 틀리는 자리)**
□ 로봇 API 마다 IN/OUT 이 짝을 이루는가 (모르면 ? 와 주석)
□ 모든 Call 에 대응하는 API 행이 있는가
□ AI-W9 경고가 없는가 (적어만 두고 부르지 않는 API 가 없는가)
□ 답이 없는 지령(작업완료_RST 등)에 Virtual 감지를 줬는가
□ «순간» 이 필요한 자리에 (R)/(F) 를 썼는가 (버튼·이탈 감지)
□ 숫자를 읽는 신호에 :DINT 등 자료형을 적었는가 (생략하면 BOOL 로 뭉개진다)
□ `=값` 을 자리에 맞게 적었는가 (조건은 COND · 내보낼 값은 OutTag)
□ 액추에이터마다 짝 동작(원위치·언클램프·후진)을 적었는가
□ API Detail 에 `sensor` 를 적지 않았는가 (v1 미구현 — AI-W10)
□ 그 작업서의 범례를 읽고 기호를 해석했는가
```

### 마지막 — 실제로 돌려 봤는가

```

```

## 11. 조립작업서 타임차트 → CSV (가장 확실한 출처)

작업서 `5. {공정번호}_{공정명}` 시트에는 **실측 타임차트**가 그대로 있다. 추정하지 말고 이것을 옮겨라.

```
구분 번호 기호 작업내역 시작 시간 누계 Main/Sub
로보트1 1 UL 부품 언로딩(S/OTR) 0 8 8 Sub
로보트2 4 L 부품 취출(팔레트) 0 8 8 Main
 5 E QR코드 리더기 인식 8 8 16 Main
 8 SL 실링작업(구조용) 30 26 56 Main
조립치구 11 C 지그 클램프(S/EXTN) 64 3 67 Main
로보트3 12 W 용접 67 36 103 Main
조립치구 14 UC 지그 언클램프(ALL) 103 3 106 Main
```

### 옮기는 규칙

| 작업서 | csvForAI |
|---|---|
| `구분`(로보트1 · 조립치구 …) | `SYS` Passive 이름 |
| `기호` + `작업내역` | `API` 이름 (`로보트2.취출`) |
| `시간` | `API` 행의 Time |
| `시작`·`누계` 순서 | `ARROW` 의 Start 사슬 |
| `Main` | 주 경로 — Start 로 직렬 연결 |
| `Sub` | 병행 — `Group` 으로 묶고 `Ignore` |

### 기호 체계는 작업서마다 다르다

**범례를 먼저 읽어라.** SIDE OTR 과 FLR 은 다른 기호를 쓴다:

| 작업서 | 기호 |
|---|---|
| SIDE OTR | `SPOT` · `PED` · `HDL'G` · `T-C` · `T-R` · `SEALER` · `BOLTING` |
| FLR | `L`(로딩) · `UL`(언로딩) · `C`(클램프) · `UC`(언클램프) · `W`(용접) · `SL`(실링) · `T`(체결) |

앞 작업서에서 익힌 기호를 다음 작업서에 그대로 적용하면 틀린다. 시트 상단 2~6행의 범례가
그 문서의 약속이다.

### 작업 기호표 (시트 상단 범례 실측)

| 기호 | 뜻 | 기호 | 뜻 |
|---|---|---|---|
| `L` | 로딩 | `UL` | 언로딩 |
| `W` | 용접 | `S` | 위치결정 |
| `C` | 클램프 | `UC` | 언클램프 |
| `T` | 체결 | `SL` | 실링 |
| `G` | 사상(그라인딩) | `A` | 접착 |
| `M` | 운반(M.H) | `AJ` | 조정 |
| `CN` | 청소 | `E` | 기타 |

`M`(원위치)은 거의 언제나 `Sub` 다 — 로봇이 돌아가는 동안 다른 설비가 움직인다.

### 대기도 작업으로 적혀 있다

FLR F131 타임차트에는 「작업대기 22초」가 **번호 붙은 작업으로** 들어 있다.
병렬로 도는 다른 로봇을 기다리는 시간이고, 이것이 있어야 누계가 맞는다.

모델에서는 **Call 없는 Work** 로 옮긴다 — `WORK` 행에 Call 을 비우고 Time 만 적으면 된다.
지어낸 대기가 아니라 **작업서에 적힌 대기**만 옮겨라.

### 택트는 «시간의 합» 이 아니다

**Main 체인의 누계**가 택트다. 전부 더하면 병행 작업까지 직렬로 세어 부풀려진다.

```
API 시간 단순 합계 132s ← 틀렸다
작업서 Main 누계 106s ← 맞다
차이 26s = Sub (로보트1 언로딩 8 + 원위치 5 + 로보트2 원위치 5 + 로보트3 원위치 5 + 전공정클램프 3)
```

Sub 를 `Group` 으로 묶으면 엔진도 병행으로 돌린다. `Start` 로 이으면 직렬이 되어 택트가 틀어진다.

## 12. 라인 전체를 적을 때 — 규칙적으로 펼쳐라

셀 하나는 손으로 적어도 되지만 라인 전체는 100줄을 넘는다. 이때 손으로 나열하면 반드시
오타가 나고, 차종 하나를 빠뜨린다. **차종 × 스테이션의 곱으로 펼친다고 생각하고 적어라.**

### 파이프라인 셀의 규모 — §0 은 지그 셀 전용이다

§0 규모표는 «지그 셀 하나» 기준이라 스테이션이 여럿이면 맞지 않는다. 이렇게 센다:

| | 셈 |
|---|---|
| `FLOW` | 스테이션 수(동시에 물리는 차체 수) |
| `WORK` | **«공정 위상» 당 4~8**(이 표는 **라인·복합 셀 전용** — 지그 셀 하나는 §0 을 쓴다). 위상이 Flow 를 **가로지르면**(파이프라인) ×Flow 를 하지 마라 — 위상 수로만 센다 |
| `ARROW` | 간선 기준 — Work 수 + 재무장(Flow 마다) |
| `API` | 설비 수 × 2(짝) — **Flow 수와 무관**하다 |
| `SYS` | 설비 수 + 차종별 설비 ×차종 + Active 1 |
| **사이클 합** | **분기만큼 더하지 마라**. **긴 쪽으로 재라**. ※ **승강·연속반송이 들어간 셀은 유예** — 그 둘은 실측 자료가 없어 셀 전체가 `?` 가 된다 — 사양에 따라 길어지면 그 값이 택트다. 스테이션 하나가 40~90s(§0) — 라인 전체가 아니라 **스테이션마다** 본다 |

**«스테이션» 은 물리 자리가 아니라 «공정 위상» 으로 센다.**
한 물리 스테이션이 반입·승강·반전·송출 넷을 하면 **위상 넷**이다 — Work 가 11개여도 과다가 아니다.
**차체가 한 자리에 머문 채 성격이 다른 일이 이어지면 위상을 나눠 세라.**

**`API` 와 `SYS` 는 Flow 를 따라 늘지 않는다** — 설비는 하나이고 여러 Flow 가 함께 쓴다(§13-C).

### 무엇이 차종 수만큼 늘어나는가

| | 차종 2종 | 늘어나는가 |
|---|---|---|
| 지그(핀 · 클램프 · 래치) | ×2 | **예** — 물리적으로 다른 설비 |
| 용접건 · 핸들링 로봇 · 실러 | ×1 | 아니오 — 공용 |
| 센서 · 판정 | ×1 | 아니오 — 공용 |
| `WORK` · `ARROW` | ×Flow 수 | Flow 마다 제 사슬을 갖는다 |
| **서보·로봇 프로그램** | ×1 (SYS) · **×차종 (API)** — 설비는 하나, 정지 위치만 다르다 |

실측 규모(실측, 차종 2종 × 스테이션 12 × Capa 2):

```
SYS Passive 20 (차종별 지그 8 + 공용 12)
WORK 26 (Flow 2 × 13)
ARROW 50 (사슬 24 + 재무장 26)
API 28 (지그 16 + 공용 12)
```

차종 3종이면 지그가 12가 되어 Passive 24 — S507 실측(유닛 36)에 가까워진다.

**설비가 하나인데 차종마다 «동작» 이 다르면 SYS 는 하나, API 만 늘린다.**
서보가 그렇다 — 스탠드서보 1대가 차종마다 다른 위치에 서므로
`서보.PRG1_KA4`·`PRG2_MV`·`PRG3_RJ` 로 **API 를 나누고 SYS 는 하나로 둔다**(§1 서보 행).

| | SYS | API |
|---|---|---|
| 차종마다 **다른 설비**(지그·게이지) | ×차종 | ×차종 |
| 설비 하나인데 **동작만 다름**(서보·로봇 프로그램) | ×1 | ×차종 |
| 공용 설비(기준핀·반송·라인상태) | ×1 | ×1 |

### 서보는 «왕복» 이 아니라 «설정 → 기동 → 완료» 다

실린더는 `ADV`/`RET` 두 API 로 끝난다. **서보는 다르다.**

```
① 축을 고른다 T축선택 %QX6.21.8.05 · L축선택 .06
② 프로그램 번호를 세운다 PG_WORK 1/2/4/8/16 %QX6.21.7.08~12 (5비트 = 1~31번)
③ 기동한다 PG_START %QX6.21.7.04
④ 그 번호의 완료가 온다 T_PRG_COMP_1~6 %IX6.21.1.01~06
```

**비트 조합은 PLC 가 한다.** 모델은 «프로그램 N 실행» 을 **API 하나**로 본다:

```
API,T축.PRG1_KA4,Normal/Normal,,944MS,%IX6.21.1.01,%QX6.21.7.04
API,T축.PRG2_MV ,Normal/Normal,,944MS,%IX6.21.1.02,%QX6.21.7.04
```

**완료가 번호별로 따로 온다**는 것은 «위치마다 다른 신호» 라는 뜻이다.
차종마다 정지 위치가 다르므로 **차종 = 프로그램 번호**다(§2).

서보에만 있는 조건도 있다 — `UNIT_READY`(`%IX6.21.0.00`)와 모드(자동/JOG/TEACH).
**유닛이 준비돼야 움직인다.** 실린더에는 없던 `ComAux` 다.

```
COND,차체.이송.T축.PRG1_KA4,ComAux,서보유닛.READY & 서보유닛.자동모드,,,
```

**한 줄로 적어라** — 줄을 나눠도 누적 AND 라 뜻은 같지만, 허가 식은 **한 글자도 바꾸지 말고
복사해야** 나중에 찾을 수 있다(§13-C).

속도도 비트다(`SPEED_10/20/40/80`). 목표·현재 위치는 **워드**(`%QW6.21.9` / `%IW6.21.2`)이고
전류값·알람코드도 워드로 온다 — 비트만 다루던 모델에 처음 나오는 종류다.

### 공유 기동 신호는 AI-W13 의 정당한 예외다

위 예제에서 API 여섯이 `%QX6.21.7.04` 를 함께 쓴다. `AI-W13` 이 경고하지만 **맞는 설계**다.

앞의 «주소 복사» 와 무엇이 다른가:

| | 무엇이 겹치나 | 판정 |
|---|---|---|
| 실측 | **서로 다른 장치**(8개 클램프)가 한 입력 비트를 나눠 읽는다 | 결함 |
| 서보 | **한 장치**의 여러 프로그램이 기동 비트를 공유한다 | 정상 |

**출력 하나가 여러 동작을 시작시키는 것은 가능하다** — 무엇을 할지는 다른 비트가 정한다.
입력 하나가 여러 센서일 수 없는 것과는 다르다. 이 경우 **주석에 이유를 남겨라.**

### 신호는 세 층이다 — 물리 → 판정 → 모델

같은 구조가 세 곳에서 반복된다:

| 층 | 예 | 영역 |
|---|---|---|
| **물리 입력** | `RH_OP_PBL_운전준비` `%IX3.20.0.00` · `RH_LOW_LS_L_SLD_전진단` `%IX3.30.1.00` | `%I` |
| **PLC 판정** | `S507R_M_운전준비` `%MX1.1050.01` · `S507R_M_L_SLID_KA4_전진단` `%MX1.1072.09` | `%M` |
| **모델** | `라인상태.운전준비` · `L슬라이드.전진` 의 InTag | — |

**모델은 판정 층을 읽는다.** 버튼이나 리밋스위치를 직접 읽으면
PLC 가 걸어 둔 조건(모드·인터록·차종)이 빠진다. `운전준비` 버튼을 눌렀다고
운전 준비가 된 것이 아니다 — 그 버튼과 다른 조건들을 PLC 가 판정해 `M_운전준비` 를 만든다.

### 센서 접두가 종류를 말한다

| 접두 | 뜻 | 어디에 |
|---|---|---|
| `RS` | 리드스위치 — 실린더 **안**에 달린다 | 클램프·슬라이드 (RH 120건) |
| `LS` | 리밋스위치 — 기구 **밖**의 물리 단 | 슬라이드 단·이탈·원점 (12건) |
| `PXS` | 광전센서 | 소재·차종 확인 (22건) |
| `PBL` / `KSW` / `PB` / `SPB` | 램프버튼 / 키스위치 / 버튼 / 순시버튼 | 조작반 `OP` (85건) |
| `SOL` | 솔레노이드 **출력** | 실린더 구동 (92건) |
| `SRV` | 서보 | 인덱스·슬라이드 (99건) |

`LS` 에는 **`이탈`·`원점`** 이 있다 — `LS_L_SLD_전진이탈`·`LS_T_SLD_원점`.
«단(端)에 닿았다» 와 «단에서 벗어났다» 는 다른 신호이고,
벗어남은 **움직이기 시작했다**는 뜻이라 `(F)` 엣지와 짝이 맞는다(§13).

### «추측하지 마라» 와 «응답을 읽어라» 는 부딪히지 않는다

§3 은 «쌍을 이름으로 추측하지 마라» 고 하고, 아래는 «응답을 InTag 로 읽어라» 고 한다.
둘 다 지킬 수 있다 — **가르는 것은 «IO 리스트를 볼 수 있는가» 다**:

| 상황 | 어떻게 |
|---|---|
| IO 리스트가 **있다** | 쌍을 **확인**해서 채운다. 확인은 추측이 아니다 |
| **없다** | InTag·OutTag 를 `?` 로 두되 **API 는 짝으로 적는다** |

**주소를 모르는 것과 구조를 모르는 것은 다르다.**
`RT5호기.정렬안착` 이 «지령을 내고 응답을 받는다» 는 것은 주소 없이도 참이다 —
API 행을 만들어 두면 **배선할 때 채울 자리가 남는다.** 그것을 안 적으면
.

§3 이 금지하는 것은 **주소를 지어내는 것**이지 짝의 존재를 적는 것이 아니다.

### 로봇 지령에는 짝이 있다 — OutTag=지령, InTag=응답

현장 태그를 계열로 세어 보면 `RT_OUT`(PLC→로봇)과 `RT_IN`(로봇→PLC)이 **쌍으로** 있다:

| 지령 `%QX` | 응답 `%IX` |
|---|---|
| `RT_OUT_정렬_안착가능` `4.05.4.11` | `RT_IN_정렬_안착완료` `4.05.1.09` |
| `RT_OUT_정렬_취출가능` `4.05.4.10` | `RT_IN_정렬_취출완료` `4.05.1.10` |
| `RT_OUT_셋팅_안착가능` `4.05.4.09` | `RT_IN_셋팅_안착완료` `4.05.1.11` |

**ApiCall 의 OutTag 에 지령을, InTag 에 응답을 적는다.** 이 지침의 산출물은 오래
**지령만 적고 응답을 비워 두었다** — 로봇에게 «해라» 고만 하고
«했다» 를 읽지 않는 모델이었다.

«가능» 과 «완료» 는 다른 신호다.

**조건 leaf 로도 쓸 것이라면 InTag 를 «유지형 판정 비트»(`%MX`)로 올려라.**
`RT_IN_…완료` 는 **1.95초만 선다**(§13 실측표) — 배선 후 leaf 는 «지금 값» 이므로
그 창 밖에서는 거짓이다. **Call 완료용 InTag 와 조건용 InTag 가 갈릴 수 있다**:

| 그 API 를 | InTag |
|---|---|
| Call 완료 판정에만 쓴다 | `%IX` 응답 그대로 |
| **조건 leaf 로도 쓴다** | **`%MX` 유지형 판정 비트**(PLC 가 래치해 둔 것) |

**InTag 열은 하나뿐이므로 «조건용» 을 적는다**(그쪽이 더 까다롭다).
`%IX` 응답은 **주석에 남겨라** — 배선할 때 둘 다 필요하다:

```
# RT_IN 응답은 %IX4.05.1.09 (Call 완료용). 조건 leaf 로 쓰므로 InTag 는 유지형 판정 비트.
API,RT5호기.정렬안착,Normal/Normal,,8483MS,%MX1.2090.03,%QX4.05.4.11
```

없으면 그 조건을 per-cycle 로 쓰지 말고 §13 「ON 창」 규칙으로 가라. `가능` 은 PLC 가 내주는 허가이고 `완료` 는 로봇이 돌려주는 사실이다.

### 차종 판정은 광전센서다

**센서는 자기 주소를 갖는다** — «모델은 판정 층을 읽는다» 의 예외다.
버튼·리밋스위치는 PLC 가 모드·인터록을 얹어 `%M` 을 만들지만, **광전센서의 «부품이 있다» 는
그 자체가 사실**이라 얹을 조건이 없다. 차종 판정도 마찬가지다:

**`%IX` 는 판정, `%QX` 는 지령이다 — 조건 leaf 에는 판정을 쓴다.**

| 신호 | 방향 | 쓰임 |
|---|---|---|
| `PXS_{차종}_LOAD` `%IX3.30.0.12~14` | 센서 → PLC | **차종 판정.** 조건 leaf 는 이것 |
| `RT_OUT_{차종}_차종` `%QX4.01.5.12` | PLC → 로봇 | 차종 **지령** — 판정이 아니다 |

지령을 leaf 로 쓰면 InTag 가 비어 §13 의 거울상 결함이 재현된다 —
**세 차종 부정이 동시에 거짓이 되어 세 지그가 한꺼번에 물린다.**

`RH_LOW_PXS_KA4_LOAD` `%IX3.30.0.12` · `…MV…` `.13` · `…RJ…` `.14` —
**차종마다 광전센서가 하나씩** 있다. 차종 판정을 «어디서 오는지 모를 신호» 로 두지 말고
이 계열을 찾아라. `PXS` 는 photoelectric sensor 다.

피더 쪽은 `PXS_{차종}_FDR_PART1/PART2` 로 **부품마다 2점**이다 —
둘 다 있어야 집는다는 뜻이므로 조건에서 AND 로 묶는다(§4).

### 주소에는 출처를 밝혀라

이 지침의 산출물 18개 중 **실제 IO 와 대조한 것은 둘뿐**이다(r14 · r22 — S507R 라인).
나머지는 예시 주소이고, 그대로 배선하면 전혀 다른 장치를 움직인다.

그래서 모든 산출물 머리말에 한 줄을 넣었다:

```
# [주소] 현장 PLC 실주소 — plc.ir.json globalVars 와 대조함. 모르는 곳은 `?`.
# [주소] **예시다.** 이 라인의 실제 IO 와 대조한 적이 없다 — 그대로 배선하지 마라.
# [주소] 전부 `?` 다 — 배선 전이라 지어내지 않았다.
```

**모델을 받는 사람은 주소가 진짜인지 알 수 없다.** 숫자는 셋 다 똑같이 생겼다.
적은 사람만 아는 사실이면 적어 두어야 한다.

### «동시» 는 측정 해상도 안에서만 말할 수 있다

다점 리드스위치가 정말 같이 켜지는지 2일 로그로 재어 봤다.
`3차클램프_RET1/2/3` 은 **1240회 전부 짝이 맞았고 중앙 시차 0.000초**였다.

그런데 이 수집기의 사이클은 **209ms** 다(`collector.json` · `stat.avg_cycle_ms`).
**209ms 보다 짧은 시차는 애초에 보이지 않는다.** 그러니 정확한 말은 이렇다 —
«동시에 켜진다» 가 아니라 **«209ms 해상도에서 구분되지 않는다»**.

실무 결론은 같다: **다점을 조건으로 AND 재현할 실익이 없다.**
셋이 한 사이클 안에 들어오므로 하나를 읽으나 셋을 읽으나 결과가 같다.
다점의 목적은 «동시 확인» 이 아니라 **«하나가 죽었을 때 검출»** 이고,
그 검출은 PLC 가 판정 비트를 만들며 이미 한다(§12).

§4 의 «다점 확인센서를 버리지 마라» 는 **조건으로 엮으라는 뜻이 아니라
판정 비트를 찾아 쓰라는 뜻**으로 읽어야 한다.

### PLC 는 복잡한 판정을 «총괄» 비트로 압축해 둔다

이 지침이 같은 것을 두 번 발견했다. 하나의 원리다:

| PLC 가 하는 일 | 결과 비트 | DS2 는 |
|---|---|---|
| 리드스위치 5개를 AND | `S507R_M_KA4_1차클램프_후진단` | 그 비트를 InTag 로 읽는다 |
| 이상 로직 **725 rung** 을 OR | `S507R_M_이상총괄` (`%MX1.1052.00`) | **부정해서** ComAux 로 읽는다 |
| 비상정지 게이트·OP·AOP 를 OR | `S507R_M_비상정지_총괄` (`%MX1.1052.14`) | 〃 |

**옮겨 적지 마라. 현장이 이미 계산해 두었고, 그 결과에 이름이 붙어 있다.**

### 총괄 비트의 극성을 확인하라

이름이 극성을 말한다. **뒤집어 읽어야 하는 비트가 있다**:

| 비트 | 참일 때 | 조건에 쓸 때 |
|---|---|---|
| `M_이상총괄` `%MX1.1052.00` | **이상이 있다** | 부정한다 — 그룹 `[부정]` 으로 감싼다 |
| `M_비상정지_총괄` `%MX1.1052.14` | **비상정지가 걸렸다** | 〃 |
| `M_운전준비` `%MX1.1050.01` | 준비됐다 | 그대로 |

**API 이름을 `라인상태.정상` 으로 붙였다고 극성이 바뀌지 않는다.**
그 API 의 InTag 가 `이상총괄` 이면 값이 1일 때 «이상» 이다.
이름과 주소가 어긋나면 나중에 읽는 사람이 반드시 틀린다 — **비트 이름을 그대로 쓰고
조건에서 부정하라**:

```
API,라인상태.이상총괄,Virtual/Virtual(100),,100MS,%MX1.1052.00,
COND,차체.고정.지그.전진,ComAux,라인상태.운전준비 & /라인상태.이상총괄,,,
```

### 모델은 PLC 의 일부만 그린다

현장 PLC(5991 rung)를 역할별로 세어 보면:

| 역할 | rung | 비중 |
|---|---|---|
| **정상 시퀀스**(차종 동작·지그·서보·런너) | 814 | **13%** |
| 이상·인터록 | 762 | 12% |
| 완료·확인 판정 | 468 | 7% |
| 나머지(물류·서열·팔레트·표시) | ~3900 | 67% |

**DS2 모델이 그리는 것은 그 13% 다.** PLC 를 열고 «이걸 다 옮겨야 하나» 싶을 때
이 숫자를 기억하라. 이상·알람은 총괄 비트 하나로 읽고, 물류·표시는 모델 밖이다.

### 차종은 몇 개인가 — PLC 프로그램이 답한다

이 라인의 PLC 에는 `KA4_동작`(130 rung) · `MV_동작`(184) · `RJ_동작`(170)이
**서로 다른 프로그램**으로 있다. §2 의 «차종 분기는 SYS 로» 가 현장 구조와 같다는 뜻이고,
동시에 **차종이 둘이 아니라 셋** 이라는 뜻이다. 프로그램 목록이 차종 목록이다.

### 실린더 하나에 신호는 세 겹이다

현장 PLC(`plc.ir.json` globalVars 4529건)를 열어 보고 알았다. 클램프 하나에 이름이 셋이다:

| 접두 | 영역 | 예 | 뜻 |
|---|---|---|---|
| `SOL` | `%QX` (Out) | `RH_UPPER_SOL_KA4_1차클램프_ADV` | 솔레노이드를 민다 |
| `RS` | `%IX` (In) | `RH_UPPER_RS_KA4_1차클램프_RET1`…`RET5` | 리드스위치 — **RET 는 5개** |
| `M_…_전진단` | `%MX` (Memory) | `S507R_M_KA4_1차클램프_전진단` | PLC 가 만든 **완료 판정** |

**InTag 에는 판정 비트(`%MX`)를 쓴다.** raw 리드스위치가 아니다 —
RET 쪽이 다섯 개라 하나를 고를 수 없고, **PLC 가 이미 다섯을 AND 해서 «후진단» 을 만들어 두었다**.
§4 의 «다점 확인센서를 버리지 마라» 에 대한 실제 답이 이것이다. 조건으로 다시 엮을 필요가 없다 —
현장이 이미 엮어 두었고, 그 결과에 이름이 붙어 있다.

이 PLC 의 영역 분포는 **Memory 2724 · In 924 · Out 881** 이다. 절반 이상이 메모리다.
완료 판정·모드·조건이 대부분 그쪽에 있다.

### 영역 문자를 지어내지 마라

`%IX1.1073.04` 는 이 지침의 산출물에 실제로 있던 주소인데, **그 PLC 에 `%IX1` 영역은 없다**
(고쳤다). 숫자는 실측에서 가져오고 영역 문자만 바꿔 적은 것이다.

- `%I…` = PLC 가 **읽는** 비트. 코일을 걸 수 없다(`AI-W14` 가 잡는다)
- `%Q…` = PLC 가 **쓰는** 비트
- `%M…` = 내부 메모리. 완료 판정·모드가 여기 있다

**LH/RH 가 쌍으로 존재한다**(`%QX2.31` / `%QX3.31`, `%QX5.23` / `%QX5.43`).
어느 유닛을 적는지 먼저 정하고 그쪽 주소만 가져와라.

### 주소는 복사하지 마라

차종별·다점별로 API 를 늘리다 보면 **주소까지 함께 복사된다.** 실제로 이 지침의 산출물에
지그 API **16개가 주소 2개를 공유**하는 모델이 있었다(고쳤다).

```
API,KA4_핀.ADV,…,%IX3.30.0.01,%QX3.31.0.01
API,KA4_1차클램프.ADV,…,%IX3.30.0.01,%QX3.31.0.01 ← 같은 비트
API,MV_3차클램프.ADV,…,%IX3.30.0.01,%QX3.31.0.01 ← 여덟 번째
```

**입력 비트 하나가 여덟 개 센서일 수는 없다.** 출력도 마찬가지다 — 하나의 코일이
여러 장치를 따로 움직이지 못한다. 그런데 문법도 연결도 멀쩡해서 **그래프 검증까지 조용히
통과한다**. 이제 파서가 `AI-W13` 으로 잡는다.

주소를 모르면 **복사하지 말고 `?` 로 두어라**(§14). 가짜 주소는 «배선이 있다» 고 말하지만
`?` 는 «아직 모른다» 고 말한다. 뒤에 오는 사람에게 전혀 다른 정보다.

### 같은 설비는 Flow 마다 똑같이 다뤄라

차종별로 Flow 를 복사해 적다 보면 **한쪽에만 손이 간다.** 실제로 이 지침의 산출물에
차종 A 는 로봇을 원위치시키고 **차종 B 는 그냥 두는** 모델이 9곳 있었다(고쳤다).
파서도 그래프 검증도 조용했다 — 문법과 연결은 멀쩡하기 때문이다.

그런데 설비는 하나다. **A 차체가 지나갈 때는 돌아오고 B 차체가 지나갈 때는 안 돌아오는**
로봇은 없다. 모델만 그렇게 적힌 것이다.

**같은 디바이스를 여러 Flow 가 부른다면, 부르는 API 도 같아야 한다.**
이제 파서가 `AI-W12` 로 잡는다:

```
AI-W12: 'SPOT1' 를 Flow 마다 다르게 다룹니다 —
 'SPOT1.타점' 는 부르면서 'SPOT1.원위치' 를 차체B 에서 부르지 않습니다.
```

예외는 **제품마다 전용 동작을 둔 경우**다(§13-C 공유 자원의 `로봇.A작업`/`로봇.B작업`).
그때는 API 자체가 Flow 전용이라 이 경고가 나지 않는다.

### 사슬과 재무장은 기계적으로 나온다

Flow 마다 Work 이름을 순서대로 늘어놓고, 인접쌍을 `Start` 로 잇는다. 마지막에 배출이
앞단 전부를 `Reset` 하고, 투입이 배출을 `Reset` 한다. 이 두 줄을 빠뜨리는 것이
규모가 커질수록 잦아진다 — **Flow 를 복사해 붙일 때 이름 치환을 빠뜨리기 때문이다.**

```
ARROW,차체B.배출,Reset,차체A.투입;… ← 복사 흔적. A 와 B 가 섞이면 한 대가 나가야
 다른 대가 도는 모델이 된다
```

검증이 이것을 «Reset 누락» 으로 잡아 주지만, 잡히지 않는 경우도 있다 — 잘못된 Flow 를
리셋해도 «리셋은 되었으므로» 통과한다. **복사한 뒤에는 Flow 이름을 눈으로 훑어라.**

## 12-B. 배선 전에 적을 때 — 다섯을 한자리에

대부분의 신규 셀은 **배선 전에 그려진다.** 그때 지켜야 할 것이 다섯 절에 흩어져 있었다.
**하나라도 빠뜨리면 파서·검증을 통과한 채 조용히 뒤집힌다.** 여기 모은다.

### ① 감지를 `Virtual(n)` 로 내린다 (§1)

동작(왼쪽)은 그대로 두고 **감지(오른쪽)만** 내린다 — `Latch/Normal` → `Latch/Virtual(100)`.
`Normal`·`Latch` 감지는 InTag 를 요구하므로(`RuntimeSemantics.fs:86`) `?` 면 Call 이 완료되지 않는다.
머리말에 **«배선 시 되돌릴 Type»** 을 적어라.

### ② 주소는 `?` — 단 조건 leaf 는 예외 (§12·§13)

지어내지 마라. **예외는 «조건 leaf 로 쓰는 읽기 전용 API» 전부다** —
차종 판정 · 총괄 비트 · 사양 판정 · 운전준비 · 판정 워드 · 엣지 leaf.
`?` 로 두면 «항상 참» 이 되어 조건이 뒤집힌다.
**서로 다른 예시 주소를 부여하고 머리말에 «예시임» 을 밝혀라.**
동작 API(ADV·RET·작업·원위치)는 `?` 여도 정확히 읽힌다.

### ③ 복귀단은 OR 로 적고, 배선 후에 AND 로 바꾼다 (§13-A2)

배선 전에는 생략된 복귀단이 «거짓» 이므로 **OR**, 배선 후에는 «참» 이 되므로 **AND** 다.
**머리말에 «주소를 채울 때 복귀단 OR 를 AND 로 바꿔라» 를 적어 두어라** — 안 적으면 놓친다.

### ④ 워드 «쓰기» 는 배선 전에 적을 수 없다

`OutTag=값` 은 주소가 있어야 성립한다. 주소가 `?` 면 값도 함께 사라진다.
**가변 목표값이 필요하면 «프로그램 번호» 로 돌려라**(§12 서보) — 그것도 안 되면
그 자리는 **배선 후로 미루고 머리말에 적어라.**

### ⑤ 시간 축 점검은 사전에 유예 선언 (§8·§9)

`?` 가 있으면 누계를 낼 수 없다. **머리말에 «`?` N개·무엇인지·그래서 무엇을 유예하는지» 를
먼저 적어라** — 사후 변명이 아니라 사전 선언이다.

## 13. 조건 표기 — 엣지와 기대값

> **조건을 쓰기 전에 이 여섯만 기억하라** — 나머지는 걸렸을 때 찾아라.
>
> 1. **leaf 판정은 InTag 가 가른다** — 있으면 «지금 값», 없으면 «그 Work 가 끝났는가»
> 2. **`Virtual` 감지 API 를 leaf 로 쓰면 InTag 를 채워라** — `?` 면 «항상 참»
> 3. **생략은 완료가 아니다** — 생략될 수 있는 것을 `AutoAux` 로 기다리지 마라
> 4. **배선 후 복귀단은 사이클 시작에 이미 참** — 혼자 쓰지 말고 per-cycle 을 앞에 깔아라
> 5. **AND 는 둘이 «동시에» 참일 때만 선다** — 짧은 신호와 늦은 레벨을 묶지 마라
> 6. **분기 조건은 값 공간을 빠짐없이·겹치지 않게 덮어라** — 마지막은 «나머지 전부»


### 범위·이상/이하는 v1 에 없다 — PLC 판정 워드를 읽어라

조건 비교는 **`=값` 하나뿐**이다. `>=`·범위는 쓸 수 없다.
그런데 토크·갭·치수는 본질이 «규정값 이상» 이거나 «범위 안» 이다.

**§12 의 총괄 비트 원리를 그대로 쓴다** — PLC 가 이미 판정해 이름을 붙여 두었다:

```
✗ COND,…,AutoAux,런너.토크>=250 ← v1 에 없는 문법
✓ COND,…,AutoAux,런너.체결NG코드=0 ← PLC 가 판정한 결과를 읽는다
```

**판정은 PLC 가 하고 모델은 결과를 읽는다.**

**값 조건 앞에는 «그 값을 만드는 동작» 을 깔아라.** 워드 leaf 는 «지금 값» 이므로
`압력NG코드=0` 은 **펌프가 서기 전에도 참**이다(아직 이상이 없으니 0이다).

```
✗ COND,차체.도포.실러.본도포,AutoAux,압력감시.압력NG코드=0,,,
✓ COND,차체.도포.실러.본도포,AutoAux,실러펌프.가압기동 & 압력감시.압력NG코드=0,,,
```

§13 의 «per-cycle 을 앞에 깔아라» 가 **워드에도 그대로 걸린다.**

### «같지 않다» 와 값이 셋 이상일 때

`!=` 는 없다(`AI051`). **부정 `/` 를 값 비교에 붙이면 그것이 «같지 않다» 다**(실측 확인 —
`NcContact` + 기대값으로 실린다):

```
COND,…,SkipAction,/계측.판정코드=0,,, ← 판정코드가 0 «이 아니면» 건너뛴다
```

값이 셋 이상이면 **OR 로 나열**한다 — `&` 와 못 섞으니 층을 괄호로 나눈다:

```
COND,…,SkipAction,계측.판정코드=1 | 계측.판정코드=2,,, ← 1 이거나 2 면 건너뛴다
```

**분기가 셋 이상이면 Work 를 셋으로 갈라 `Group` 동반자로 두어라**(§13-A2) —
각 Work 가 «자기 코드가 아니면 건너뛴다» 를 갖는다.

**분기 조건은 값 공간을 «빠짐없이·겹치지 않게» 덮어야 한다.**

| 잘못 | 무슨 일이 나나 |
|---|---|
| **못 덮음** — 코드 3 을 아무도 안 맡음 | 그 차체는 **반출 없이 조용히 셀을 빠져나간다** |
| **겹침** — 두 Work 가 코드 1 을 맡음 | 반출이 두 번 돌아 **로봇이 충돌한다** |

**둘 다 파서·그래프 검증을 통과한다.** 코드가 0~3 네 값이고 분기가 셋이면 이렇게 덮는다:

```
COND,차체.정상반출,SkipAction,/계측.코드=0,,, ← {0}
COND,차체.재작업반출,SkipAction,/계측.코드=1,,, ← {1}
COND,차체.NG반출,SkipAction,계측.코드=0 | 계측.코드=1,,, ← {2,3} — 나머지 전부
```

**값이 둘뿐이면 `/` 하나로 끝난다** — `/` 는 «같지 않다» 다:

```
COND,차체.정상반출,SkipAction,/계측.코드=0,,, ← 0 이 아니면 건너뛴다
COND,차체.NG반출,SkipAction,계측.코드=0,,, ← 0 이면 건너뛴다 = 나머지 전부
```

**마지막 하나는 «나머지 전부» 로 적어라** — 값이 늘어나도 새지 않는다.
머리말 주석에 **«코드 공간 {0}{1}{2,3} 을 덮는다»** 를 적어 두면 읽는 사람이 확인할 수 있다.

### 판정 코드를 읽을 때 지킬 것 셋

**① 코드 체계는 PLC 가 정한다 — 모델이 발명하지 마라.**
`0=정상`·`1=경미`·`2=중대` 같은 값은 현장 문서나 IR 에 있다. 알 수 없으면
**머리말에 «가정: 0=OK, 1=NG» 를 적고** 배선할 때 확인하라. 모델이 정한 코드는 반드시 어긋난다.

**② 판정은 «측정이 끝난 뒤» 읽어라.**
**Work 레벨 `SkipAction` 은 Group 시작 순간 한 번 평가된다** — 검사와 같은 Group 에 두면
측정 전에 판정한다. **판정 분기 Work 는 한 단계 뒤 Group 에 붙여라.**

**같은 이유로 `Source` Work 를 곧바로 차종 Group 의 전달자로 두지 마라.**
Group 은 Source 가 서는 순간 시작하는데, **그때는 차체가 아직 도착 전이라 차종 비트가 다 거짓**이다 —
셋 다 생략되어 OR 층에서 셀이 선다. Work 에는 `AutoAux` 를 못 걸므로(`AI014`)
**「수취(Source) → `Start` → 고정 Group」으로 한 단계를 끼워라.** 분기 Call 의 `AutoAux` 에 **계측 완료**를 걸지 않으면
**이전 사이클 값**을 읽는다. 값이 남아 있기 때문에 조건은 «참» 이 되고, 앞 차체의 판정으로
이번 차체를 내보낸다 — 검증은 통과한다.

```
COND,차체.분기.반출.정상,AutoAux,계측기.원위치,,, ← 측정이 끝났다는 사실을 먼저 건다
COND,차체.분기.반출.정상,SkipAction,/계측.코드=0,,,
```

**③ «아무 것도 아닌» 경우와 «둘 이상» 인 경우를 정하라.**
차종 판정이 **둘 다 참**이면 지그 둘이 물린다 — 모델로는 막을 수 없다(각 SkipAction 이 독립이다).
**PLC 가 배타를 보장한다고 머리말에 적고, 아니면 `/다른차종` 을 AND 로 더하라.**
 차종 판정 셋이 **다 거짓**일 수 있다(미판독·센서 고장).
§13-A2 의 OR 층은 «하나는 반드시 온다» 를 전제하므로, 그 전제가 깨지면 셀이 선다.
**서는 것이 맞다** — 정체를 모르는 차체를 물리면 지그가 깨진다.
다만 **그 사실을 머리말에 적어라**: «차종 미판독이면 셀이 정지한다(의도)». 범위를 모델에 옮기지 마라 —
§12 「모델은 PLC 의 일부만 그린다」 가 여기에도 적용된다.

### 부정(`/`)·값 비교(`=`) leaf 는 InTag 가 반드시 있어야 한다

앞 절의 **거울상**이다. 모은 것이 «완료가 오지 않는 것을 기다린다» 였다면,
이쪽은 **«완료가 와 버려서 조건이 뒤집힌다»** 다.

`/차종판정.KA4` 를 적었는데 그 API 의 InTag 가 `?` 라면 —
leaf 는 «그 Work 가 완료됐는가» 로 읽힌다. 그런데 판독 Work 가 차종 셋을 다 Call 하므로
**셋 다 완료된다.** 그러면 `/KA4`·`/MV`·`/RJ` 가 **동시에 거짓**이 되어
**세 차종 지그가 한꺼번에 물린다.** 긍정으로 적어도 같다 — `Virtual` 센서 Call 은
실제 비트와 무관하게 완료되므로 `?` 면 «항상 참» 이다.

파서도 그래프 검증도 통과한다.

**규칙**: **leaf 의 종류에 따라 갈린다**(실측 엔진 확인 — «InTag 없으면 대상 Work 의 Finish»):

| leaf 가 가리키는 API | InTag | 왜 |
|---|---|---|
| **읽기 전용 API**(센서·판정·워드 — `Virtual` 감지) | **반드시 채워라** | Call 이 실제 비트와 무관하게 완료되므로 `?` 면 **«항상 참»** 이 된다 |
| **실제로 돌아야 Finish 가 나는 API**(ADV·RET·작업·원위치·쓰기 지령) | `?` 여도 된다 | 돌지 않으면 Finish 가 안 나므로 «그 동작이 끝났는가» 로 **정확히** 읽힌다 |

### 판정 비트는 «언제 꺼지는가» 를 확인하라 — «배선 후» 규칙이 전부 여기 매달려 있다

배선 후 leaf 는 «지금 값» 이다(§13). 그러면 **`M_…완료` 같은 판정 비트가
사이클 시작에 꺼지지 않으면 지난 사이클 값으로 조건이 선다.**

**아래 세 규칙이 전부 이 전제 위에 있다** — 전제가 깨지면 셋이 **동시에 조용히** 뒤집힌다
(파서·그래프 검증 모두 통과):

- leaf 판정(«지금 값» 인가 «완료» 인가)
- 전진단 OR / 복귀단 AND
- per-cycle 과 레벨의 ON 창 겹침

**규칙**: **InTag 로 쓰는 판정 비트는 «언제 리셋되는가» 를 확인하라.**
확인할 수 없으면 **per-cycle 사실로 쓰지 마라** — 레벨로만 쓰거나,
차종 신호·라인 상태처럼 **사이클 내내 참인 것**과 묶어라.
확인했으면 **머리말에 «판정 비트는 반입 시 PLC 가 클리어한다» 를 적어라.**

**per-cycle 로 쓸 수 있는 것은 «그 사이클에만 서는 것» 이 증명된 신호뿐이다.**

**대신할 사실이 아예 없는 셀도 있다**(도포 완료·헤밍 완료를 대신할 것이 없다).
그때는 **per-cycle 로 쓰되 머리말에 전제를 못 박아라** —
«`M_도포완료` 는 반입 시 PLC 가 클리어한다고 **가정**. 배선 시 확인할 것».
**가정을 적은 모델은 고칠 수 있지만, 적지 않은 모델은 왜 서는지 아무도 모른다.**

### 신호마다 «얼마나 서 있는가» 가 다르다 — 실측표

2일 로그에서 ON 유지 시간 중앙값을 쟀다(660여 회씩). **조건 leaf 로 쓸 수 있는지가 갈린다**:

| 신호 | 유지 | 조건에 쓰는 법 |
|---|---|---|
| `RT_OUT_자동기동` | **0.97s — 펄스** | **`(R)` 엣지로 잡아라.** 그냥 leaf 로 쓰면 놓친다 |
| `RT_IN_…완료`(5호기) | **1.95s** | **per-cycle 사실**로 쓴다. 짧으니 그 안에 읽어야 한다 |
| `RT_OUT_…가능` | 5.8~28s | 레벨 — 혼자 쓰지 말고 per-cycle 과 AND |
| `RT_IN_기동OK` · `작업완료_RST` | 29~30s | 레벨 |
| `RT_OUT_{차종}_차종` | 58~65s(사이클 내내) | 레벨 — **상태**이지 사건이 아니다 |

**«완료» 는 짧고 «가능·차종» 은 길다.** 로봇 응답을 조건 leaf 로 쓸 때
`…완료` 는 per-cycle, `…가능`·`…차종` 은 레벨로 다뤄라 — 아래 규칙과 그대로 이어진다.

### 배선 후에는 «너무 일찍 서는» 쪽을 조심하라

지금까지 모은 함정은 전부 **«완료가 오지 않는 것을 기다린다»** 쪽이었다. **반대 방향이 하나 있다.**

**InTag 를 채우면 동작 API leaf 도 «지금 값» 으로 바뀐다**(§13 leaf 판정).
그런데 **후진단·원위치단은 사이클 시작 시점에 이미 참**이다 — 지난 사이클에 돌아와 있기 때문이다.

```
✗ COND,차체.해제.기준핀.RET,AutoAux,검사기.원위치,,,
 ← 배선 전에는 «검사가 끝났는가» 지만, 배선 후에는 «검사기가 지금 원위치에 있는가» 다.
 도포 중에도 참이므로 차체가 작업 도중에 풀린다.
```

**«이번 사이클에 일어난 사실» 을 앞에 깔고 레벨 판정을 AND 로 쌓아라**:

```
✓ COND,차체.해제.기준핀.RET,AutoAux,검사기.검사 & 검사기.원위치,,,
 ← 이번에 검사를 했고(per-cycle) 지금 돌아와 있다(level)
```

| leaf 가 가리키는 것 | 배선 전 | 배선 후 |
|---|---|---|
| 작업·타점·검사(한 번 돌면 끝) | 완료 | «지금 하고 있는가» — **per-cycle 사실로 쓴다** |
| 원위치·후진단(제자리 복귀) | 완료 | **사이클 시작에 이미 참** — 혼자 쓰면 안 된다 |

**레벨 비트를 혼자 조건으로 쓰지 마라.** 앞에 이번 사이클 사실을 깔아라.

### AND 로 묶을 때는 «ON 창이 겹치는가» 를 보라

앞 절이 «per-cycle 을 깔고 레벨을 AND» 라고 했지만, **AND 는 둘이 «동시에» 참일 때만 선다.**
per-cycle 신호는 짧다 — 로봇 완료 응답은 **1.95초**다(위 실측표). 그 창이 닫힌 뒤에
레벨이 서면 **AND 가 한 번도 성립하지 않는다.**

```
✗ COND,…,AutoAux,로봇.작업완료 & 로봇.원위치,,,
 ← 완료 응답 1.95s 가 닫힌 뒤에 원위치가 서면 영영 안 선다
```

**가르는 법**:

| 앞 leaf(per-cycle)의 창 | 어떻게 |
|---|---|
| 뒤 레벨이 **그 창 안에** 선다 | AND 로 묶어도 된다 |
| 뒤 레벨이 **이미** 서 있다(사이클 내내) | AND 로 묶어도 된다 — 가장 안전하다 |
| 뒤 레벨이 **창이 닫힌 뒤** 선다 | **묶지 마라.** per-cycle 하나만 쓰거나 **InTag 를 «유지형 판정 비트»(`%MX`)로 바꿔라**(§12) |

**가장 쉬운 답은 «이미 서 있는 것과 묶는 것» 이다** — 차종 신호(58~65s)·라인 상태처럼
사이클 내내 참인 레벨이 그 자리다.

**감지를 `Latch` 로 올려도 소용없다** — `Latch` 는 **Call 완료**를 붙잡지 leaf 판정을 바꾸지 않는다.
leaf 는 여전히 그 주소의 현재 값을 읽는다. **바꿀 것은 Type 이 아니라 «어느 주소를 읽는가» 다.**

**유지 시간을 모르면 per-cycle 하나만 써라.** 지어낸 AND 는 검증을 통과하고 현장에서 안 선다.

**생략된 대상을 가리키는 leaf 는 «거짓» 으로 읽힌다.** 생략된 Work·Call 은 Finish 가 나지 않기 때문이다.

**배선 후에는 뒤집힌다 — 방향을 보라.** InTag 가 채워지면 leaf 는 «지금 값» 이므로(§13):

| 무엇을 가리키나 | 배선 전 | 배선 후 | 어떻게 묶나 |
|---|---|---|---|
| **전진단**(ADV·작업) — 이번에 참이 된다 | 생략되면 거짓 | 생략되면 거짓 | **OR** — «실행된 하나» 를 고른다 |
| **복귀단**(RET·원위치) — 사이클 시작에 이미 참 | 생략되면 거짓 → **OR** | **생략돼도 참** → **AND** | **배선 전은 OR · 배선 후는 AND** |

**«어떻게 묶나» 는 배선 단계마다 다르다** — 표의 마지막 열을 그대로 쓰지 말고
**지금 어느 단계인지 먼저 보라.** 배선 전에 복귀단을 AND 로 묶으면
생략된 차종의 RET 이 «미완료» 라 **영영 서지 않는다.**
배선 전에 적었다가 주소를 채울 때 **OR 를 AND 로 바꿔라** — 머리말에 그 사실을 적어 두면 놓치지 않는다.

**배선 후 복귀단을 OR 로 묶으면** 생략된 차종의 후진단이 이미 참이라 **하나만으로 조건이 선다** —
실제로 물린 차종의 지그가 아직 물고 있는데 다음 단계로 간다.
그래서 §13-A2 의 **OR 층이 «실제로 실행된 하나» 를 고른다** — 생략된 둘은 거짓이므로 남지 않는다.

§13-A 의 «생략은 완료가 아니다»(`AutoAux` 가 기다리면 안 선다)와 **같은 사실의 다른 얼굴**이다.
§13-A2 의 «Group 에게 생략은 완료다» 는 **Group 멤버 판정에만** 해당한다 — leaf 판정과 다른 자리다.

**주소를 지어내야 하는 것은 앞쪽뿐이다** — §12 «지어내지 마라» 와 부딪히는 범위가 여기까지로 좁아진다.
엣지(`(R)`/`(F)`)와 값 비교(`=`)는 **값이 있어야 뜻이 있으므로** 종류와 무관하게 채워라.
`Virtual` 이든 `Latch` 든 같다 — leaf 판정을 가르는 것은 **감지 종류가 아니라 InTag 유무**이기 때문이다.
엣지(`(R)`/`(F)`) leaf 도 마찬가지다. 값이 없으면 엣지가 설 자리가 없다.
부정·값 비교·엣지뿐 아니라 **긍정 leaf 도 같다** — `Virtual` Call 은 실제 비트와 무관하게
완료되므로 InTag 가 `?` 면 «항상 참» 이 된다.

**§12 의 «모르면 지어내지 마라» 와 부딪히는 자리다.** 차종 판정은 §0 이 필수로 놓았고
대신할 «다른 사실» 이 없다 — 차종 판정이 그 사실 자체이기 때문이다. **이때는 §13 이 이긴다**:
예시 주소를 서로 다르게 부여하고 **머리말에 «차종·총괄 비트만 예시 주소, 나머지는 `?`» 를 밝혀라.**
가짜 주소가 남는 것보다 **조용히 뒤집힌 조건이 훨씬 비싸다.**
모르면 그 조건을 쓰지 말고, 쓸 수 있는 다른 사실을 찾아라.

```
✗ API,차종판정.KA4,Virtual/Virtual(100),,100MS,?, ← `/차종판정.KA4` 가 무너진다
✓ API,차종판정.KA4,Virtual/Virtual(100),,100MS,%IX3.30.0.12,
```

`/라인상태.이상총괄` 도 같은 자리다. **총괄 비트와 차종 판정은 주소를 아는 것부터 시작하라.**

### leaf 는 «지금 켜져 있는가» 인가 «끝났는가» 인가 — InTag 가 가른다

엔진을 확인했다(`WorkConditionChecker.checkConditionSpecBase`). **둘 다 맞고, 가르는 것은 InTag 다**:

```fsharp
match ioValue with
| Some v -> ValueSpec.evaluate spec.InputSpec v // IO 가 있으면 → 지금 값
| None -> rxState = Some Status4.Finish // 없으면 → 대상 Work 완료
```

| leaf 의 API 에 InTag 가 | 판정 | 읽는 법 |
|---|---|---|
| **있다** | 그 신호의 **지금 값** | «켜져 있는가» |
| **없다**(`?` 포함) | 대상 Work 의 **Finish** | «끝났는가» |

**여기서 사고가 난다.** `Normal` 동작은 **끝나면 출력이 꺼진다.**
그 API 의 InTag 를 «동작 중 신호» 로 잡아 두고 조건에 쓰면,
**끝난 순간 조건이 꺼져** 기다리던 Call 이 영영 서지 않는다.

**그래서 InTag 에 «완료 판정 비트» 를 쓰라는 것이다**(§4·§12):

```
✗ API,지그.전진,…,%IX5.41.0.06,… ← 리드스위치 raw. 미는 동안만 선다
✓ API,지그.전진,…,%MX1.2051.03,… ← «전진단» 판정 비트. 물린 뒤에도 서 있다
```

`…전진단`·`…후진단` 은 **도착한 상태를 유지하는 비트**다. 값으로 읽어도 «끝났다» 와 같다.
**§4 의 «판정 비트를 InTag 로» 가 이 문제의 답이었다** — 다점 확인 때문만이 아니다.

**InTag 를 `?` 로 둔 모델은 자동으로 «완료» 판정이 된다.** 배선 전 설계 단계에서
조건이 뜻대로 도는 이유가 이것이고, 주소를 채울 때 «동작 중 신호» 를 넣으면 갑자기 멈춘다.


### 세 조건은 «사는 자리» 가 다르다

조건을 적기 전에 먼저 정할 것은 표기가 아니라 **자리**다.

| 조건 | 붙는 곳 | 엔진이 하는 일 |
|---|---|---|
| `AutoAux` | **Call 만** | 서면 그 Call 이 시작한다 |
| `ComAux` | **Call 만** | 서면 그 Call 이 시작한다 |
| `SkipAction` | Work · Call | **만족하면 건너뛴다** (나머지 둘과 방향이 반대) |

Work 에 `AutoAux` 나 `ComAux` 를 적으면 `AI014` 로 거부된다. 엔진에 Work 용 Aux 자리가
아예 없기 때문이다 — 막히는 편이 낫다. 조용히 무시됐다면 «조건을 걸었는데 왜 안 듣지» 로
한나절을 버렸을 것이다.

### AutoAux 와 ComAux 는 무엇이 다른가

**엔진에게는 다르지 않다.** 둘 다 모아 AND 로 함께 본다:

```
evalExpr AutoAux && evalExpr ComAux // WorkConditionChecker.fs
```

둘 다 서야 Call 이 나간다. 어느 쪽에 적든 동작은 같다. 그러면 왜 둘인가 — **읽는 사람을
위한 분류**다. 차체라인에서는 이렇게 가른다:

| | 뜻 | 예 |
|---|---|---|
| `AutoAux` | **이 공정이 진행될** 조건 | 선행 공정 완료 · 지그 클램프됨 · 소재 있음 |
| `ComAux` | **어떤 동작이든 허가되는** 조건 | 자동운전 중 · 안전문 닫힘 · 비상정지 해제 · 에어압 정상 |

가르는 기준은 하나다 — **이 조건이 이 Call 에만 걸리는가, 라인 전체에 걸리는가.**
안전문은 모든 Call 에 똑같이 걸린다 → `ComAux`. 지그 클램프는 용접에만 걸린다 → `AutoAux`.

섞어 적어도 돌아간다. 하지만 라인이 통째로 멈췄을 때 **`ComAux` 만 훑으면 되는 상태**와
Call 마다 뒤져야 하는 상태의 차이는 크다. 실제 현장에서 «왜 안 서는가» 를 찾는 시간이
그대로 갈린다.

한 Call 이 둘 다 갖는 것이 정상이다:

```
COND,차체.용접.용접로봇.타점,AutoAux,지그.클램프,,,
COND,차체.용접.용접로봇.타점,ComAux,안전문.닫힘확인 & 비상정지.해제확인 & 운전반.자동운전,,,
```


조건 leaf 는 «그 신호가 켜졌는가» 가 기본이지만, 차체라인에는 그것으로 부족한 자리가 있다.

| 표기 | 뜻 | 차체라인 사례 |
|---|---|---|
| `A.B` | 켜져 있는 동안 | 클램프가 물려 있다 |
| `A.B(R)` | **켜지는 순간** | 기동 버튼을 누른 그 순간 |
| `A.B(F)` | **꺼지는 순간** | 차체가 빠져나간 그 순간 |
| `/A.B` | 꺼져 있는 동안 | 안전문이 열려 있다 |
| `A.B=100` | 값이 100 | QR 이 읽은 차종 코드 |

### 엣지를 써야 하는 자리

**«동안» 과 «순간» 은 다르다.**

```
COND,차체.차종판독.QR리더기.코드읽기,AutoAux,조작반.사이클기동(R),,,
```

버튼을 누르고 **있는 동안** 조건이 서면, 손을 떼지 않는 한 계속 재기동된다.
`(R)` 은 누르는 그 순간 한 번만 통과시킨다.

```
COND,차체.게이트닫힘.진출게이트.닫힘,AutoAux,이탈판정.통과(F),,,
```

차체가 **없는 동안** 이 아니라 **빠져나간 순간** 게이트를 닫는다.
`/이탈센서.감지` 로 적으면 차체가 오기 전부터 조건이 서 있어 게이트가 미리 닫힌다.

### 값을 안 적으면 어떻게 되나 — csvForAI 는 안전하다

DS2 CORE 명세 `COND.INPUT.ALL` 은 «판정 불가는 false 가 아니다» 라고 말한다.
실제 구현에서 `ValueSpec.UndefinedValue` 는 **`true` 로 통과한다**(`ValueSpec.fs`) —
조건을 걸어 두고도 «조건이 없는 것» 이 되는 함정이다.

**csvForAI 경로에서는 걱정하지 않아도 된다.** 매퍼가 기대값 없는 leaf 에
`BoolValue(true)` 를 **명시적으로** 넣는다(`AiCsvMapper.fs`). `UndefinedValue` 가 남지 않는다.
Promaker 에서 손으로 만든 조건과 다른 점이다.

### `=값` 이 쓰이는 자리는 둘이고, 뜻이 다르다

같은 `=1200` 을 두 군데 적을 수 있는데 **하는 일이 다르다**:

| 어디 | 예 | 하는 일 |
|---|---|---|
| **API 행 InTag** | `T축거리@%IW6.21.2:INT=1200` | ApiCall 의 **`InputSpec`** — 받은 값이 «활성» 인지 판정 |
| **API 행 OutTag** | `T축목표@%QW6.21.9:INT=1200` | ApiCall 의 **`OutputSpec`** — 엔진이 **내보낼 값** |
| **COND leaf** | `COND,…,AutoAux,위치감시.현재위치=1200` | 조건이 **비교하는 값** |

셋 다 산다. 다만 **하는 일이 다르므로 자리를 골라야 한다**:

- **조건을 걸려면 COND 쪽**이다. API 행에만 적으면 조건 `ValueSpec` 은 `BoolValue(true)` 로 남는다
- **값을 내보내려면 OutTag 쪽**이다. 서보 목표값이 여기 간다
- 둘은 **함께 쓸 수 있다** — OutTag 로 1200 을 내보내고 COND 로 현재값이 1200 인지 본다

적재 확인: COND 에 적으면 `Int64Value(1200L)` 로 실린다.

### 서보에 위치를 주는 길은 둘이다

| 방법 | 어떻게 | 언제 |
|---|---|---|
| **프로그램 번호** | `PG_WORK` 비트로 티칭된 자리를 고른다 | 차종처럼 **정해진 위치** |
| **목표값 쓰기** | `%QW6.21.9` 에 거리값을 써 넣는다 | **가변 위치** |

①은 «몇 번 자리로» 이고 ②는 «몇 mm 로» 다.

②는 **OutTag 에 `=값` 으로 적는다** — `목표@%QW6.21.9:INT=1200`.
ApiCall 의 `OutputSpec` 으로 실리고 엔진이 그것으로 내보낼 값을 만든다.
(매퍼를 이었다. 그 전에는 주소만 실리고 값이 사라졌다.)

**목표를 써 넣은 «뒤» 에 기동한다.** 순서가 바뀌면 이전 목표로 간다 —
기동 Call 의 `AutoAux` 에 «목표값 쓰기 완료» 를 걸어야 한다.

### 워드 신호는 비트와 다르게 읽는다

서보에는 워드가 있다 — 위치·전류·알람코드:

```
API,위치감시.현재위치,Virtual/Virtual(100),,?,T축거리@%IW6.21.2:INT,
# 알람코드는 «정상이 0» 이다 — 평소 꺼진 비트와 같다. 감지를 Virtual 로(§1).
API,위치감시.알람코드,Virtual/Virtual(100),,?,알람@%IW6.21.6:INT,

COND,차체.위치검증.위치감시.현재위치,AutoAux,위치감시.현재위치=1200 & 위치감시.알람코드=0,,,
```

- 주소가 `%IW`/`%QW` 다(`%IX`/`%QX` 가 아니다)
- **자료형을 반드시 적는다** — `:INT` 를 빠뜨리면 BOOL 로 뭉개져 값 비교가 무너진다
- `알람코드=0` 처럼 **«정상은 0»** 인 신호가 있다. 켜짐/꺼짐이 아니라 코드다

**완료 비트와 위치값은 다른 사실이다.** `PRG_COMP_1` 은 «프로그램이 끝났다» 이고
거리값 1200 은 «지금 여기 있다» 이다. 끝났는데 엉뚱한 곳에 서 있을 수 있다 —
정밀이 필요한 자리는 둘 다 본다.

### 값 비교 — bool 이 아닌 것

QR·비전·토크처럼 숫자를 읽는 신호는 `=값` 으로 비교한다.

```
API,QR리더기.코드읽기,Virtual/Virtual(100),,3S,차종코드@%IW3.10.2:INT,
COND,차체.게이트열림.진출게이트.열림,AutoAux,QR리더기.코드읽기=100,,,
```

`:DINT` 로 자료형을 적어야 정수로 읽힌다. 생략하면 BOOL 이 되어 `=100` 이 뭉개진다.

### SkipAction 에는 엣지가 듣지 않는다

SkipAction 판정은 `Ready → Going` 전이 **그 순간 1회**다. 엣지 조건은 «이번 clock 에 값이
바뀌었는가» 를 함께 보는데, 두 순간이 정확히 겹칠 일이 드물어 사실상 늘 거짓이 된다.
엔진이 `(R)`→`A접`, `(F)`→`B접` 으로 접어 버리므로 **적어도 의미가 없다.**

엣지는 `AutoAux` · `ComAux` 에만 쓴다 — 그쪽은 조건 루프에서 반복 평가되기 때문이다.

## 13-A. 생략한 Work 를 기다리게 두지 마라

> **배선 후에는 한 겹 더 보라.** InTag 가 채워지면 복귀단 leaf 는 «생략돼도 참» 이 되어
> 이 규칙이 뒤집힌다 — §13 「배선 후에는 뒤집힌다」 표로 가라.


DS2 CORE 명세 `CALL.DONE.SKIP_BLOCK` 이 말한다 —
**이번 대상 Work 의 생략은 기다리는 Call 을 완료시키지 않는다.**

사양 분기에서 `SkipAction` 으로 Work 를 건너뛰었는데 다른 Call 이 그 Work 의 완료를
`AutoAux` 로 기다리고 있으면 **그 Call 은 영원히 서지 않는다**. 엔진은 «생략» 을 «완료» 로
쳐주지 않는다(`workCompletion` 이 실행 회차 epoch 증가를 요구한다).

```
✗ 보강용접 Work (사양 B 면 Skip)
 마무리 Call.AutoAux = 보강용접 완료 ← 사양 A 차종에서 멈춘다

✓ 마무리 Call.AutoAux = 공통 고정 완료 ← 생략되지 않는 사실을 기다린다
```

**생략될 수 있는 것을 기다리지 말고, 생략되지 않는 사실을 기다려라.**
Ver110 도 같은 말을 한다 — 판정이 아직 없으면 «생략하지 않는 선행» 에서 준비를 기다린다.

또한 **복귀중(Homing)은 완료가 아니다**(`CHK.BIT_DONE`). 재무장 중인 Work 를
Start 선행으로 기다리면 그 조건은 아직 서지 않는다.

## 13-A0. «생략되지 않는 것» 을 먼저 찾아라

차종·사양 분기가 있는 셀에서 **세 가지를 정해야 하는데 셋 다 같은 물음**이다:

| 무엇을 정하나 | 어디 |
|---|---|
| `ComAux`(안전 허가)를 어느 Call 에 거나 | §13-C |
| `AutoAux` 가 **무엇의 완료**를 기다리나 | §13-A |
| `Group` **전달자**를 누구로 두나 | §13-A2 |

**답은 하나다 — «이번 차체가 무엇이든 반드시 도는 것».**

**OR 층은 순서 조건이 아니라 «안전 조건» 이기도 하다.**
`Group` 전달자에서 나가는 `Start` 는 «전원 완료» 뒤이므로 순서만 보면 OR 층이 없어도 된다.
**그러나 빼면 차종 셋이 전부 생략돼도 Group 이 닫혀 «정체 모를 차체를 그냥 처리한다».**
§13 ③ 이 «차종 미판독이면 셀이 서는 것이 맞다» 고 한 그 «섬» 을 만드는 장치가 OR 층이다 —
**순서 때문에 필요 없어 보여도 빼지 마라.** 보통 이런 것들이다:

- **공용 설비**(기준핀·안착센서·반입출 컨베이어 — §1)
- 차종·사양과 무관한 **공정 단계**(배출 확인·계측 완료)

**모델을 적기 전에 이것부터 목록으로 만들어라.** 셋을 따로 판단하면 세 번 틀린다.

**그 목록을 머리말 주석에 남겨라** — `[주소]`·`[시간]` 옆이 그 자리다. 안 남기면 다음 사람이 처음부터 다시 만든다.

**목록은 «Call» 단위로 만들어라 — Work 단위로는 모자란다.**
한 Work 안에 «반드시 도는 Call» 과 «생략될 수 있는 Call» 이 **함께 있을 수 있다**:

```
WORK,차체.볼팅,,런너.본체결 > 런너.보강체결 > 런너.원위치,,,
COND,차체.볼팅.런너.보강체결,SkipAction,/사양판정.보강,,,
```

이 Work 는 «생략되지 않는다» 고 적어 두면 틀린다 — 안의 `보강체결` 은 생략된다.
**`ComAux` 를 걸 자리도, `AutoAux` 가 기다릴 대상도 Call 단위로 고른다.**
생략될 수 있는 것밖에 없다면 **OR 층이나 탈출 층**으로 «어느 쪽이든 하나» 를 만든다(§13-A2).

## 13-A1. 고정·해제를 한 Work 로 접을 것인가 — 결정표

§13-B 와 §13-A2 에 답이 나뉘어 있어 매번 다시 판단하게 됐다. **한 표로 닫는다.**

| 차종·사양 분기 | 사이 작업이 **토큰을 받나** | 어떻게 | 왜 |
|---|---|---|---|
| **있다** | 무관 | **두 Work**(고정/해제) + `Group` 동반자 | 생략되려면 Group 동반자여야 한다(§13-A2) |
| 없다 | **받는다**(그 사이가 공정 위상이다) | **두 Work** | 토큰이 머물 Work 가 있어야 한다 |
| 없다 | 안 받는다(Group 동반자로 붙는다) | **한 Work 왕복 + `RET` 에 `AutoAux`** | AutoAux 가 사이를 벌린다(§13-B) |
| 없다 | 사이에 작업이 없다 | **한 Work 왕복**(`ADV > RET`) | 가장 단순하다 |

**순서대로 물어라 — «분기가 있는가» → «사이 작업이 토큰을 받는가».**
분기가 있으면 사이 사정과 무관하게 두 Work 다. 분기가 없으면 **토큰이 가른다** —
그 사이가 공정 위상이면(압착·용접·계측처럼 차체가 머문다) Work 를 나눠야 토큰이 머물 자리가 생긴다.

**한 파일에 두 모양이 섞여도 된다** — 차종 지그는 두 Work, 공용 압착은 한 Work 왕복.

## 13-A2. Group 안에 «생략될 수 있는 Work» 를 두어도 된다

차종 분기가 있는 용접 셀에서 반드시 부딪히는 물음이다:

> 고정 Work 를 차종 수만큼 만들면 그중 하나만 돌고 나머지는 `SkipAction` 으로 생략된다.
> `Group` 은 «전원 완료» 를 기다리는데, **생략된 멤버 때문에 Group 이 영영 안 닫히지 않는가?**

**닫힌다.** DS2 디자인 패턴 Ver110 §3.1 이 명시한다 —
**«Group 은 실행한 기능과 생략한 기능의 완료를 모두 기다린다.»**
생략은 그 Work 에 대해 **완료로 친다.**

§13-A 와 헷갈리지 마라. 둘은 **다른 자리**다:

| | 무엇이 기다리나 | 생략을 완료로 치나 |
|---|---|---|
| **`Group` 멤버** | Group 전체 | **친다** — 닫힌다 |
| **`AutoAux` 로 그 Work 를 기다리는 Call** | 다른 Call | **안 친다** — 영영 안 선다(§13-A) |

그러니 차종 분기는 이렇게 적을 수 있다:

```
WORK,차체.기준고정,,기준핀.ADV > 기준핀.RET,,, ← 전달자: 차종 무관 공용
WORK,차체.KA4고정,Ignore,KA4지그.ADV > KA4지그.RET,,,
WORK,차체.MV고정,Ignore,MV지그.ADV > MV지그.RET,,,
ARROW,차체.기준고정,Group,차체.KA4고정 ; 차체.MV고정 ; 차체.용접,,,
COND,차체.KA4고정,SkipAction,/판정.KA4,,,
COND,차체.MV고정,SkipAction,판정.KA4,,,
```

**차종 셋 중 하나만 도는 것을 기다릴 때는 OR 층을 쓴다.**
어느 차종이 올지 모르므로 «생략되지 않는 사실»(공용 설비)을 AND 로 깔고,
차종 쪽은 OR 로 묶는다 — `&` 와 `|` 는 한 괄호에 못 섞으니 괄호로 층을 나눈다:

```
COND,차체.용접.로봇.타점,AutoAux,기준핀.ADV & (KA4지그.ADV | MV지그.ADV | RJ지그.ADV),,,
```

**생략될 수 있는 Work 는 `Start` 사슬에 두지 말고 반드시 `Group` 동반자로 두어라.**
사슬에 두면 생략된 Work 가 토큰을 넘기는지가 불분명하지만, Group 동반자는 «생략도 완료» 라
위에서 보증된다. 차종 고정·사양 공정·OK/NG 반출이 전부 이 판단에 걸린다.

**동반자 수에 상한은 없다.** 실측으로 6개까지 확인했고(실측 산출물) 검증도 조용하다.
다만 **여섯을 넘으면 읽기 어려워진다** — 공정 위상이 정말 같은지 다시 보라.
«같은 제품에 동시에 일어나는 일» 이 아니면 Work 를 나누는 것이 맞다.

**다만 전달자(비-Ignore)는 생략되지 않는 Work 여야 한다.** 전달자가 건너뛰어지면
토큰을 넘길 곳이 없다 — 차종 셋이 다 생략될 수 있으면 **공용 Work 를 전달자로 두어라**
(예: 차종 무관 기준핀·안착확인).

---

### 한 Work 안에서 Call 하나만 건너뛸 때

Work 를 나눌 것까지 없고 **Call 하나만 빼면 될 때**가 있다 — 사양에 따라 볼트 한 점을 더 죄는 식.
`SkipAction` 은 **Call 에도 붙는다**(4마디 경로):

```
WORK,차체.체결,,런너.1번 > 런너.2번 > 런너.3번,,,
COND,차체.체결.런너.3번,SkipAction,/사양판정.보강,,, ← 보강 사양이 아니면 3번을 건너뛴다
```

**Work 레벨과 무엇이 다른가**: Work 를 건너뛰면 그 안의 Call 이 전부 빠지고
`Group` 동반자로 두어야 한다(§13-A2). **Call 하나만 빠지는 것은 사슬이 그대로**라
`>` 로 이어 두어도 된다 — 생략된 Call 은 다음 Call 로 그냥 넘어간다.

**기능 차이가 크면 Work, 한 동작만 다르면 Call.**

**짝(ADV/RET)은 같은 조건으로 함께 건너뛰어라.** ADV 만 빼고 RET 을 남기면
«걸지 않은 핀을 푸는» 모델이 된다:

```
COND,차체.고정.받침.ADV,SkipAction,/판정.KA4,,,
COND,차체.해제.받침.RET,SkipAction,/판정.KA4,,, ← 같은 조건
```

**생략될 수 있는 동작 «뒤» 에 와야 하는 동작에는 «탈출 층» 을 쓴다.**
뒤따르는 비-생략 사실이 없을 때가 있다 — 보강 체결(생략 가능) 다음의 원위치가 그렇다.
**«그 동작이 끝났거나, 애초에 그 사양이 아니거나»** 를 OR 로 묶는다:

```
COND,차체.복귀.런너.원위치,AutoAux,기준고정.ADV & (런너.보강체결 | /사양판정.보강),,,
```

앞 층은 생략되지 않는 사실, 뒤 괄호가 탈출 층이다. **둘 중 하나는 반드시 참이 되므로 선다.**

**앞 층조차 생략될 수 있으면 두 줄로 쌓아라.** 차종 검사 셋이 전부 생략 가능한 경우다 —
`&` 와 `|` 를 한 괄호에 못 섞으니, **같은 종류 COND 두 줄 = 누적 AND** 를 쓴다:

```
COND,차체.계측.계측기.원위치,AutoAux,검사_KA4 | 검사_MV | 검사_RJ,,, ← 차종 OR 층
COND,차체.계측.계측기.원위치,AutoAux,루프검사 | /사양판정.선루프,,, ← 사양 탈출 층
```

두 줄이 AND 로 누적되므로 «어느 차종이든 하나는 끝났고, 루프검사를 했거나 그 사양이 아니다» 가 된다.

**생략될 수 있는 Call 의 완료도 기다리지 마라**(§13-A 의 Call 판).
그 Call 이 빠지면 완료가 오지 않는다 — 앞뒤로 생략되지 않는 Call 을 기다려라.

### 판정 결과로 경로를 가를 때

자동 검사·계측은 **판정 결과가 다음 동작을 가른다**(OK 반출 / NG 반출).
분기도 §13-A2 와 같은 모양이다 — **양쪽을 Group 동반자로 두고 반대 방향 `SkipAction`**:

```
WORK,도어.OK반출,Ignore,반출로봇.정상반출 > 반출로봇.원위치,,,
WORK,도어.NG반출,Ignore,반출로봇.NG반출 > 반출로봇.원위치,,,
WORK,도어.배출확인,,완료센서.배출,,, ← 생략되지 않는 전달자
ARROW,도어.배출확인,Group,도어.OK반출 ; 도어.NG반출,,,
COND,도어.OK반출,SkipAction,계측.판정코드=1,,, ← NG 면 건너뛴다
COND,도어.NG반출,SkipAction,계측.판정코드=0,,, ← OK 면 건너뛴다
```

**전달자는 판정과 무관한 Work** 여야 한다(§13-A2). 둘 다 생략될 수 있으면 토큰이 죽는다.

## 13-B. 고정과 용접은 «직렬» 이 아니라 «협동» 이다

차체라인을 적을 때 가장 흔한 모양은 이것이다:

```
클램프 Work → 용접 Work → 언클램프 Work ← Work 3개 직렬
```

**DS2 디자인 패턴 Ver110 §3.1 은 이것을 다르게 본다.** 고정은 «한 장치의 왕복» 이므로
Work 하나이고, 고정과 용접은 **함께 시작**한 뒤 실행 순서를 Call 조건으로 정한다:

```
Group[ 고정 Work ‖ 용접 Work ]

고정 Work: 전진 Call ─Start→ 후진 Call
용접 Call.AutoAux = 이번 전진 완료
후진 Call.AutoAux = 이번 용접 완료
```

CSV 로는 이렇게 적는다:

```
WORK,패널.고정,,키지그.전진 > 키지그.후진,,,
WORK,패널.용접,Ignore,용접건.타점 > 용접건.원위치,,,
ARROW,패널.고정,Group,패널.용접,,,
COND,패널.용접.용접건.타점,AutoAux,키지그.전진,,,
COND,패널.고정.키지그.후진,AutoAux,용접건.타점,,,
```

### 왜 직렬이 아닌가

**고정 Work «전체» 의 완료를 용접 시작 조건으로 쓰면 후진까지 기다리게 된다.**
그런데 후진은 용접이 끝나야 하므로 — 서로 기다리며 멈춘다. Ver110 이 명시적으로 경고하는
데드락이다. `Group` + Call `AutoAux` 는 **«전진 완료» 라는 더 작은 사실**을 조건으로 삼아
이 고리를 끊는다.

Work 수도 줄어든다. 3개가 2개가 되고, 클램프와 언클램프가 «같은 장치의 왕복» 이라는 사실이
모델에 남는다.

### Group 동반자 앞에는 선행 Work 가 있어야 한다

동반자는 **전달자의 선행을 물려받는다**. 그래서 전달자가 `Source` 면 물려받을 선행이 없어
동반자가 그래프 검증에서 «Source 후보» 로 잡힌다. 고정·용접 앞에 반입 Work 를 두면 해결된다 —
실제 라인도 그 모양이다.

### 고정·해제를 한 Work 로 접을 것인가 두 Work 로 가를 것인가

> **결정표는 §13-A1 에 있다.** 아래는 그 근거다.

§13-B 는 «고정은 한 장치의 왕복 = Work 하나», §13-A2 의 차종 예제는 «고정»·«해제» 두 Work 다.
**가르는 것은 «생략될 수 있는가» 다**:

| | 어떻게 |
|---|---|
| 왕복 사이에 **다른 공정이 없다** | **한 Work 왕복**(`ADV > RET`) — §13-B |
| 왕복 사이에 **작업이 들어간다**(분기든 반전이든) | **두 Work** — 왕복 하나를 `Group` 동반자로 두면 **고정과 해제가 동시에 시작**한다. 사이에 작업이 들어갈 자리가 없다 |

**한 Work 왕복이어도 «RET 의 `AutoAux`» 로 사이를 벌릴 수 있다** —
`ADV > RET` 로 두고 `RET` 에 «검사 완료» 를 걸면 그 사이에 작업이 들어간다.
**Work 를 가르는 진짜 이유는 «생략» 과 «토큰» 이다** — 차종 분기로 생략돼야 하거나
그 사이 단계가 토큰을 받아야 하면 두 Work 로 간다.

**«해제까지 함께 생략된다» 는 것은 문제가 아니다** — 짝은 같은 조건으로 함께 건너뛰는 것이 맞다(§13-A2).
문제는 **순서**다: 왕복 하나는 «ADV 하고 바로 RET» 이라 그 사이에 용접·도포를 넣을 수 없다.

**한 파일에 두 모양이 섞여도 된다** — 차종 지그는 두 Work, 공용 압착은 한 Work 왕복.
**설비마다 분기 여부가 다르기 때문이다.**

### 직렬이 맞는 자리도 있다

공정 위상이 실제로 바뀌면 Work 를 나누는 것이 맞다 — 반입 → 고정 → 반출은 직렬이다.
**한 장치의 왕복인지, 다른 공정 단계인지**가 기준이다.

## 13-C. 공유 자원 — 자리가 비는 것과 장치가 도는 것은 다르다

로봇 한 대를 두 라인이 번갈아 쓴다. 이때 흔한 실수는 **한 조건으로 둘을 묶는 것**이다.

> **다음 제품을 받는 조건**과 **공유 자원을 다시 쓰는 조건**은 따로 연결한다.
> — DS2 디자인 패턴 Ver110 §3.4

지그가 비었다고 로봇을 쓸 수 있는 것이 아니다. **앞 라인이 아직 반납(원위치) 중일 수 있다.**
제품 수락만 제한하면 생산량은 맞아 보여도 반납 전에 다른 요청이 나간다.

```
COND,A라인.로봇작업.공유로봇.A작업,ComAux,공유로봇.B원위치,,,
COND,B라인.로봇작업.공유로봇.B작업,ComAux,공유로봇.A원위치,,,
```

상대 라인의 **원위치 완료**를 조건으로 건다. 라인 전체에 걸리는 허가이므로 `ComAux` 가 맞다(§13).

**어느 Call 에 거는가**: **그 Work 에서 «반드시 실행되는» Call 에 건다.**

보통은 첫 Call 이면 된다 — 그 Work 가 못 서면 안의 Call 도 못 선다.
**그런데 첫 Call 이 생략될 수 있으면 규칙이 깨진다.** `SkipAction` 은 차단이 아니라 건너뜀이라,
그 Work 는 **자동운전·비상정지 허가 없이 돈다.** 비상정지가 걸려도 그 동작만 움직인다 —
검증은 통과한다.

| 그 Work 의 첫 Call 이 | 어디에 거나 |
|---|---|
| 반드시 실행된다 | **첫 Call 하나** |
| 생략될 수 있다 | **배타적 대안 Call 전부**, 또는 **«먼저 도는»** 비-생략 Call 로 옮긴다 |
| `;` 나열(병렬) | **전부에 걸어라** — 한 Call 을 막아도 **형제 Call 은 나간다** |
| **읽기 전용 Call**(센서·판정 비트) | **걸지 않는다** — 막을 출력이 없다 |
| `>` 사슬의 **두 번째 이후 Call** | **걸지 않는다** — 앞 Call 이 막히면 뒤도 못 나간다 |
| `;` 형제에 **세 종류가 섞였다** | **허가가 필요한 것에만** 건다 — 읽기 전용·안전 동작은 빼고 센다 |

**동작 종류 말고 «무엇을 내보내는가» 로도 갈린다**:

| Call 이 | 허가 |
|---|---|
| **비트 지령**(코일을 켠다) | **건다** — 단 «안전 상태로 가는 동작» 이면 면제가 이긴다 |
| **워드 쓰기**(목표값을 써 넣는다) | **건다** — 값이 남아 다음 기동에 쓰인다 |
| **읽기 전용**(센서·판정·워드 읽기) | 걸지 않는다 |
| **작은 서보의 원점**(마커 헤드 등) | 면제해도 된다 — 질량이 작아 중간에 서도 무해하다 |
| **안전 상태로 가는 동작** | **걸지 않는다** — 걸면 비상정지 때 그 자리에 멈춘다 |
**«해제·복귀 = 안전» 은 전제다 — 설비마다 확인하라.** 깨지는 것들이 있다:

| 동작 | 안전한가 |
|---|---|
| 클램프 RET · 로봇 원위치 · 펌프 정지 | **안전** — 면제한다 |
| **회전락 언락** | **위험** — 풀면 물고 있던 것이 자유로워진다 |
| **리프트 하강** | **위험** — 중력 방향으로 내린다 |
| **회전 지그 복귀** | **위험** — 움직이는 설비다 |
| **회전락 «락»** | **안전** — 걸어야 자유로워지지 않는다. 면제한다 |
| **셔틀·캐리어 «원점»** | **위험** — 질량이 크다. 허가를 걸어라 |

**«비상정지가 걸렸을 때 그 동작이 일어나도 되는가» 로 판정하라.** 아니면 허가를 걸어라.

표에 없는 설비는 **두 물음으로** 가른다:
- **사람이나 차체 위로 움직이는가**(하강·셔터 닫힘·게이트 닫힘) → **위험. 허가를 걸어라**
- **열리거나 물러나는가**(셔터 열림·부스 개방·스토퍼 후퇴) → **안전. 면제해도 된다**

**질량과 방향이 기준이다** — 「해제·복귀」라는 이름이 아니다.

| 먼저 도는 Call 이 **면제 대상**이다 | **다음 Call 로 옮긴다** — 비상정지 때 해제는 되고 다음 동작만 선다 |

**같은 식이 여러 줄로 복사되는 것은 피할 수 없다.** v1 에 «공통 조건을 한 곳에 두는» 자리가 없다.
§10 의 «Call 마다 흩뿌리지 마라» 는 **아무 데나 거는 것**을 막는 말이지 복사 자체를 금지하는 것이 아니다.

**대신 두 가지를 하라**:
- **식을 한 글자도 바꾸지 말고 그대로 복사하라** — 한 줄만 다르면 찾을 수 없다
- **머리말에 «라인 허가 식을 N 곳에 걸었다» 를 적어라** — 안전 신호가 바뀌면 그 N 을 세어 고친다

걸어야 할 자리는 위 표가 정한다. **그 표를 지킨 결과로 늘어난 줄은 결함이 아니다.**
| `;` 나열인데 **생략될 수 있는 것이 섞임** | 비-생략 Call 에 건다. 없으면 대안 전부 |

**«옮긴다» 에는 «먼저 도는» 이 붙어야 한다.** 비-생략 Call 이 **맨 뒤**에 있으면
허가가 거기에만 붙어 — **비상정지 중에도 앞의 동작이 끝까지 돈 뒤** 멈춘다.
차종별 서보 PRG 셋 다음의 `원점` 이 정확히 그 모양이다. **앞에 없으면 대안 전부에 걸어라.**
그 Work 가 못 서면 안의 Call 도 못 서므로, 모든 Call 에 반복해 걸 필요가 없다.
«모았다» 는 **분류** 를 말하는 것이지 한 자리에 물리적으로 합치는 것이 아니다 —
v1 에 그런 자리는 없다.

### 반납이 무슨 사건인지 정하라

Ver110 이 구분하라고 말하는 넷이다 — **다 다르다**:

| 사건 | 뜻 |
|---|---|
| 작업 종료 | 용접·체결이 끝났다 |
| 공구 이탈 | 건이 제품에서 떨어졌다 |
| 반납 동작 완료 | 로봇이 원위치로 돌아왔다 |
| 이전 제품의 소비 완료 | 그 제품이 라인을 떠났다 |

차체라인에서 다음 요청의 조건으로 쓸 것은 보통 **반납 동작 완료**(원위치)다.
「작업 종료」로 걸면 로봇이 아직 제품 위에 있는데 다른 라인이 부른다.

### 반납 조건을 양쪽 대칭으로 걸면 첫 사이클에 멈춘다

**설비(Passive) Work 는 전부 `Ready` 로 시작한다.** 실측으로 확인했다 —
매퍼가 만드는 `공유로봇_Flow.A원위치` 등이 모두 `Ready` 다. 아직 «완료» 가 아니다.

그래서 이렇게 적으면 **둘 다 영영 서지 않는다**:

```
✗ COND,A라인.로봇작업.공유로봇.A작업,ComAux,공유로봇.B원위치,,,
✗ COND,B라인.로봇작업.공유로봇.B작업,ComAux,공유로봇.A원위치,,,
```

A 는 B 의 반납을, B 는 A 의 반납을 기다리는데 **둘 다 아직 돈 적이 없다.**
파서도 그래프 검증도 통과한다 — «지침을 다 지키면 멈추는 모델» 과 같은 부류다.

### «원위치 완료» 를 조건으로 읽어도 되는가 — 짝이 있으면 된다

공유 자원의 반납 조건(`ComAux,로봇.A원위치`)은 **그 Finish 가 얼마나 오래 서 있는가**에 달렸다.
캐스케이드 구조를 확인했다(`ImportPlan.Device.fs:283`):

| 디바이스 | 재무장 | 조건으로 읽기 |
|---|---|---|
| **API 가 둘 이상**(작업+원위치 — §14 가 권하는 모양) | 다음 동작이 돌 때 상대를 되돌린다 | **안전하다** — 다음 사이클까지 Finish 가 선다 |
| **API 가 하나** | `DONE` 더미가 **즉시 Finish** 하고 바로 되돌린다 | **위험하다** — 읽을 틈이 짧다 |

**§14 의 «액추에이터는 짝으로 적어라» 가 여기에도 걸린다.**
반납·완료를 조건으로 읽을 설비는 **반드시 짝을 적어라** — 구조적 Source 후보를 없애는 것보다
이쪽이 더 중요한 이유다.

**설비 Work 에 초기 `Finish` 를 줄 수단은 v1 에 없다.** `WORK` 행의 `Finish` 는
Active Work 전용이고, 설비 Work 는 매퍼가 만들기 때문이다. 그래서 **조건 쪽을 비대칭으로** 만든다.

«셔틀이 초기에 원점에 있다» 같은 전제는 **머리말 주석에 남겨라** — 모델에는 못 적는다.

**규칙: 먼저 도는 쪽을 정하고 한쪽에만 건다.**

**셋 이상이 쓰면 «첫 사용만» 면제한다:**

```
COND,차체A.이송.갠트리.PRG1,ComAux,… ← 첫 사용: 반납 조건 없음
COND,차체B.이송.갠트리.PRG2,ComAux,갠트리.원점,,, ← 둘째부터 상대 반납을 기다린다
COND,차체C.이송.갠트리.PRG3,ComAux,갠트리.원점,,,
```

**«먼저 도는 하나» 를 빼고 나머지 전부에 건다.**

**무엇으로 정하나** — 물리가 정한다:

| 구조 | 먼저 도는 쪽 |
|---|---|
| 파이프라인(직렬) | **앞 스테이션** — 첫 사이클에 뒤가 비어 있다 |
| 2열 병렬 | 아무 쪽이나. **`Finish` 를 준 쪽의 상대**가 먼저 돈다(§7) |
| 공유 로봇 | 물리적으로 먼저 닿는 자리 |

**앞 스테이션의 «보내도 되는가» 는 모델 밖이다.** 뒤가 비었는지 확인하려고 조건을 걸면
첫 사이클에 멈춘다(설비 Work 는 전부 Ready). **PLC 인터록이 할 일**이고,
모델은 «13% 만 그린다»(§12). 머리말에 «ST 간 인터록은 PLC» 를 적어 두어라.

```
✓ COND,B라인.로봇작업.공유로봇.B작업,ComAux,공유로봇.A원위치,,,
```

A 가 먼저 돌고, B 는 A 의 반납을 기다린다. 두 번째 사이클부터는 A 도
B 가 끝나야 지그가 비므로 자연히 교대가 된다 — **Work 사슬이 이미 막고 있다.**

Active Work 는 `Finish` 로 초기 상태를 줄 수 있지만(§7),
**설비 Work 에는 그 수단이 없다.** 그래서 조건 쪽을 비대칭으로 만든다.

### API 를 나눌 때와 나누지 말아야 할 때

파이프라인에서 Flow 여럿이 한 설비를 부른다. **나눌지 말지가 먼저다**:

| 설비가 하는 일 | API | 예 |
|---|---|---|
| 제품마다 **다른 동작** | **나눈다** | 로봇이 A는 8타·B는 4타 용접 → `로봇.A작업`/`로봇.B작업` |
| 제품마다 **같은 동작** | **하나로 둔다** | 셔틀이 A도 B도 똑같이 옮긴다 → `셔틀.전진` |

**같은 동작이면 나누지 마라.** 나누면 **물리적으로 없는 둘째 셔틀이 모델에 생긴다.**

하나로 두어도 문제가 없다는 것을 확인했다 — 두 Flow 가 같은 `셔틀.전진` 을 불러도
매퍼는 Passive Work 를 **하나만** 만들고(`셔틀_Flow.전진`), Call 은 Flow 마다 따로 생긴다.
그래프 검증도 조용하다.

**«반납» 이라는 사건이 없는 공유 설비도 있다.**
축적식 체인 컨베이어가 그렇다 — 구간 전체를 계속 밀고, **자리는 게이트가 정한다.**
이때는 **배타 조건을 걸지 마라** — 걸면 §13-C 의 대칭 반납이 되어 첫 사이클에 멈춘다.
**«한 번에 하나만 쓰는가» 를 먼저 보라.** 아니면 공유가 아니라 «환경» 이다.

**상호배제도 그대로 된다.** 같은 Passive Work 의 완료를 보는 것이므로
조건이 Flow 를 가리지 않는다:

```
COND,차체B.이송.셔틀.전진,ComAux,셔틀.후진,,,
```

«셔틀이 돌아와 있어야 쓴다» — A가 쓰고 있으면 후진이 서지 않으므로 B가 기다린다.
**다른 Flow 의 Work 를 직접 참조할 필요가 없다.** 공유 설비 자체가 만나는 자리다.

### 같은 API 를 여러 Call 이 읽는 것과 «여러 번 작업» 은 다르다

> 같은 API 의 완료 하나를 여러 Call 이 읽었다고 제품별 독립 작업을 여러 번 수행한 것은 아니다.
> — Ver110 §3.4

제품마다 따로 작업해야 한다면 **요청마다 새 실행과 그 요청의 완료가 대응**해야 한다.
위 예제가 `공유로봇.A작업` 과 `공유로봇.B작업` 을 **다른 API 로** 나눈 이유다.
하나의 `공유로봇.작업` 을 두 라인이 부르면 «한 번 돈 것을 둘이 읽는» 모델이 된다.

## 14. 검증 경고 읽는 법 — 무엇이 결함이고 무엇이 구조인가

불러오기 뒤 경고는 **두 군데**서 나온다. 둘을 같은 것으로 보면 안 된다.

| | 내는 곳 | 뜻 |
|---|---|---|
| `AI-W…` | 파서 | CSV 표기 문제. **`AI-W2`·`AI-W11` 을 빼고 전부 없애야 한다**<br>(`AI-W13` 은 공유 기동 신호일 때만 예외 — §12) |
| Source 후보 · Group 미Ignore · 토큰 도달불가 | 그래프 검증 | 모델 구조 문제. **일부는 정상이다** |

파서 경고가 0이라고 모델이 깨끗한 것이 아니다. 그래프 검증은 따로 돈다.

**예외는 둘이다 — `AI-W2`(Time 미기입)와 `AI-W11`(IO 미상).**
둘 다 `?` 로 «아직 모른다» 고 적었을 때 나는 경고다. 없애려면 값을 지어내야 하므로,
**모르는 것은 `?` 로 두고 경고를 남기는 편이 옳다**. 나머지 파서 경고는 고쳐 없애야 한다.

`?` 와 빈 칸은 뜻이 다르다 — **빈 칸은 적는 것을 잊은 것이고 `?` 는 알고 비운 것이다.**
IO 를 빈 칸으로 두면 `AI-W3`(OutTag 없음)가 API 마다 하나씩 쏟아지지만,
`?` 로 두면 `AI-W11` 한 줄로 «IO 미상 N건» 이 묶인다.

### `sensor` 표기는 적지 마라

API 행 Detail 에 `sensor` 를 적을 수 있지만 **v1 에서는 아무 일도 하지 않는다**.
단일 API 디바이스의 `DONE` 더미와 Source 후보 경고를 면제하려던 자리인데 구현되지 않았고,
적으면 `AI-W10` 경고만 남는다. 센서임은 **`Virtual/…` 이 이미 말한다** — 출력이 없다는 뜻이다:

```
API,안착센서.PARTON,Virtual/Latch(30),,100MS,%IX3.10.0.01,
```

### Source 후보 — `디바이스_Flow.API` 형태는 결함이 아니다

```
Source 후보: 안착센서 / 안착센서_Flow.PARTON
```

API 가 **하나뿐인** Passive 디바이스에서 반드시 나온다. 이유는 모델이 틀려서가 아니라
캐스케이드가 만드는 재무장 구조 때문이다 — API Work 하나로는 반복 동작을 할 수 없어
`DONE` 더미를 붙이고 `API -Start-> DONE` 과 `API <-ResetReset-> DONE` 으로 잇는다
(`ImportPlan.Device.fs`). 그 `Start` 때문에 API Work 가 Start 네트워크에 들어가는데
정작 선행이 없어 «Source 후보» 로 잡힌다.

**Passive 디바이스 Work 는 토큰을 발생시키지 않는다** — Active 쪽 Call 이 ApiCall 로 구동한다.
그러니 이 경고는 **무시해도 되는 것이 맞다**. Active Flow 의 Work 가 잡혔다면 그때는 진짜 결함이다.

### 그래도 줄일 수 있는 쪽이 있다 — 액추에이터

센서·버튼은 API 1개가 정상이라 경고가 남는다. 하지만 **액추에이터가 API 1개라면 모델링이 덜 된 것**이다.
차체라인 구동부는 거의 전부 짝을 이룬다:

| 적다 만 것 | 실제 |
|---|---|
| `용접로봇.타점` | 타점 · **원위치** |
| `지그.클램프` | 클램프 · **언클램프** |
| `실린더.전진` | 전진 · **후진** |
| `리프트.상승` | 상승 · **하강** |

짝을 적으면 캐스케이드가 두 Work 를 이어 순환을 만들고 `DONE` 을 붙이지 않는다 —
경고가 사라지고, 무엇보다 **모델이 현장과 같아진다**. 로봇은 타점하고 그 자리에 서 있지 않다.

### Group 미Ignore 는 Work 레벨만 본다

`findGroupWorksWithoutIgnore` 는 **Work 화살표만** 훑는다. Call 레벨 `Group` 에는 Ignore 가
필요 없다 — Call 에는 토큰이 없기 때문이다. Call 을 Group 으로 묶고 Ignore 를 찾지 마라.

---

### Call 레벨 Group — 동시에 물려야 하는 것들

한 Work 안에서 여러 Call 을 **함께** 내보낼 때 쓴다. 4점 클램프가 전형이다 —
순서대로 물리면 차체가 틀어진다.

`;` 로 나열하는 것과 무엇이 다른가:

| 표기 | 언제 나가는가 |
|---|---|
| `A ; B` | 각자 선행이 없으므로 **Work 시작 즉시** 둘 다 |
| `핀상승 > A` + `A Group B` | **핀상승이 끝난 뒤** A·B 가 함께 |

`Group` 은 **선행을 옮겨 준다**. 묶인 Call 중 하나가 선행을 가지면 나머지 전원이 그 선행을
물려받는다. 그래서 대표 하나만 이어 두면 된다:

```
WORK,차체.위치결정,,벅지그.핀상승 > 벅지그.클램프LH전 ; 벅지그.클램프LH후 ; 벅지그.클램프RH전 ; 벅지그.클램프RH후,,,
ARROW,차체.위치결정.벅지그.클램프LH전,Group,차체.위치결정.벅지그.클램프LH후,,,
ARROW,차체.위치결정.벅지그.클램프LH전,Group,차체.위치결정.벅지그.클램프RH전,,,
ARROW,차체.위치결정.벅지그.클램프LH전,Group,차체.위치결정.벅지그.클램프RH후,,,
```

넷 모두 `핀상승` 을 선행으로 갖게 된다(SimIndex `CallStartPreds` 실측 확인).
`핀상승 > 각각` 을 네 번 적어도 결과는 같지만, `Group` 은 **«이 넷은 한 덩어리» 라는 의도**가 남는다.

**선행이 없으면 `Group` 은 아무 일도 하지 않는다.** `A ; B ; C` 처럼 나열만 한 Call 들을
묶어 봐야 옮겨 줄 선행이 없다 — 넷 다 Work 시작 즉시 나가는 것은 묶기 전과 똑같다.
Work 레벨 `Start` 가 이미 «앞 공정이 끝난 뒤» 를 보장하고 있다면 `;` 나열로 충분하다.
`Group` 은 **한 Work 안에서 일부 Call 만 선행을 갖는** 경우에 쓴다.

Call 레벨 ARROW 는 `Start` 와 `Group` 둘뿐이다(`AI008`). 4마디 경로로 적는다 — `Flow.Work.디바이스.API`.
